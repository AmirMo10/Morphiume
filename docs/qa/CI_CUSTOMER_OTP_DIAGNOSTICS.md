# تشخیص OTP مشتری در CI

خروجی واقعی [run38270611494](https://github.com/AmirMo10/Morphiume/actions/runs/38270611494) روی checkpoint`3f999fd` طبق بررسی هماهنگ‌کننده:۱۵۰/۱۵۰ واحد/DB موفق، مرورگر۱۴/۱۸موفق و۴شکست همگی در WebKit؛ image skipped و تصویر پذیرفته‌شده ندارد. سه caller در catalog-paging:114، inventory-permissions:93 و shipping-consent:38 به loginCustomer/send-otp پاسخ صریح429 گرفتند. T25 پس از کلیک دریافت کد، input کد را ندید؛ وضعیت HTTP در آن شکست ثبت نشده، بنابراین نسبت‌دادن قطعی آن به429 صحیح نیست.

source نصب‌شدهٔ BetterAuth۱٫۷٫۷ phone plugin، max10/window60 برای مسیرهای `/phone-number` دارد؛ storage به مسیر واقعی و IP/fallback همان مسیر وابسته است. ارسال و verify یک bucket ترکیبی مشترک نیستند. حذف/reset رکورد یا جعل IP/زمان/کد و افزایش limit، راه‌حل QA نیست.

تغییر صرفاً QA: helper امن اکنون Page و APIRequestContext را پشتیبانی می‌کند و دسته‌های ثابت customer send/verify/wrong-code را به diagnostics و sanitizer اضافه می‌کند. فقط429 واقعی یک تلاش دوباره بعد از Retry-After یا X-Retry-After عددی و۲۵۰ms حاشیه اجازه می‌دهد؛ نبود header، بازهٔ کامل تأییدشدهٔ۶۰ثانیه را به‌کار می‌برد. کد valid در هر verify از inbox کنترل‌شدهٔ همان phone خصوصی دوباره خوانده می‌شود؛ ارسال دیگری انجام نمی‌شود. انقضا یا وضعیت غیرمنتظره fail است، نه resend یا retry پنهان.

در T25، outage کنترل‌شده503 باید همان503 و حفظ شماره/نشانی را ثابت کند. کد عمداً متفاوت باید400 واقعی بدهد؛ اگر پیش از رسیدن به validator429 رخ داد، تنها یک انتظار مجاز است و سپس همان آزمون400 ادامه می‌یابد. ورود valid بعد از آن از کد جاری کنترل‌شده استفاده می‌کند. هیچ بدنه، cookie، شماره، OTP، URI، recovery code یا header محرمانه به diagnostics اضافه نشده است. timeout پیش‌فرض۱۲۰ثانیه و global۱۵دقیقه حفظ شده‌اند؛ افزایش فقط پس از شواهد واقعی برای سناریوی مشخص قابل بررسی است.

پس از اعلام صریح آزادشدن shared auth/DB slot، probe واقعاً اجرا و موفق شد. ده phone مصنوعی با native send200، ورود UI بعدی429 باX-Retry-After60 و نبود input کد را تولید کردند؛ مقدار phone حفظ شد. helper روی پاسخ429 واقعی۶۰٫۲۵ثانیه صبر کرد و retry200/input گرفت؛ کد عمداً اشتباه400 و کد جاری200 و سشن verified واقعی داشتند. user ساخته‌شده غیرفعال و سشن صفر شد؛ فقط۱۱phone که پیش از شروع در هیچ user/challenge/mock/library verification وجود نداشتند پاک‌سازی شدند. limiter/runtime/IP/clock تغییر نکرد و هیچ queue/checkout fixture ساخته نشد. `customer-rate-window-reproduction.json` فقط diagnostics/count امن نگه می‌دارد. این شاهد local سازوکار missing-input است و HTTPstatus مورد چهارم CI را از گذشته اثبات نمی‌کند.

اجرای کامل شش spec محلی Chrome/WebKit روی runtime منجمد48583 پس از این اصلاح، **۱۲/۱۲ در۲۷۵٫۷۷۷۴۵۹ثانیه موفق**؛ unexpected/skipped/flaky و Playwright retry صفر. timeout۱۲۰ثانیه و global۱۵دقیقه تغییر نکردند. sanitizer واقعاً۷۱status امن بیرون داد. هر دو T25،503کنترل‌شده و400کد اشتباه را جدا و بدون retry آن outcomeها گرفتند. WebKit API verify مشتری429 باX-Retry-After11 گرفت؛ پس از۱۱٫۲۵ثانیه، inbox همان phone خصوصی دوباره خوانده شد، هیچ resend انجام نشد و verify بومی200 و کل موجودی/رهگیری/لغو نقش قبول شد. دو429رمزساز با۵و۴ثانیه نیز به انتظار واقعی و کد تازه200 رسیدند. cleanup fixtureها و سیاست ارسال طبیعی تمام شد و shared DB window آزاد شد. `browser-summary.json` همین اجرای تازه و `browser-checkpoint-3f999-local.json` شاهد قبلی۱۲/۱۲ است. Linux/Firefox دوباره اجرا نشده‌اند و چهار نتیجهٔ CI گذشته به موفقیت محلی تبدیل یا حذف نمی‌شوند.

پیش‌نیاز guard DB runtime در `SERVER_FIXTURE_PREREQUISITES.md` صرفاً طرح آینده است؛ هیچ اجازهٔ جدید DB یا تغییر guard در این checkpoint OTP فعال نشده است.
