# Native load-fixture preparation — source verified, actual setup unrun

Prepared on 2026-10-12 under the coordinator's source-only authorization. No setup, native handler, app HTTP, PostgreSQL, fixture, worker, migration, deployment or load call was executed for this change. Actual 200-account/200-product setup, fallback-bucket behavior, signup throughput, 200 VU and restored staging remain **unrun**. The accepted immutable image, matching source/schema/auth keys and explicit DB/native window remain prerequisites. The exact loopback database allowlist and mock test/staging gates are unchanged.

`native-fixture-actions.ts` invokes the maintained native handler and keeps its per-path fallback-IP rules. Each send or verify action permits at most one retry, and only after an observed 429 carrying numeric `Retry-After` or `X-Retry-After` between 0 and 60 seconds. Missing, malformed, nonfinite, excessive or date-form intervals fail closed. Other statuses, including a genuine 400 denial, are not retried. The actual interval plus 250 ms is slept in chunks no larger than 60 seconds. No forwarded IP, native-library bypass, limiter row reset, clock change or limit increase is added.

Verification re-reads the current controlled OTP immediately before every actual attempt. A verify 429 does not issue another send. Missing/expired controlled OTP stops setup; no code is guessed or implicitly reissued. Successful native response/session cookies retain the existing private fixture representation. The first issued session is still checked against the target application's real session endpoint to establish key compatibility when setup eventually runs.

The default monotonic setup budget is **30 minutes**, an engineering limit rather than a measured completion time. The budget covers operations and waits; an expired budget does not start another native action. In-flight operations receive an AbortSignal and the runner stops waiting at the budget, but this is **not proof that a native database transaction was cancelled**. Shutdown has a separate bounded 5-second allowance. A pending native/DB outcome is marked for reconciliation, and termination never proves whether it committed. These mechanics have controlled tests; no actual 30-minute setup duration or process/database cancellation has been established.

Before each owned mutation, the runner atomically writes a private ignored `.local/load-setup-progress-<fixtureUUID>.json` record. It contains planned/created product and variant IDs, synthetic phones, known native account IDs, phases, fixed failure classification and reconciliation state. No OTP, password, cookie, token, provider reference, connection URL or raw error is in this progress ledger. A separate `.local/load-setup-latest.json` contains only fixture ID/state/reconciliation status. Unix file/directory modes are 0600/0700; Windows private-folder ACL requirements remain in PERFORMANCE.md. The final `.local/load-fixture.json` alone contains the necessary genuine native cookies and remains ignored/private.

Native account ID is checkpointed before cookie parsing or target-session preflight can fail. Synthetic phone selection first checks that it is absent from the existing user table. A partial product setup retains its planned namespace and IDs even if one of its subsequent rows was not created. Failure emits only fixed stages/statuses/categories, counts and timing configuration, sets a failing exit code and performs **no automatic archive, disable, deletion or replay**. Exact owned rows must be reconciled after pending operations settle; cleanup may then archive verified fixture product IDs/namespaces and disable verified synthetic accounts. Never use a broad phone/slug match, delete order/payment/inventory history, or infer an unknown account from an unrelated existing user.

The coordinator-owned load runner should require the final fixture's `setupStatus: complete`, matching per-fixture progress with `state: complete`/`reconciliationRequired: false`, and a latest-attempt record matching that same fixture ID and complete state. The coordinator accepted this contract and owns its separate implementation/tests; this QA patch does not edit `scripts/run-load.mjs`. A failed preparation exit must always stop orchestration; an old successful fixture/marker on disk cannot be assumed to represent the new attempt, especially after a filesystem failure. The existing full-fixture `validate-ledger.ts --cleanup` is not a partial-setup reconciliation tool.

If trusted process configuration supplies `LOAD_APP_COMMIT`, it must be exactly 40 hexadecimal characters and is recorded as lowercase `appCommit` in all three private records. If absent, `appCommit` is null; the preparer does not invent a server revision from current Git or uncommitted source. This metadata alone does not establish accepted-image/source compatibility. Target `environment` and `baseURL` are recorded consistently; the actual target health environment must equal the declared test/staging environment before mutations. Completion timestamps record when the session fixture is ready, with later partial shutdown/persistence failure still blocking readiness.
