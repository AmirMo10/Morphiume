# Load readiness gate

Coordinator-owned `scripts/load-fixture-state.mjs` rejects legacy, partial, different-target and superseded preparation records before the load runner starts k6. It reads bounded private JSON: fixture at most2MiB, per-fixture progress256KiB, latest pointer8KiB. A UUID is validated before resolving the progress filename; malformed JSON produces one fixed error without reflecting private contents.

The final fixture, complete progress and fixed latest-attempt pointer must have the same fixture ID, timestamps, declared controlled environment, origin and explicit40-hex accepted app revision. Products must be200 unique IDs with completed matching mutations; accounts must be200 distinct matching session-ready IDs with private native cookies. Reconciliation must befalse, the progress failure must benull and no live provider is allowed. The process target must match the recorded origin; query/fragment/userinfo/path-bearing origins are rejected. `run-load.mjs` no longer invents server identity from generator Git HEAD. Operators must supply a trusted `LOAD_APP_COMMIT` and preserve successful setup exit0 as a separate prerequisite; files alone cannot prove a new attempt succeeded after a filesystem failure.

Targeted controlled tests:20/20 in384ms; no actual app HTTP, native handler, PostgreSQL,200-account setup or load ran in this check. Synthetic files use a unique OS temporary directory and are removed after each file test. Tests cover superseded/partial attempts, mismatched metadata, pending account/product mutations, invalid namespace and bounded/malformed private records. This is preparation validation, not accepted image provenance, native key compatibility or capacity evidence. Actual load remains dependent on an accepted source-compatible runtime and a coordinated database window.
