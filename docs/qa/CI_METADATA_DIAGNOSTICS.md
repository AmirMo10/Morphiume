# بررسی عنوان صفحه در CI

نتیجهٔ واقعی [run38275593404](https://github.com/AmirMo10/Morphiume/actions/runs/38275593404) روی checkpoint `538ff1c`، طبق گزارش هماهنگ‌کننده: **۱۵۰/۱۵۰ واحد/DB و۱۷/۱۸ مرورگر Linux موفق**؛ زمان مرورگر۴٫۳دقیقه. تنها شکست Firefox در `public-rtl.spec.ts`، قاعدهٔ جدی `document-title` در axe بود. مسیر آن شکست ثبت نشده است؛ image skipped است و هنوز تصویر پذیرفته‌شده‌ای نداریم. موفقیت ورود مدیریت/OTP مشتری/خرید در این CI، شکست عنوان را توضیح نمی‌دهد. metadata artifact امن۱۸نتیجه،۱۵۲۵بایت و SHA256 `cd3cbf3a67ac250ecc980d29105494d2c4cd61dab5db1611d7b9834710efe01e` فقط از هماهنگ‌کننده دریافت شد؛ فایل artifact مستقلاً دانلود نشد.

در source برنامهٔ اجراشده `76dfcd1`، عنوان products و account ثابت است و admin/login عنوان layout مدیریت را می‌گیرد. عنوان‌های معنایی مورد انتظار به‌ترتیب «عطرها | Morphiume»، «حساب کاربری | Morphiume» و «مدیریت فروشگاه | Morphiume» هستند. سه GET مستقیمِ بدون JavaScript از runtime `48583` هر سه HTTP200 و همان عنوان را داشتند. سند نصب‌شدهٔ Next۱۶٫۴، `node_modules/next/dist/docs/01-app/03-api-reference/04-functions/generate-metadata.md`، توضیح می‌دهد که metadata پویا می‌تواند پس از UI stream شود و template والد بر عنوان فرزند اعمال می‌شود. این توضیح **اثبات علت شکست Firefox نیست**؛ سه مسیر بررسی‌شده metadata ثابت دارند.

اصلاح فقط QA است: آزمون عمومی پس از navigation، تغییر sort و قبل و بعد از axe، HTTP200 سند و عنوان دقیق همان route را با انتظار معنایی Playwright بررسی می‌کند. برای sort، وضعیت HTTP متعلق به سند navigation اولیه است؛ settle شدن URL/sort و عنوان جداگانه بررسی می‌شوند. fallback یا عنوان خالی پذیرفته نمی‌شود. فهرست کامل قواعد WCAG2A/AA/2.1AA/2.2AA و انتظار صفر violation حفظ شده‌اند؛ sleep ثابت، retry سراسری، حذف قاعده یا تغییر برنامه انجام نشد. diagnostics فقط alias ثابت `products|account|admin-login`، phase، status، وجود عنوان، تطابق عنوان، readyState و readiness نگه می‌دارد؛ عنوان واقعی، URL/query، بدنه و cookie صادر نمی‌شوند.

بررسی خواندنی مستقل در۲۰۲۶-۱۰-۱۲، آغاز `2026-10-12T16:36:04.443Z` و زمان۲۱٫۹۷۲ثانیه، روی build `24244` و server `48583` واقعاً انجام شد. Chrome۱۵۴٫۰٫۸۰۳۷٫۹۳ و WebKit۲۷٫۲ در مجموع۶صفحهٔ عمومی، HTTP200، عنوان دقیق، sort صعودی/نزولی و **axe کامل صفر** داشتند. عنوان خالی در برنامهٔ واقعی بازتولید نشد. هر موتور۶درخواست API سمت مرورگر را با پاسخ کنترل‌شده جایگزین کرد؛ هیچ API به سرور ادامه نیافت. سند/RSC/CSS/JS واقعی سرور حفظ شدند. این کنترل لازم بود چون GET سبدِ SiteShell، سبد مهمان می‌سازد. این شاهد، پذیرش cart/session/API واقعی نیست و DB یا limiter را تغییر نداده است.

دو fixture HTML مستقل با H1 قابل مشاهده و document کامل ولی عنوان خالی، هر دو `document-title` واقعی دادند. gate عنوان پس از مشاهدهٔ خالی‌بودن، منتظر تکمیل صریح head ماند؛ بعد از تکمیل، عنوان دقیق و axe صفر شدند. در کنترل منفی هر دو موتور، عنوانِ همیشه خالی پس از انتظار معمول۵ثانیه رد شد و axe همچنان `document-title` داد. این شاهد نشان می‌دهد H1 آماده به‌تنهایی شرط کافی برای عنوان نیست؛ بازتولید Firefox Linux یا تشخیص قطعی CI اصلی محسوب نمی‌شود. خروجی امن در [public-metadata-observations.json](public-metadata-observations.json) ثبت است. اجرای معمول `public-rtl.spec.ts` در این نوبت انجام نشد، چون shared DB باید برای regression بک‌اند بدون تغییر بماند.

کنترل کیفیت واقعاً موفق: scoped ESLint، `pnpm typecheck` و sanitizer مستقل. sanitizer روی نسخهٔ خصوصی گزارش قبلی در دایرکتوری ignored،۱۲نتیجه/۷۱status بومی را حفظ کرد؛۹annotation خراب/نامعتبر حذف و۲metadata معتبر با فقط۷فیلد مجاز صادر شدند. فیلدهای اضافی آزمایشی صادر نشدند. `browser-summary.json` قبلی بازنویسی نشد؛ شاهد۱۲/۱۲محلی OTP مربوط به همان اجرای سابق است. Firefox Windows با خطای launcher قبلی در دسترس نیست و هیچ flag یا دورزدن به‌کار نرفت. نتیجهٔ Linux پس از این اصلاح باید از CI جدید ثبت شود.

برای تکرار probe خواندنی، فقط زمانی که هماهنگ‌کننده همین runtime را آزاد کرده باشد: `pnpm exec tsx tests/e2e/public-title-observe.ts`. این ابزار همهٔ APIهای مرورگر را intercept می‌کند و صرفاً شواهد metadata/axe را می‌سنجد. شواهد این نوبت پس از پایان به هماهنگ‌کننده تحویل شد؛ از آن پس درخواست دیگری به runtime قدیمی اجرا نشد.
