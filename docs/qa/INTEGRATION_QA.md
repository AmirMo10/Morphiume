# آزمون یکپارچهٔ صفحه‌بندی، ارسال و دسترسی انبار

آخرین نتیجهٔ محلی، ۲۰۲۶-۱۰-۱۲: production build هماهنگ‌کننده `24244` و server `48583` در localhost:3000، runtime منجمد checkpoint `76dfcd1`. پس از اصلاح فقط helper QA، اجرای کامل شش spec در Chrome و WebKit **۱۲ از ۱۲ در۲۷۲٫۹۸۴۴۸۹ثانیه موفق**، unexpected/skipped/flaky و Playwright retries صفر بود. خلاصهٔ امن همین اجرا با۴۶ وضعیت بومی در `browser-summary.json` است. شاهد اجرای قبلی۱۲/۱۲ در۲۷۲٫۵۷۰۷۴۷ثانیه با آغاز `2026-10-12T14:46:21.448Z` در `browser-checkpoint-76df-local.json` محفوظ است؛ زمان‌های جدول زیر از آن اجرای پیش از اصلاح helper هستند. runtime اصلاحات نهایی ارسال، تازگی MFA بازپرداخت و projection نقش فعلی پاسخ رهگیری را دارد. scoped ESLint و TypeScript سراسری موفق بودند. CI همین checkpoint، پس از۱۵۰/۱۵۰ واحد/DB،۱۱/۱۸ مرورگر و۷شکست داشت؛ Linux هنوز دوباره اجرا نشده و image پذیرفته‌شده نداریم. [CI_AUTH_DIAGNOSTICS.md](CI_AUTH_DIAGNOSTICS.md) محدودیت‌های واقعی هر مسیر/IP و بازآزمایی مستقل را ثبت می‌کند.

دو اجرای پیش از نتیجهٔ جاری، روی همین build `24244` هرکدام۱۰قبول/۲شکست داشتند. اول، آزمون به‌اشتباه `unitPrice.irr` را می‌خواست؛ قرارداد واقعی `MoneyDto.amountIrr` است. DTO اکنون صریحاً typed است و مقدار دقیق `{amountIrr:"1234560",currency:"IRR"}` بررسی می‌شود. خروجی آن شکست در `browser-final-build-initial.json` محفوظ است. دوم، آزمون ممنوعیت اضافی برای CSV سفارش فرض کرده بود، درحالی‌که `orders.read` با MFA تازه، دریافت پنج ستون وضعیت غیرمالی را مجاز می‌کند. قرارداد به CSV200/no-store/پنج ستون دقیق و ردیف سفارش واقعی، همراه productCSV403 و receipt403 اصلاح شد؛ خروجی شکست در `browser-final-build-csv-assumption.json` محفوظ است. هیچ تغییر محصول برای قبول این دو فرض غلط انجام نشد؛ اجرای بعدی کامل۱۲از۱۲ قبول شد.

اجرای اول دوازده مورد روی build پیشین، ۴ قبول و ۸ شکست داشت: چند نام قدیمی QA، واحد نامعتبر `5 seconds` در cleanup و یک نقص واقعی axe در جدول قابل‌اسکرول سفارش. واحد lock timeout به `5s` اصلاح شد؛ تنظیم مشترک باقی‌مانده فقط با شواهد اولین HTTP واقعی و guard مالک fixture بازگردانده شد. عامل رابط، جدول‌ها را قابل تمرکز با region و نام دسترس‌پذیر کرد؛ build جدید آن اصلاح را واقعاً گذراند. نبود POST هنگام یک شکست ورود قدیمی دلیل اثبات‌شدهٔ محدودیت نرخ نبود؛ آن مورد به 429 نسبت داده نشد.

اجرای جامع دوم روی build `96791`، **۱۰ قبول و ۲ شکست، ۲۵۳٫۹s** داشت. دو شکست فقط نام قدیمی دکمهٔ preview در آزمون موجودی بودند؛ رابط فعلی «پیش‌نمایش تغییرها» است. خروجی امن کامل در `browser-second-run.json` است. خرید کامل Chrome۲۰٫۸s/WebKit۲۹٫۹s، گالری۱۰٫۲s/۲۱٫۸s و صفحات عمومی۴٫۰s/۵٫۵s نیز در همین اجرا قبول شدند. تصویر T25 یک PNG مصنوعی و مشخص آبی #3355B1، ۱۶×۲۰ است؛ قبل از screenshot در هر دو موتور `decode()`، naturalWidth/Height و پاسخ رسانهٔ WebP200 واقعی بررسی شدند. تصویر واقعی کالا ادعا نمی‌شود.

در سابقهٔ build `96791`، بازآزمایی موجودی پس از اصلاح locator به پاسخ واقعی **429** کتابخانه رسید. قاعدهٔ BetterAuth۱٫۷٫۷ حداکثرسه درخواست درده‌ثانیه برای **هر مسیر/IP** است؛ enrollment و renewal دو حساب، مسیر مشترک verify-totp را مصرف می‌کنند. traceهای private،429 و نبود header استاندارد Retry-After را ثابت کردند؛ بررسی بعدی source نشان داد نسخهٔ جاری header زمان را X-Retry-After می‌نامد. helper آن مرحله پس از429 یک‌بار حداقل۱۰٫۱ثانیه صبر کرد و TOTP تازه با handler بومی فرستاد؛ limiter، IP و دادهٔ محدودیت دستکاری نشدند. خروجی شکست در `browser-inventory-rate-window.json` است. بازآزمایی بعد Chrome را قبول کرد ولی WebKit هنگام enrollment به همان429 رسید (`browser-inventory-first-retry.json`). helper محدود برای enrollment هم استفاده شد؛ آن WebKit **۱ از ۱،۳۶٫۹s** قبول شد (`browser-inventory-final-webkit.json`). در آن مرحله فقط پذیرش ترکیبیِ اجراها موجود بود. پس از checkpoint76df، helper برای تمام sign-in/enable/enroll/renew به header واقعی و diagnostics امن اصلاح شد؛ [CI_AUTH_DIAGNOSTICS.md](CI_AUTH_DIAGNOSTICS.md) نتیجهٔ مستقل و محدودیت Linux را ثبت می‌کند.

fixtures فقط در DB با نام `morphiume_staging`، tunnel localhost، mock PSP/SMS و محیط test/staging اجرا می‌شوند. حساب owner اولیه در SQL ساخته می‌شود ولی session، فعال‌سازی MFA، proof و login مشتری از handler واقعی‌اند. نقش انبار از فرم واقعی دعوت ساخته می‌شود؛ ارسال ایمیل واقعی وجود ندارد. قدیمی‌کردن زمان proof فقط برای حساب مصنوعی همین آزمون است؛ موفقیت بعدی به native TOTP وابسته است و proof با SQL جعل نمی‌شود.

۳۰۵ محصول و ۱۲۵ سفارش خالی فقط برای خواندن/صفحه‌بندی با SQL آماده می‌شوند؛ مسیر نوشتن واقعی محصول در T25 جداست. سفارش‌های خالی هرگز reservation یا payment ندارند و فقط همین fixtureها حذف می‌شوند. محصولات بایگانی، حساب‌ها غیرفعال و سشن‌ها حذف می‌شوند. تاریخچهٔ checkout واقعی آزمایشی و receipt/refund/ledger نگه داشته می‌شود. policy مشترک تنها اگر آخرین نویسنده هنوز حساب fixture باشد، در transaction و با قفل همان policy به مقدار/نسخهٔ اولیه بازگردانده می‌شود؛ نویسندهٔ خارجی بازنویسی نمی‌شود.

بزرگ‌نمایی واقعی Chrome: ابزار computer-use سطح فعالی نداشت و ساخت tab عادی Chrome در آن در دسترس نبود؛ native computer API غیرفعال ماند. سپس روش پروفایل موقت مرورگر با source اصلی Chromium بررسی و واقعاً اجرا شد. `ChromeZoomLevelPrefs`، ترجیح `partition.default_zoom_level.x` را برای partition اصلی در HostZoomMap بار می‌کند؛ Blink ضریب را `1.2^level` می‌سازد. دو پروفایل تازهٔ ignored با مقدار۰ و۳٫۸۰۱۷۸۴۰۱۶۹۲۳۹۳۰۸، Chrome۱۵۴٫۰٫۸۰۳۷٫۹۳ را با `viewport:null` و headless عادی اجرا کردند. outer780×580 و screen800×600 ثابت، inner764×485→382×242 و DPR1→2 شدند؛ CSSzoom1 و visualViewport.scale1 ماندند. چهار route واقعی `/products`، `/account`، `/admin/login` و `/guide` در هر دو پروفایل HTTP200، بدون سرریز افقی، Tab روی کنترل و axe با tags WCAG2A/AA/2.1AA/2.2AA صفر داشتند. پروفایل کاربر، CSSzoom، DPR override، pinch/PageScale و flag سفارشی تغییر نکردند. شواهد عددی و لینک source در `native-zoom-observations.json` هستند. این شاهد zoom بومی در runtime headless Chrome است؛ کنترل دستی GUI، screen reader و دستگاه واقعی هنوز اجرا نشده‌اند. screenshot Playwright در این zoom، عرض فیزیکی را بریده نشان داد و به‌عنوان تصویر معتبر نگه‌داری نشد.

probe اولیهٔ build `96791` قبل از اصلاح مسیر `/catalog` به `/products`، همهٔ قواعد axe را به‌جای دامنهٔ WCAG اجرا کرد؛ best-practice `region` برای `.environment-banner` گزارش شد و به coordinator تحویل داده شد. build جاری، region نام‌دار محیط آزمایشی دارد؛ probe جامع all-rules جدا دوباره اجرا نشده است. مشاهدهٔ zoom بومی بر build پیشین محفوظ است و به‌عنوان اجرای دستی یا جدید این build ارائه نمی‌شود. Firefox Windows همچنان بدون دورزدن launcher آزموده نمی‌شود؛ نتیجهٔ Linux باید از CI همان source ثبت شود.

افزونهٔ رهگیری موجودی در نتیجهٔ جاری واقعاً اجرا و در هر دو موتور قبول شد: guest cart پیش از ورود، OTP بومی، quote/checkout و verify mock سرور، سپس GET و دو PATCH رهگیری با نقش fulfillment. مبلغ‌های سفارش و item حذف، refund خالی و payment/refund event absent بودند؛ no-store، product CSV و receipt403 و CSV وضعیت سفارش200 با پنج ستون بررسی شدند. یک receipt/shipment و stock6→5 در PG واقعی تأیید شدند؛ paid یا grant با SQL جعل نشد.

دستور مرورگر پس از اعلام آماده‌بودن build: `E2E_CHROMIUM_CHANNEL=chrome pnpm test:e2e --project=chromium --project=webkit`، اکنون شش spec و دوازده مورد محلی. سه موتور Linux هجده مورد خواهند داشت. raw trace/report فقط ignored است و sanitizer فقط title/status/timing/count بیرون می‌دهد. آزمون مشترک policy با suite DB دیگر هم‌زمان اجرا نمی‌شود.

load آماده به مسیر فعلی `/api/catalog/page?pageSize=24` و نه endpoint legacy منتقل شد؛ خواندن کاتالوگ ۲۰۰ محصول، صفحه‌های ۱ تا ۹ را انتخاب می‌کند. هر محصول fixture یک ردیف واقعی product_image نمونهٔ مشخص دارد. `k6 inspect --execution-requirements` روی فایل اصلاح‌شده واقعاً موفق شد: max۲۰۰VU، plateau۲۰دقیقه و کل۲۵دقیقه۳۰ثانیه. هیچ درخواست load یا ادعای ظرفیت از inspect نتیجه نمی‌شود.
