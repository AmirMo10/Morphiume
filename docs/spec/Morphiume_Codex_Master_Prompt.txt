پرامپت اجرایی ساخت فروشگاه Morphiume با Codex
نسخهٔ ۱ — تهیه‌شده در ۱۲ اکتبر ۲۰۲۶

از اینجا تا پایان فایل، دستور ساخت پروژه است. این سند مشخصات اجرای آینده را تعریف می‌کند؛ وجود آن به معنی ساخته‌شدن سایت، نصب Skillها، قبولی آزمون‌ها یا آماده‌بودن درگاه واقعی نیست.

۱. مأموریت و نتیجهٔ مورد انتظار

تو هماهنگ‌کننده و مهندس ارشد یک تیم چندعاملی هستی. یک فروشگاه کامل، قابل نگهداری، قابل استقرار و قابل آزمون برای برند مستقل عطر Morphiume بساز. کاربر اصلی ایرانی است؛ تمام مسیرهای خرید و مدیریت باید فارسی روان، راست‌به‌چپ و برای فرد غیرمتخصص قابل فهم باشند.

املای قطعی برند در کد، متادیتا، لوگو، رسید و رابط، دقیقاً Morphiume است. املای فارسی رسمی، دامنه، آدرس، تلفن، سابقهٔ برند و مشخصات محصولات را حدس نزن. مقدارهای نامعلوم را در تنظیمات و فهرست نیازمندی‌های صاحب کسب‌وکار ثبت کن.

کار را به پیشنهاد یا ماکت محدود نکن. پس از بررسی مخزن، طراحی، کدنویسی، یکپارچه‌سازی، آزمون، رفع اشکال و مستندسازی را مرحله‌به‌مرحله انجام بده. تا جایی که دسترسی موجود اجازه می‌دهد نسخهٔ کامل محلی و محیط آزمایشی آماده کن. رابط باید به منطق واقعی سرور و پایگاه داده متصل باشد.

فرض پایه: یک فروشگاه تک‌برند و تک‌فروشنده، یک انبار در شروع، فروش داخل ایران، زبان fa-IR، نمایش تومان، ورود مشتری با شمارهٔ همراه و درگاه ایرانی. کاتالوگ از صفر تا چندصد محصول قابل استفاده باشد. هدف اولیه حدود ۲۰۰ حساب کاربری است؛ ۲۰۰ خریدار هم‌زمان یک سناریوی آزمون مستقل است.

برای تصمیم‌های برگشت‌پذیر از قضاوت مهندسی استفاده کن و پیش برو. اطلاعات نامعلوم را شفاف ثبت کن؛ برای دامنه، قرارداد درگاه، مجوز فونت تجاری یا اطلاعات واقعی کالا مقدار ساختگی نساز. نبود کلید سرویس نباید طراحی و پیاده‌سازی مستقل را متوقف کند: adapter آزمایشی، آزمون قرارداد و راهنمای اتصال بساز و وابستگی واقعی را مسدود و مشخص نگه دار. انتشار عمومی، تراکنش واقعی و تغییر دادهٔ عملیاتی فقط در محدودهٔ مجوز صاحب پروژه انجام شود.

۲. بررسی اولیه و تصمیم‌های فنی

ابتدا README، AGENTS.md، وضعیت Git، ساختار مخزن، فایل قفل وابستگی‌ها و تنظیمات موجود را بخوان. تغییرهای صاحب پروژه را حفظ کن. اگر پروژه از قبل پشتهٔ سالم و سازگاری دارد، بدون دلیل مستند آن را بازنویسی نکن.

نسخهٔ نصب‌شدهٔ Codex و قابلیت واقعی subagent، مهارت‌های موجود، ابزار مرورگر، دسترسی شبکه و امکان اجرای Docker را بررسی کن. فقط از تنظیمات سازگار با همان نسخه استفاده کن. عبارت «آخرین نسخه» را از حافظه به عدد تبدیل نکن؛ نسخه‌های پایدار، پشتیبانی‌شده و دارای اصلاحات امنیتی را از مستندات رسمی بررسی، ثبت و در lockfile و runtime pin کن.

خروجی شروع:
- docs/PROJECT_BRIEF.md: هدف، فرض‌ها، محدودیت‌ها و نیازمندی‌های کسب‌وکار.
- docs/IMPLEMENTATION_PLAN.md: مراحل، مالک هر کار، وابستگی‌ها و معیار پذیرش.
- docs/STATUS.md: کارهای انجام‌شده، کار جاری، مانع واقعی و قدم بعد.
- docs/adr/: تصمیم‌های مهم معماری با دلیل و هزینهٔ نگهداری.
- docs/SOURCE_REGISTER.md: منابع رسمی، نشانی دقیق، تاریخ مشاهده و موارد استفاده.
- docs/OWNER_INPUTS.md: دامنه، اطلاعات برند، محصولات، PSP، پیامک، ارسال، سیاست‌ها و مجوزها.

مستندات کوتاه و کاربردی باشند و با کد به‌روز بمانند. فقط بخش مرتبط را به هر عامل بده؛ کل مخزن و تمام Skillها را بی‌دلیل در زمینهٔ همهٔ عامل‌ها نریز.

۳. معماری پیشنهادی

پیش‌فرض یک Modular Monolith با TypeScript strict است:
- Next.js پایدار و اصلاح‌شده برای فروشگاه، پنل مدیریت و ورودی‌های سمت سرور.
- React، Tailwind CSS و مؤلفه‌های دسترس‌پذیر با طراحی اختصاصی Morphiume.
- PostgreSQL به‌عنوان مرجع قطعی کاربران، قیمت، موجودی، سفارش، پرداخت و رخدادها.
- یک ORM یا query builder جاافتاده با migration؛ یکی را انتخاب کن و دلیل بنویس.
- کتابخانهٔ احراز هویت نگهداری‌شده و سازگار با OTP و MFA انتخابی؛ رمزنگاری و سشن را از صفر اختراع نکن.
- یک worker مستقل برای outbox، تطبیق پرداخت، آزادسازی رزرو، اعلان و پردازش تصویر.
- Object Storage سازگار با S3 یا سرویس مناسب برای رسانه؛ اصل تصویر و خروجی عمومی جدا.
- Nginx برای reverse proxy؛ Docker Compose برای توسعه و استقرار اولیهٔ قابل بازتولید.
- کش و rate limiter مشترک فقط در صورت نیاز کتابخانه یا چندنمونه‌ای شدن؛ Redis/Valkey را با بررسی سازگاری انتخاب کن. دفتر موجودی و پرداخت داخل کش نباشد.

ماژول‌های سرور: identity، catalog، media، pricing، cart، inventory، checkout، payments، orders، fulfillment، returns، content، notifications، audit.

مرز server/client روشن باشد. دسترسی DB و secrets فقط server-only؛ عملیات حساس از یک لایهٔ مشترک احراز مجوز و منطق دامنه عبور کنند. هم صفحه، هم API و هم Server Action مستقیم باید امن باشند.

برای این مقیاس، Kubernetes، Kafka، چندین backend موازی، موتور جست‌وجوی جدا، microservice و LLM در مسیر خرید پیش‌فرض نیستند. برای جست‌وجوی اولیه، PostgreSQL با ستون نرمال‌شده و index مناسب را بررسی کن. استفاده از هستهٔ تجارت آماده فقط زمانی قابل قبول است که با بررسی مستند نشان بدهی با پرداخت ایرانی، RTL، مجوز نرم‌افزار و منابع هدف سازگار و نگهداری آن ساده‌تر است؛ آن را هم‌زمان با یک هستهٔ سفارشی موازی نساز.

خود فروشگاه برای اجرا به مدل هوش مصنوعی یا GPU نیاز نداشته باشد. Multi Agent مربوط به فرایند توسعه است.

۴. اجرای واقعی Multi Agent

عامل هماهنگ‌کننده مسئول قراردادهای مشترک، اولویت‌بندی، یکپارچه‌سازی و پذیرش نهایی است. عامل‌های تخصصی را واقعاً فراخوانی کن و نتیجهٔ واقعی آن‌ها را دریافت کن:

- Product & Brand Designer: معماری اطلاعات، هویت بصری، لوگو و UX خرید/مدیریت.
- Frontend Engineer: فروشگاه، مؤلفه‌ها، فرم‌ها، RTL و اتصال به دادهٔ واقعی.
- Commerce & Backend Engineer: مدل داده، قیمت‌گذاری، موجودی، سفارش، پرداخت و worker.
- Security Reviewer: threat model، احراز هویت، مجوزها، بررسی کد و آزمون سوءاستفاده.
- DevOps & SRE Engineer: شبکه، کانتینر، CI/CD، پایش، بکاپ و بازیابی.
- QA & Performance Engineer: سناریوهای پذیرش، E2E، دسترس‌پذیری و آزمون ظرفیت.
- Persian UX Editor: متن فارسی، اصطلاحات عطر، راست‌به‌چپ، ارقام و خطاهای فرم.

این‌ها نقش‌ها هستند؛ لازم نیست همه هم‌زمان باز باشند. تعداد عامل‌های فعال را به ظرفیت واقعی محیط محدود کن؛ شروع پیشنهادی یک هماهنگ‌کننده و حداکثر سه عامل فعال است. کارهای مستقل را موازی و کارهای وابسته را پس از قرارداد مشترک اجرا کن.

برای هر مأموریت مشخص کن: هدف، ورودی، فایل‌های مجاز، ممنوعیت ویرایش مشترک، خروجی، وابستگی و تست لازم. از worktree یا مالکیت انحصاری مسیرها استفاده کن. تغییر schema/migration، lockfile و تنظیمات ریشه یک مالک داشته باشد. عامل‌ها تغییر یکدیگر را بازنویسی نکنند.

هر تحویل عامل شامل نتیجه، فایل‌های تغییرکرده، آزمون‌های واقعاً اجراشده، شکست‌ها و ابهام‌ها باشد. نام‌گذاری چند نقش داخل یک پاسخ، اجرای واقعی چندعاملی محسوب نمی‌شود. اگر محیط subagent ندارد، این محدودیت را اعلام و تنظیم یا روش اجرای موازی سازگار را آماده کن؛ خروجی جعلی از عامل‌ها نساز.

در صورت پشتیبانی نسخهٔ نصب‌شده، نقش‌ها را در .codex/agents/ و تنظیمات پروژه را در .codex/config.toml تعریف کن. schema را از مستندات جاری همان نسخه بررسی کن؛ مدل ناموجود یا گزینهٔ منسوخ تحمیل نکن و سیاست مجوزهای محیط را تغییر نده.

۵. Skillهای محلی و پیش‌نیازهای داخل پروژه

در شروع، AGENTS.md ریشه را کوتاه و اجرایی بنویس: دستورات واقعی اجرا/آزمون، قواعد مالی و امنیتی، مالکیت فایل‌ها، نحوهٔ استفاده از Skillها و تعریف اتمام.

سپس پوشه‌های زیر را داخل .agents/skills/ همین مخزن ایجاد کن:

1) morphiume-brand-ux
   کاربرد: هویت برند، لوگو، ساختار صفحات، جریان کشف و خرید.
   ورودی: brief و منابع طراحی.
   خروجی: design tokens، طرح صفحات، سناریوهای کاربر و SVGهای هویت.

2) morphiume-fa-rtl
   کاربرد: هر متن یا مؤلفهٔ قابل مشاهده برای مشتری و ادمین.
   ورودی: واژه‌نامه، اطلاعات تأییدشدهٔ برند و صفحات واقعی.
   خروجی: متن فارسی و بازبینی ارقام، bidi، فرم و راست‌به‌چپ.

3) morphiume-storefront
   کاربرد: صفحهٔ اصلی، جست‌وجو، محصول، سبد و تکمیل خرید.
   خروجی: رابط responsive متصل به داده، تمام stateها و آزمون مسیر خرید.

4) morphiume-admin
   کاربرد: مدیریت محصول، محتوا، سفارش، انبار و مشتری.
   خروجی: جریان کاری ساده، کنترل مجوز، پیش‌نویس/انتشار و audit.

5) morphiume-commerce
   کاربرد: تغییر قیمت، تخفیف، انبار، سفارش یا مرجوعی.
   خروجی: invariants، تراکنش کوتاه، migration و تست هم‌زمانی/محاسبات.

6) morphiume-iran-payments
   کاربرد: اتصال PSP، callback، verify، reconciliation و refund.
   ورودی: مستندات رسمی همان provider و قرارداد واحد مبلغ.
   خروجی: adapter واقعی و آزمایشی، تست قرارداد، وضعیت‌های خطا و تکرار.

7) morphiume-auth-security
   کاربرد: auth، session، نقش، API، فایل، secrets و تغییر مرز اعتماد.
   خروجی: threat model به‌روز، کنترل امنیتی و آزمون سوءاستفادهٔ مرتبط.

8) morphiume-ops
   کاربرد: build، استقرار، شبکه، مانیتورینگ، backup و restore.
   خروجی: تنظیمات قابل اجرا، runbook و شواهد راه‌اندازی/بازیابی.

9) morphiume-qa
   کاربرد: پذیرش قابلیت و انتشار.
   خروجی: تست مستقل، شواهد مرورگر، گزارش شکست و بازآزمایی اصلاح.

10) morphiume-seo-performance
    کاربرد: متادیتا، دادهٔ ساخت‌یافته، index، رسانه، کش و ظرفیت.
    خروجی: بررسی SEO، بودجهٔ عملکرد، تست کش و اندازه‌گیری روی build واقعی.

هر پوشه باید SKILL.md معتبر و غیرخالی با YAML front matter شامل name و description داشته باشد. description زمان استفاده و مرز کار را روشن کند. بدنه شامل ورودی، مراحل، قواعد پروژه، تعریف اتمام و مسیر منابع مرتبط باشد. اگر script لازم است، آن را واقعاً بنویس و اجرا کن؛ پوشهٔ خالی یا TODO را Skill تمام‌شده معرفی نکن.

دستورهای عمومی برنامه‌نویسی را تکثیر نکن. به قواعد ویژهٔ Morphiume، نمونهٔ متن فارسی، قرارداد پول و سناریوهای خطا تمرکز کن. فایل‌های طولانی را در references نگه دار و فقط هنگام نیاز بخوان.

اگر Skill بیرونی لازم شد، اول وجود واقعی آن، ناشر، مجوز، نسخه/commit و محتوایش را بررسی کن. نصب اسکریپت ناشناخته یا تکیه بر نام‌های خیالی ممنوع است. منبع و دلیل استفاده در docs/SKILLS_MANIFEST.md ثبت شود. هیچ secret یا دسترسی production در Skill قرار نگیرد. این Skillها مخصوص مخزن باشند؛ تنظیمات عمومی کاربر را بی‌دلیل تغییر نده.

Skillها و پیکربندی‌های معتبر را در Git همین پروژه نسخه‌بندی کن. قابلیت کشف شدن آن‌ها را در Codex بررسی کن؛ اگر محیط تنها خواندن مستقیم را پشتیبانی می‌کند، همان محدودیت را گزارش بده. وجود فایل‌ها را با نصب یا فعال‌شدن اثبات‌نشده یکی ندان.

۷. هویت بصری و لوگو

جهت پیشنهادی طراحی: فضایی آرام، دقیق و معاصر با تمرکز بر شیشهٔ عطر، عکس باکیفیت و تایپوگرافی خوانا. رنگ پایهٔ پیشنهادی استخوانی #F6F2EB، متن زغالی #20211F و رنگ امضای شرابی عمیق #5C2333 است. رنگ‌های معنایی خطا/موفقیت مستقل باشند. این پالت پیشنهاد اولیه است؛ کنتراست واقعی تمام کاربردها اندازه‌گیری شود.

صفحات خرید و ادمین روشن و خوانا؛ فضای تیره در روایت یا کمپین به اندازهٔ محدود قابل استفاده است. فاصله‌گذاری منظم، grid دقیق، خطوط ظریف، اندازهٔ مناسب عکس و انتقال‌های کوتاه بساز. از قالب عمومی پر از کارت یکسان، افکت شیشه‌ای تزئینی، گرادیان بی‌هدف و ازدحام عناصر دوری کن. سادگی نباید باعث پنهان‌شدن قیمت، موجودی یا دکمهٔ خرید شود.

سه اتود اصیل لوگو بساز:
- لوگوتایپ Morphiume با تنظیم دقیق فاصلهٔ حروف و یک تغییر ظریف اختصاصی.
- مونوگرام M با فضای منفی ساده الهام‌گرفته از انتشار رایحه.
- نشانهٔ انتزاعی با دو منحنی کنترل‌شده همراه لوگوتایپ.

یک مسیر منسجم را با دلیل انتخاب و در سایت اجرا کن؛ دو اتود دیگر را برای بازبینی نگه دار. خروجی نهایی وکتور SVG تمیز و قابل ویرایش، تک‌رنگ، روشن/تیره، favicon و نسخهٔ مناسب لیبل باشد. حداقل اندازه، حریم و رفتار در ۱۶، ۳۲ و ۱۲۸ پیکسل بررسی شود. تصویر bitmap داخل SVG را لوگوی وکتور معرفی نکن. دربارهٔ ثبت تجاری یا یکتایی حقوقی بدون بررسی ادعا نکن.

لوگو در حالت ثابت کامل و خوانا باشد. موشن اختیاری، کوتاه و سازگار با prefers-reduced-motion باشد. انیمیشن ورود اجباری، صدای خودکار، scroll hijacking، نشانگر سفارشی اجباری یا WebGL ضروری برای خرید نساز.

عکس واقعی محصول بر تصویر مفهومی اولویت دارد. تصاویر نمونه فقط در توسعه برچسب‌دار باشند. شیشه، رنگ، حجم، بسته‌بندی یا ترکیب محصول واقعی را بدون دادهٔ صاحب برند اختراع نکن. دارایی‌ها و مجوزها در docs/ASSET_REGISTER.md ثبت شوند.

۸. فارسی، فونت و دسترس‌پذیری

فونت پایهٔ پیشنهادی Vazirmatn است. WOFF2 مناسب را self-host کن و مجوز OFL را همراه فایل‌ها نگه دار. برای فونت تجاری ابتدا مجوز واقعی لازم است. متن‌ها و کنترل‌های اصلی روی موبایل خوانا باشند؛ وزن و اندازه را برای خوانایی انتخاب کن، نه تزئین. فاصله‌گذاری حروف لاتین لوگو را به متن متصل فارسی اعمال نکن.

ریشهٔ سند lang=fa و dir=rtl داشته باشد؛ فقط text-align کافی نیست. از CSS logical properties و ترتیب منطقی DOM استفاده کن. نام لاتین، ایمیل، شمارهٔ تماس و شناسه‌ها bidi-isolated باشند. ورودی تلفن، OTP و کدپستی string با inputmode مناسب باشد؛ صفر اول حذف نشود.

ارقام فارسی، عربی و لاتین در ورودی‌های عددی پذیرفته و به شکل داخلی ثابت تبدیل شوند. شمارهٔ همراه به قالب canonical واحد تبدیل شود و uniqueness در DB داشته باشد. کلید جست‌وجو جدا از متن اصلی، ی/ک و فاصله/نیم‌فاصله را نرمال کند؛ متن اصلی حفظ شود. هیچ نرمال‌سازی زبانی روی password انجام نشود.

زمان رخدادها UTC ذخیره و برای کاربر جلالی نمایش داده شود. زمان‌بندی کسب‌وکار با Asia/Tehran محاسبه شود. «روز تحویل» که تاریخ بدون ساعت است، با timestamp اشتباه نشود.

لحن فارسی: محترمانه، کوتاه، مشخص و طبیعی. متن ترجمه‌زده یا وعدهٔ اغراق‌آمیز ننویس. اصطلاح فنی عطر را در صورت نیاز با توضیح کوتاه روشن کن. واژه‌نامه و نمونه‌های زیر را در docs/FA_COPY_GUIDE.md ثبت کن:

- افزودن به سبد خرید
- مشاهدهٔ عطرها
- راهنمای انتخاب رایحه
- انتخاب حجم
- ویرایش نشانی
- ادامه و انتخاب روش ارسال
- پرداخت ۱٬۲۹۰٬۰۰۰ تومان
- کد تأیید را وارد کنید.
- کد تأیید منقضی شده است. دوباره درخواست کد بدهید.
- این حجم فعلاً موجود نیست.
- قیمت این محصول تغییر کرده است. مبلغ به‌روز را پیش از پرداخت بررسی کنید.
- پرداخت هنوز تأیید نشده است. نتیجه از همین صفحه قابل پیگیری است.
- تغییرات محصول ذخیره شد.
- محصول منتشر شد.

عدد قیمت در نمونه بالا صرفاً نمونهٔ قالب متن است و قیمت واقعی هیچ کالایی نیست.

هدف دسترس‌پذیری WCAG 2.2 AA باشد: semantic HTML، نام مناسب کنترل، برچسب واقعی فرم، خطای متصل به فیلد، focus واضح، ترتیب صفحه‌کلید، skip link، مدیریت focus در dialog، اعلان تغییر سبد با live region و کنتراست کافی.

هدف طراحی دکمه‌های لمسی حداقل ۴۴×۴۴ CSS px است؛ این را با حداقل ۲۴×۲۴ معیار AA و استثناهای رسمی آن یکی ندان. بزرگ‌نمایی، صفحه‌خوان و عرض ۳۲۰ پیکسل آزمون شوند. کنترل فقط-hover، placeholder به جای label و معنی‌رسانی فقط با رنگ قابل قبول نیست.

۹. صفحات و مسیر مشتری

صفحات لازم:
- صفحهٔ اصلی با معرفی کوتاه برند، CTA واضح، عطرهای منتخب، خانواده‌های رایحه و خدمات واقعی.
- فهرست عطرها و مجموعه‌ها با فیلتر کاربردی و حفظ حالت در URL.
- جست‌وجوی فارسی/لاتین، پیشنهاد مرتبط، حالت بی‌نتیجه و اصلاح فیلترها.
- صفحهٔ محصول و تنوع‌های حجم.
- سبد خرید و تکمیل خرید.
- نتیجهٔ پرداخت در وضعیت موفق، ناموفق، لغوشده و نامشخص.
- ورود با شمارهٔ همراه، پروفایل، نشانی‌ها، سفارش‌ها و علاقه‌مندی‌ها.
- پیگیری سفارش مهمان با احراز امن و بدون افشای اطلاعات دیگران.
- راهنمای انتخاب رایحه و مقالات آموزشی قابل مدیریت.
- دربارهٔ برند، تماس، پرسش‌های متداول، ارسال، مرجوعی، حریم خصوصی و شرایط استفاده.
- ۴۰۴، خطای قابل بازیابی، نبود موجودی و حالت نگهداری.

داده‌های واقعی از پنل قابل مدیریت باشند. سربرگ، پاورقی، اطلاعات تماس، بنر و پیوندهای خدمات hardcode غیرقابل‌ویرایش نباشند. بخش‌های وابسته به خدمتی که هنوز وجود ندارد با feature flag مخفی شوند.

جست‌وجو، دیدن قیمت و ساخت سبد نیازمند ورود نباشد. پیش‌فرض تکمیل خرید: خرید بدون ساخت پروفایل اجباری، با تأیید کوتاه شمارهٔ همراه پس از ورود اطلاعات ضروری و پیش از آغاز پرداخت. ایجاد پروفایل کامل اختیاری باشد. رفتار شمارهٔ متعلق به حساب قبلی، مجوز مشاهدهٔ نشانی‌های ذخیره‌شده و زمان درخواست OTP روشن و آزموده باشند. ایمیل، تاریخ تولد و اطلاعات غیرضروری اجباری نشوند.

سبد با refresh و بازگشت از درگاه حفظ شود؛ ادغام سبد مهمان پس از ورود رفتار مشخص و تست داشته باشد. ورود/خروج روی دستگاه مشترک نباید نشانی و دادهٔ خصوصی کاربر قبلی را باقی بگذارد.

در جزئیات سفارش، مشتری واجد شرایط بتواند درخواست لغو یا مرجوعی ثبت کند و وضعیت رسیدگی و بازپرداخت را ببیند. گزینه‌ها مطابق وضعیت واقعی سفارش و سیاست فروش نمایش داده شوند. علاقه‌مندی برای مهمان می‌تواند محلی باشد؛ ذخیره/حذف و ادغام آن برای حساب احرازشده تعریف شود. اگر نقد و امتیاز فعال است، ثبت نظر، نشان خریدار تأییدشده، گزارش نظر و مدیریت محتوای نامناسب کامل باشد؛ در غیر این صورت این بخش مخفی بماند.

فیلترها فقط بر اساس دادهٔ موجود کاتالوگ: خانوادهٔ رایحه، حجم، قیمت، غلظت و موجودی. تعداد نتیجه و فیلترهای فعال روشن باشند. مرتب‌سازی «پرفروش» تنها از دادهٔ واقعی سفارش و بازهٔ تعریف‌شده ساخته شود.

۱۰. صفحهٔ محصول مخصوص عطر

در اولین بخش صفحه، نام، تصویر، قیمت دقیق تنوع انتخاب‌شده، حجم، موجودی، معرفی کوتاه و دکمهٔ خرید واضح باشد. در موبایل CTA ثابت می‌تواند استفاده شود، به شرط آنکه محتوا، پیام خطا، کنترل‌ها و نشانگر فوکوس را نپوشاند و دسترسی با صفحه‌کلید را مختل نکند.

فیلدهای محصول: نام، slug، SKU تنوع، حجم میلی‌لیتر، غلظت، خانوادهٔ رایحه، نت‌های آغازین/میانی/پایه، توصیف کوتاه، توضیح کامل، تصاویر، اطلاعات نگهداری و هشدارهای تأییدشده، وزن/ابعاد بسته برای ارسال در صورت نیاز.

انتخاب حجم باید قیمت، موجودی، شناسهٔ تنوع و تصویر مربوط را هماهنگ تغییر دهد. تفاوت حجم و غلظت را پنهان نکن. نبود موجودی به‌وضوح نمایش داده شود.

ماندگاری، پخش بو، کشور تولید، اصالت، ترکیبات، مجوز، ضدحساسیت‌بودن و ادعاهای مشابه فقط از دادهٔ معتبر برند بیایند. دادهٔ نامعلوم را جعل نکن. نقد، امتیاز و برچسب خریدار واقعی بر اساس شواهد سفارش باشند؛ نمونهٔ ساختگی به production منتقل نشود.

راهنمای انتخاب رایحه با چند سؤال کوتاه و منطق قابل توضیح بر اساس ویژگی محصول کار کند. نتیجه علت پیشنهاد داشته باشد. AI پولی، ادعاهای روان‌شناختی یا ثبت اطلاعات حساس برای این قابلیت لازم نیست.

بستهٔ نمونه، هدیه و یادداشت هدیه در صورت امکان واقعی عرضه شوند. برای پک قابل انتخاب، شمارنده، محدودیت، قیمت و موجودی اجزای پک شفاف باشند. اعتبار خرید سمپل و قواعد تخفیف تنها با سیاست مصوب فعال شوند.

۱۱. سبد، آدرس و تکمیل خرید

مسیر کوتاه و قابل فهم: بررسی سبد، اطلاعات گیرنده/نشانی، روش ارسال، جمع‌بندی و پرداخت. بازگشت به مرحلهٔ قبل اطلاعات واردشده را پاک نکند. دوبار کلیک یا چند تب با کنترل idempotency به درخواست تکراری سفارش منجر نشود. قبل از ایجاد تلاش پرداخت جدید، وضعیت تلاش قبلی نامشخص تعیین تکلیف شود؛ اگر با وجود این دو دریافت واقعی رخ داد، هر دو ثبت و پرداخت اضافی طبق بخش پرداخت رسیدگی شود.

سبد تغییر تعداد، حذف کالا، اعمال و حذف کد تخفیف، خطای قابل فهم کد، محاسبهٔ مجدد سمت سرور و حالت سبد خالی با مسیر ادامهٔ خرید داشته باشد.

نشانی: نام گیرنده، شمارهٔ تماس، استان، شهر، نشانی، پلاک، واحد اختیاری و کدپستی. فهرست استان/شهر منبع و امکان به‌روزرسانی داشته باشد. آدرس برای شخص دیگر و سفارش هدیه پوشش داده شوند.

پیش از هدایت به درگاه، جمع کالا، تخفیف، هزینهٔ ارسال، مالیاتِ واقعاً قابل اعمال و مبلغ نهایی نمایش داده شوند. آستانهٔ ارسال رایگان و تخفیف قابل تنظیم و روی سرور ارزیابی شوند. اگر قیمت/موجودی تغییر کرد، تأیید مبلغ به‌روز را بگیر.

زمان آماده‌سازی را از زمان حمل جدا کن. هزینه و SLA ارسال از تنظیمات یا قرارداد واقعی بیاید. سازگاری حمل عطر و بسته‌بندی با شرکت ارسال منتخب پیش از فعال‌سازی بررسی شود.

۱۲. پنل مدیریت آسان و کامل

ناوبری: نمای کلی، محصولات، موجودی، سفارش‌ها، مشتریان، تخفیف‌ها، محتوا، گزارش‌ها و تنظیمات. آمار فقط از دادهٔ واقعی ساخته شود و حالت شروع با صفر داده طراحی شود.

محصول جدید با جریان کوتاه:
۱) نام و اطلاعات پایه
۲) حجم، قیمت و موجودی
۳) تصاویر
۴) توضیح رایحه و اطلاعات تکمیلی
۵) پیش‌نمایش
۶) انتشار

پیش‌نویس خودکار یا ذخیرهٔ روشن، هشدار خروج با تغییر ذخیره‌نشده، اعتبارسنجی کنار فیلد و جلوگیری از انتشار ناقص لازم است. اعتبارسنجی باید در سرور هم اجرا شود. پیش‌نمایش محرمانه و خارج از index عمومی باشد.

ویرایش گروهی قیمت/موجودی، تکرار محصول و CSV با پیش‌نمایش و گزارش خطای سطری فراهم شود. import ابتدا dry run داشته باشد و دادهٔ اشتباه را نیمه‌کاره منتشر نکند. export از نظر مجوز و formula injection امن باشد.

مدیریت سفارش: جست‌وجو و فیلتر، timeline، وضعیت مالی مستقل، روش ارسال، کد رهگیری، یادداشت داخلی، درخواست لغو/مرجوعی، صورتحساب قابل چاپ و اعلان‌های مرتبط.

ویرایش قیمت محصول نباید سفارش پرداخت‌شده را عوض کند. حذف محصول سابقهٔ سفارش را از بین نبرد. تغییر حساس، ویرایش گروهی و اصلاح موجودی، actor/time/reason قابل پیگیری داشته باشند.

نقش‌ها: مالک، مدیر محتوا/محصول، مسئول ارسال/انبار، پشتیبانی و مالی. جدول مجوز ریزدانه بساز. نقش پشتیبانی به‌صورت پیش‌فرض اجازهٔ بازپرداخت یا تغییر نقش کاربران را نداشته باشد. مسئول انبار فقط دادهٔ لازم برای آماده‌سازی/ارسال را ببیند. حذف یا غیرفعال‌کردن آخرین مالک فعال مهار شود.

ویرایش هم‌زمان محصول، قیمت و تنظیمات با version check یا optimistic locking محافظت شود؛ فرم قدیمی تغییر جدید دیگری را بی‌خبر بازنویسی نکند. اصلاح موجودی به‌صورت رخداد دفتر انبار و با رعایت رزروهای فعال انجام شود.

کدها و عبارات فنی مانند SKU و callback در جریان عادی ادمین به زبان قابل فهم یا همراه توضیح کوتاه نمایش داده شوند. ادمین برای انتشار محصول نیازمند ترمینال یا SQL نباشد.

۱۳. داده و قواعد مالی

حداقل مدل‌های مورد نیاز: User، Session، VerificationChallenge، Role/Permission، Address، Product، Variant، Media، Collection، InventoryLedger، InventoryReservation، Cart، WishlistItem، Order، OrderItemSnapshot، PaymentAttempt، PaymentEvent، Shipment، ReturnRequest، Refund، Coupon، CouponRedemption، ContentPage، OutboxJob و AuditEvent. اگر نقد فعال است Review و چرخهٔ مدیریت آن نیز مدل شوند.

برای پول یک قرارداد واحد تعریف کن. پیش‌فرض: مبلغ صحیح BIGINT با واحد صریح IRR در سرور/DB، و تومان در UI. تبدیل فقط در utility مرکزی و adapter انجام شود. قیمت تومان ورودی ادمین باید دقیقاً یک بار در ۱۰ ضرب شود. serialization BIGINT، محدودهٔ مجاز و گردکردن تعریف شوند؛ استفادهٔ تصادفی از floating point ممنوع است.

سیاست گردکردن تخفیف/مالیات و حداقل واحد قابل نمایش را مشخص کن تا جمع تومانِ تأییدشده توسط مشتری دقیقاً با ریالِ درگاه برابر باشد. مبلغ نهایی بعد از تأیید کاربر مخفیانه تغییر نکند.

قیمت، تخفیف، مالیات، ارسال و جمع نهایی فقط با دادهٔ معتبر سرور محاسبه شوند. عددهای ارسال‌شده از client مرجع قیمت نیستند. مقدار منفی، overflow، تنوع نامعتبر و کد تخفیف غیرمجاز مهار شوند.

سقف مصرف کوپن برای هر مشتری و کل کمپین با کنترل اتمیک اعمال شود. رزرو، مصرف و آزادسازی سهم تخفیف و اثر لغو/بازپرداخت تعریف شوند. چند تلاش پرداخت یک سفارش چند مصرف کوپن نسازند. استفادهٔ هم‌زمان از آخرین سهم تخفیف نتواند سقف را نقض کند.

نام و حجم کالا، قیمت، تخفیف، ارسال، نشانی و نسخهٔ سیاست مرتبط در سفارش snapshot شوند. رخدادهای مالی سابقهٔ قابل حسابرسی داشته باشند. نرخ مالیات و فیلدهای قانونی فاکتور بر اساس وضعیت واقعی کسب‌وکار تعیین شوند، نه عدد حدسی.

۱۴. انبار، سفارش و هم‌زمانی

افزودن به سبد به معنی رزرو موجودی نباشد. رزرو در شروع فرایند پرداخت و در تراکنش کوتاه انجام شود. موجودی فیزیکی، مقدار رزروشده و مقدار قابل فروش معانی جدا و رابطهٔ روشن داشته باشند.

کاهش/رزرو موجودی با عملیات اتمیک شرطی یا row lock در PostgreSQL و constraint مناسب انجام شود. دو خریدار آخرین واحد نباید هم‌زمان تعهد فروش معتبر بگیرند. ترتیب lock برای چند SKU ثابت و retry برای deadlock/serialization محدود باشد.

رزرو expiry قابل تنظیم داشته باشد و worker آن را idempotent آزاد کند. احتکار رزرو با سقف تعداد/زمان مهار شود. برای هر عملیات انبار یک شناسهٔ یکتا و دلیل قابل حسابرسی وجود داشته باشد.

Order، PaymentAttempt، Reservation، Refund و Shipment state machine مستقل داشته باشند. نمودار انتقال و guardهایشان را مستند کن. یک سفارش ممکن است چند تلاش پرداخت داشته باشد؛ آن‌ها را با چند سفارش اشتباه نگیر.

رویداد سفارش و job لازم در یک تراکنش DB وارد transactional outbox شوند. worker پایدار و قابل retry باشد. شبکه می‌تواند پیام را چند بار تحویل دهد؛ اثر مالی و انبار در DB deduplicate شود. ادعای exactly-once سراسری نکن.

پرداخت موفقِ دیررس بعد از انقضای رزرو باید تأیید و ثبت شود. اگر موجودی باقی است تخصیص امن بده؛ اگر نیست وضعیت استثنا و گردش‌کار تعیین تکلیف/بازپرداخت ایجاد کن. نه پول پرداخت‌شده گم شود و نه موجودی منفی تولید شود.

۱۵. درگاه ایرانی و صحت پرداخت

PaymentProvider با قرارداد typed برای create، verify، inquiry/reconcile و refund-capability تعریف کن. یک adapter محلی آزمایشی قطعی و یک adapter واقعی برای provider منتخب بساز. پیش‌فرض پیشنهادی زرین‌پال است؛ فعال‌سازی واقعی به قرارداد و دسترسی صاحب کسب‌وکار وابسته است.

مستندات جاری provider را دقیق بخوان. نمونهٔ زرین‌پال هنگام تهیهٔ این سند currency=IRR و currency=IRT را پشتیبانی می‌کند. برای مسیر اولیهٔ کم‌ابهام از دفترکل ریالی و ارسال صریح IRR استفاده کن و request/verify را با مستندات و sandbox همان نسخه تطبیق بده. واحد هیچ PSP را حدس نزن.

PaymentAttempt و شناسهٔ idempotency پیش از تماس خارجی ذخیره شوند. اتصال درگاه خارج از تراکنش باز DB انجام شود. merchant، authority، مبلغ و سفارش مرتبط از رکورد سرور خوانده شوند. idempotency key به کاربر/عملیات و fingerprint دادهٔ درخواست وابسته باشد؛ استفادهٔ همان کلید با محتوای متفاوت conflict بدهد و رکورد کاربر دیگری را برنگرداند.

Status=OK در callback مرورگر به‌تنهایی موفقیت پرداخت نیست. نتیجه باید server-to-server با API رسمی verify و قرارداد amount/currency/order بررسی شود. callback امضاشده فقط اگر provider چنین امضایی مستند کرده، اعتبارسنجی شود؛ header یا HMAC خیالی برای زرین‌پال نساز.

callback تکراری، refresh، retry و verify مجدد فقط یک اثر مالی و یک ثبت تعهد موجودی داشته باشند. uniqueness در DB و transition اتمیک لازم است. کدهای ۱۰۰ و ۱۰۱ زرین‌پال طبق مستندات جاری تفسیر و تست شوند؛ ۱۰۱ نباید به اجرای دوبارهٔ عملیات منجر شود.

دو دریافت واقعی با authority/ref متفاوت را با callback تکراری یک دریافت اشتباه نگیر. همهٔ دریافت‌های واقعی با شناسهٔ یکتای تراکنش ثبت شوند؛ هر سفارش فقط یک تعهد موجودی و یک جریان ارسال داشته باشد. پرداخت موفق اضافی به وضعیت قابل پیگیری و گردش‌کار تعیین تکلیف/بازپرداخت برود؛ رکورد آن حذف یا نادیده گرفته نشود.

timeout در create/verify یعنی نتیجه ممکن است نامشخص باشد. فوراً «ناموفق» یا «پرداخت شد» اعلام نکن. reconciliation قابل retry و وضعیت قابل پیگیری بساز. endpoint inquiry را به‌جای verify قرار نده.

پس از بازگشت از درگاه، موفقیت در مرورگر فقط از وضعیت معتبر سفارش در سرور خوانده شود. تأیید پرداخت نباید به باقی‌بودن cookie مرورگر در redirect وابسته باشد؛ نمایش اطلاعات خصوصی سفارش همچنان احراز مجوز خود را لازم دارد.

اطلاعات کارت، CVV2، رمز کارت و OTP بانکی دریافت یا ذخیره نشوند. کاربر برای ورود این اطلاعات به صفحهٔ رسمی PSP هدایت شود. مقصد redirect به allowlist محدود باشد.

Refund را از cancel و reverse جدا مدل کن. قابلیت بازپرداخت کامل/جزئی و محدودیت زمانی/قراردادی را بررسی کن. یک reverse محدود را سیستم عمومی مرجوعی معرفی نکن. اگر API مناسب در دسترس نیست، گردش‌کار دستی کنترل‌شده با وضعیت pending و ثبت مدرک فراهم کن. تا نتیجهٔ معتبر دریافت نشده، refunded نشان نده.

دو refund هم‌زمان نباید از مبلغ واقعاً پرداخت‌شده منهای بازپرداخت‌های قبلی/درحال‌انجام تجاوز کنند. برگشت موجودی کالای مرجوعی به تصمیم بررسی کیفیت و سیاست واقعی وابسته باشد.

۱۶. هویت، سشن و مجوزها

ورود مشتری با OTP کوتاه و قابل فهم باشد. الگوی پیشنهادی اولیه و قابل تنظیم: کد تصادفی حداقل شش‌رقمی، اعتبار دو تا سه دقیقه، فاصلهٔ ارسال مجدد حدود ۶۰ ثانیه و سقف محدود تلاش ناموفق. این‌ها تنظیمات پیشنهادی پروژه‌اند؛ رفتار واقعی با کتابخانه و سرویس انتخابی تطبیق داده شود.

کد باید یک‌بارمصرف و مصرف آن اتمیک باشد. ارسال دوباره، شمارندهٔ خطا یا محدودیت امنیتی را صفر نکند. کد منقضی/مصرف‌شده قبول نشود. ذخیرهٔ OTP کوتاه با روش امن کتابخانه انجام شود؛ کد خام وارد log یا response تولید نشود.

rate limit چندلایه برای شماره، challenge، IP و بودجهٔ کل پیامک تعریف کن. مسدودسازی کور یک IP مشترک نباید بی‌دلیل همهٔ مشتریان شبکهٔ موبایل را قفل کند. افشای وجود حساب مهار و خطاهای پیامک قابل بازیابی باشند.

ادمین MFA اجباری داشته باشد؛ WebAuthn/passkey با user verification ترجیح دارد، و در صورت نیاز password قوی به‌همراه TOTP با کتابخانهٔ معتبر. ورود و بازیابی ادمین با SMS تنها پذیرفته نیست. بازیابی نباید راه دورزدن عامل دوم باشد؛ recovery code امن و کنترل‌شده لازم است.

Session قابل revoke، timeout مشخص، گردش شناسه بعد از ورود/تغییر حساس و خروج از همهٔ دستگاه‌ها فراهم کن. cookie با HttpOnly، Secure و SameSite متناسب با جریان واقعی؛ host-only و در صورت سازگاری __Host- prefix. توکن auth در localStorage یا sessionStorage ذخیره نشود.

سشن ادمین از مشتری جدا باشد. اگر subdomain جدا انتخاب شد، cookie مشترک Domain-wide نساز و CSRF/host/SSO implications را مستند کن. اگر /admin روی همان دامنه است، مجوز و سشن مدیریتی مستقل را در سرور اعمال کن.

هر عملیات حساس در endpoint و لایهٔ دسترسی داده، مجوز و مالکیت شیء را بررسی کند. مخفی‌کردن دکمه، محافظت layout یا middleware کافی نیست. حذف نقش یا تعلیق کاربر باید درخواست بعدی حساس را از مجوز محروم کند.

تغییر شماره، MFA، نقش، صادرات اطلاعات و بازپرداخت حساس نیازمند احراز مجدد متناسب باشند. بازیابی حساب و ادغام سبد/حساب با شمارهٔ تأییدنشده انجام نشود.

۱۷. امنیت برنامه و حریم خصوصی

هدف امنیتی: الزامات قابل اعمال OWASP ASVS Level 2 با نسخهٔ رسمی جاری، threat model و شواهد کنترل. در زمان تهیهٔ سند ASVS 5.0.0 نسخهٔ پایدار اعلام‌شده است؛ در شروع پروژه دوباره بررسی کن. صرف اجرای scan را گواهی یا تضمین امنیت معرفی نکن.

threat model شامل کاربر ناشناس، مشتری مخرب، تصاحب حساب ادمین، دستکاری مبلغ، فروش هم‌زمان، replay پرداخت، سرقت سشن، CSRF، XSS، SQL injection، SSRF، فایل مخرب، افشای PII، سوءاستفادهٔ پیامک و وابستگی آلوده باشد.

اعتبارسنجی سمت سرور، query پارامتری، output encoding، پاک‌سازی محتوای غنی و فهرست مجاز داده‌های قابل ویرایش را اعمال کن. mass assignment و تغییر role/owner توسط client مهار شود.

CSRF را برای mutationهای احرازشده اجرا کن؛ SameSite تنها دفاع نباشد. CORS credentialed با wildcard ممنوع است. callback درگاه قرارداد خاص خود را داشته باشد؛ برای درست‌شدن آن CSRF کل سایت خاموش نشود.

CSP متناسب با route و rendering تدوین کن. nonce تصادفی برای هر پاسخ می‌تواند dynamic rendering لازم کند؛ با فرض کش عمومی تمام HTML در تضاد نباشد. tradeoff امنیت/کش را ثبت و تست کن. برای رفع خطا به‌صورت عمومی unsafe-inline/unsafe-eval فعال نکن. اگر راهکار مورد اتکا آزمایشی است، آن را وابستگی قطعی production معرفی نکن.

حساب، سفارش، سبد، checkout، ادمین، invoice و response شخصی وارد shared cache/CDN نشوند. تست نشت بین دو کاربر لازم است. اطلاعات محرمانه در bundle عمومی یا متغیر NEXT_PUBLIC قرار نگیرند.

حداقل دادهٔ لازم جمع‌آوری شود. کد ملی، تاریخ تولد و اطلاعات کارت پیش‌فرض درخواست نشوند. اطلاعات حساس در log/analytics redact شوند؛ نشانی، متن OTP و tokenها وارد رویدادهای تحلیلی نشوند.

رضایت پیامک تبلیغاتی جدا، اختیاری و از پیش انتخاب‌نشده باشد. پیام تراکنشی و بازاریابی تفکیک شوند. سیاست نگهداری داده و حذف/ناشناس‌سازی با تعهد نگهداری سوابق مالی سازگار و نیازمند تصمیم واقعی کسب‌وکار باشد.

۱۸. رسانه و آپلود

آپلود محصول فقط با مجوز مناسب باشد. پسوند و MIME کافی نیست؛ محتوا decode/re-encode، metadata پاک و اندازهٔ فایل، تعداد پیکسل، زمان پردازش و حجم خروجی محدود شوند.

فقط rasterهای لازم مانند JPEG/PNG/WebP پذیرفته شوند. SVG/HTML فعال و فایل اجرایی دلخواه ادمین پذیرفته نشوند. SVG لوگوی کنترل‌شدهٔ داخل مخزن یک مورد جداست.

نام object تصادفی/تولیدشده باشد؛ مسیر یا نام فایل ورودی مرجع storage path نباشد. اصل خصوصی و مشتق عمومی جدا باشند. تصویر خصوصی و پیوست پشتیبانی در CDN عمومی نرود.

URL خارجی دلخواه برای fetch تصویر مجاز نباشد؛ از SSRF و image proxy abuse جلوگیری کن. remotePatterns و دسترسی object storage حداقلی باشند. پیش‌نمایش تصویر باید خطای پردازش را شفاف نشان بدهد.

۱۹. شبکه، استقرار و پایداری

شبکهٔ عمومی فقط reverse proxy را در معرض قرار دهد؛ HTTPS عمومی، HTTP صرفاً برای redirect/صدور گواهی در صورت نیاز. SSH از مسیر مدیریتی کنترل‌شده باشد. DB و Redis احتمالی پورت عمومی منتشر نکنند.

Firewall پیش‌فرض منع، TLS مناسب، تمدید خودکار گواهی، هدرهای امنیتی و HSTS با دامنهٔ صحیح تنظیم شوند. trusted proxy و forwarded headers به‌دقت محدود شوند. فعال‌بودن UFW به‌تنهایی اثبات امنیت Docker نیست؛ exposure واقعی IPv4/IPv6 از بیرون بررسی شود.

اگر CDN/WAF انتخاب شد، سازگاری مسیر ایران، callback، cache keys و origin access بررسی شود. origin نباید از مسیر عمومی فرعی حفاظت edge را دور بزند. CAPTCHA خارجی پیش‌فرض شرط ضروری خرید نباشد؛ راه مقابله با ربات متناسب با دسترسی واقعی طراحی شود.

کانتینرها non-root، image کم‌حجم و pin‌شده، health/readiness، graceful shutdown، restart و resource limit داشته باشند. migration با کنترل نسخه و بدون تخریب خودکار داده اجرا شود. Docker socket، فایل تنظیمات کامل میزبان و secretهای نامرتبط mount نشوند. هر سرویس فقط secretهای موردنیاز خود را با دسترسی حداقلی از secret manager یا فایل اختصاصی فقط‌خواندنی دریافت کند.

محیط فروش واقعی با نبود secret ضروری، mock provider فعال یا تنظیمات ناامن به‌صورت روشن fail کند. حالت build بهینه را از محیط استقرار جدا کن: NODE_ENV=production می‌تواند برای تست build بهینه استفاده شود، اما DEPLOYMENT_ENV=test|staging|live مرز محیط را مشخص کند. mock تنها در test/staging صریح و دارای کنترل دسترسی، بدون secrets و دادهٔ واقعی مجاز باشد؛ در live حتماً رد شود. .env.example فقط نام و توضیح و مقدار نمونهٔ بی‌خطر داشته باشد. secretهای live در secret store/تنظیمات حفاظت‌شده قرار گیرند.

فونت، آیکن و JS/CSS ضروری self-host شوند. خرید به analytics، CDN عمومی کتابخانه یا AI خارجی وابسته نباشد. حذف وابستگی غیرضروری به معنی امکان تأیید پرداخت یا ارسال SMS بدون provider نیست؛ در اختلال وضعیت قابل بازیابی لازم است.

از دو شبکهٔ موبایل و یک اینترنت ثابت داخل ایران، مسیر فروشگاه، تصاویر، ورود، SMS و پرداخت بررسی شود. اگر این دسترسی در محیط موجود نیست، روش آزمون و شواهد لازم را تحویل بده و نتیجه را اجراشده ننویس.

در استقرار چند App، session، rate limit و invalidation کش مشترک/هماهنگ باشند؛ build یکسان و کلیدهای لازم Server Action طبق مستندات نسخهٔ واقعی هماهنگ شوند. روی هر replica جداگانه build متفاوت نساز.

۲۰. پایش، بکاپ و بازیابی

log ساختاریافته با request/order/payment correlation ID و دادهٔ خصوصی redactشده ایجاد کن. خطا، تأخیر، pool DB، صف worker، verifyهای معطل، refund ناموفق، موجودی ناسازگار، جهش هزینهٔ SMS، فضای دیسک، بکاپ ناموفق و انقضای TLS پایش شوند.

health عمومی اطلاعات اتصال، نسخهٔ حساس یا secrets را نمایش ندهد. دسترسی ابزار پایش محدود باشد. هشدارها صاحب و مسیر رسیدگی مشخص داشته باشند؛ صرفاً نصب ابزار کافی نیست.

بکاپ رمزگذاری‌شدهٔ DB و رسانه با نسخه‌بندی خارج از همان سرور و با دسترسی جدا لازم است. نگهداری پیشنهادی اولیه ۷ روزانه، ۴ هفتگی و ۳ ماهانه است؛ با حجم داده و سیاست کسب‌وکار بازبینی شود.

اهداف پیشنهادی: RPO حداکثر ۱۵ دقیقه برای دادهٔ سفارش با WAL/PITR معتبر و RTO حداکثر ۲ ساعت در تمرین. این‌ها هدف‌اند؛ تا اندازه‌گیری، تعهد اثبات‌شده اعلام نشوند. بکاپ روزانه به‌تنهایی هدف ۱۵دقیقه‌ای را تأمین نمی‌کند.

تمرین restore واقعی در محیط جدا اجرا کن؛ سفارش‌ها، ارجاع رسانه و قابلیت ورود را بررسی کن. پس از بازیابی، پرداخت‌های خارج از recovery point با PSP تطبیق داده شوند تا پرداخت موفق از دست نرود یا سفارش دوباره ارسال نشود.

runbookهای deploy، rollback، restore، اختلال PSP/SMS، پرشدن دیسک و compromise حساب ادمین آماده شوند. برگشت نسخهٔ برنامه را با برگشت امن schema اشتباه نگیر؛ migrationهای سازگار و rollout کنترل‌شده لازم‌اند.

۲۱. SEO، کارایی و تحلیل محصول

صفحات محصول/مجموعه محتوای قابل crawl، عنوان و description واقعی، canonical، sitemap، robots و redirect مناسب برای slug تغییرکرده داشته باشند. ادمین، preview، حساب، checkout و فیلترهای بی‌ارزش بی‌دلیل index نشوند.

دادهٔ ساخت‌یافتهٔ Product/Offer و Breadcrumb مطابق محتوای قابل مشاهده باشد. قیمت schema با واحد اعلام‌شدهٔ استاندارد سازگار باشد؛ مبلغ تومان را با کد IRR برچسب نزن. امتیاز و review ساختگی نساز.

تصاویر responsive و اندازهٔ مشخص، خروجی بهینه، بارگذاری lazy پایین صفحه و اولویت مناسب تصویر اصلی داشته باشند. فونت‌ها محدود و بدون وابستگی render-blocking غیرضروری باشند. JS سمت client فقط در مؤلفهٔ نیازمند تعامل.

هدف تجربهٔ واقعی در صدک ۷۵: LCP حداکثر ۲٫۵ ثانیه، INP حداکثر ۲۰۰ میلی‌ثانیه و CLS حداکثر ۰٫۱. قبل از انتشار تست آزمایشگاهی و پس از انتشار RUM لازم است؛ نمرهٔ Lighthouse به‌تنهایی اثبات تجربهٔ واقعی کاربران نیست.

رویدادهای تحلیلی ساده و بدون PII: product_view، search، add_to_cart، checkout_started، payment_verified و order_completed. درآمد از پرداخت تأییدشده و با dedup و تعریف اثر refund محاسبه شود؛ بارگذاری صفحهٔ تشکر درآمد ایجاد نکند. funnelها بر اساس دادهٔ واقعی باشند.

۲۲. آزمون و معیار پذیرش

ابزارهای پیشنهادی: Vitest برای منطق، آزمون integration با PostgreSQL واقعی آزمایشی، Playwright برای مسیرهای مرورگر، axe برای بخشی از دسترس‌پذیری و k6 برای بار. نسخه‌ها و سازگاری را بررسی کن. آزمون‌ها باید خطر واقعی را بسنجند؛ درصد پوشش ساختگی یا تستی که فقط implementation را تکرار می‌کند کافی نیست.

سناریوهای اجباری:

T01 مشتری بدون ثبت‌نام کاتالوگ را می‌بیند، حجم انتخاب می‌کند و سبد پایدار می‌سازد.
T02 ارقام فارسی/عربی/لاتین و شکل‌های معتبر شمارهٔ ایران هویت تکراری نمی‌سازند.
T03 OTP منقضی، تکراری و مصرف هم‌زمان دوباره پذیرفته نمی‌شود؛ resend سقف تلاش را reset نمی‌کند.
T04 دسترسی مستقیم به API/Server Action ادمین بدون مجوز رد می‌شود.
T05 کاربر A با تغییر شناسه به سفارش، نشانی، invoice یا پیوست B دسترسی پیدا نمی‌کند.
T06 نقش لغوشده و سشن باطل‌شده نمی‌توانند عملیات حساس انجام دهند.
T07 قیمت، تخفیف، هزینهٔ ارسال، مقدار منفی و overflow ارسالی client بی‌اثر یا رد می‌شوند.
T08 دو خریدار آخرین واحد نمی‌توانند هر دو موجودی را تعهد بگیرند.
T09 درخواست تکراری checkout با یک idempotency key نتیجهٔ یکسان دارد.
T10 callback جعلی با Status=OK سفارش را paid نمی‌کند.
T11 callback/verify تکراری، از جمله وضعیت already verified، اثر انبار/ارسال/مالی تکراری ندارد.
T12 timeout درگاه وضعیت نامشخص درست و تطبیق بعدی قابل بازیابی دارد.
T13 پرداخت موفق پس از انقضای رزرو گم نمی‌شود و فروش بیش از موجودی ایجاد نمی‌کند.
T14 authority ناشناس، merchant اشتباه، amount/currency نامنطبق و نگاشت سفارش غلط مهار می‌شوند.
T15 دو درخواست refund هم‌زمان بیش از مبلغ مجاز بازپرداخت نمی‌کنند.
T16 restart شدن worker رخداد ثبت‌شده را از بین نمی‌برد و اثر قبلی را تکرار نمی‌کند.
T17 فایل با MIME جعلی، ابعاد عظیم، SVG فعال یا نام مخرب امن رد می‌شود.
T18 cache/CDN دادهٔ خصوصی یک کاربر را به دیگری نمی‌دهد.
T19 قطع SMS، خطای ارسال و بازگشت از درگاه، اطلاعات ضروری فرم را بی‌دلیل پاک نمی‌کند.
T20 متن طولانی فارسی، متن لاتین، RTL، zoom، keyboard و reduced-motion درست نمایش داده می‌شوند.
T21 ادمین غیرمتخصص می‌تواند بدون SQL محصول پیش‌نویس بسازد، پیش‌نمایش ببیند و منتشر کند.
T22 backup در محیط جدا restore می‌شود و reconciliation پرداخت پس از بازیابی قابل انجام است.
T23 هزینه و مبلغ نمایشی تا ریال ارسالی درگاه و واحد schema محصول دقیقاً تطبیق دارند.
T24 دادهٔ نمونه، رمز پیش‌فرض، mock payment و پنل debug به production راه پیدا نمی‌کنند.
T25 یک مسیر مثبت کامل از ایجاد محصول در ادمین، خرید مهمان، verify موفق، ثبت یک سفارش و اثر انبار، ثبت رهگیری و مشاهدهٔ وضعیت توسط مشتری کار می‌کند.
T26 دو PaymentAttempt موفق با authority/ref متفاوت برای یک سفارش، دو دریافت ثبت‌شده اما فقط یک جریان ارسال ایجاد می‌کنند و دریافت اضافی قابل تعیین تکلیف است.
T27 دو checkout هم‌زمان برای آخرین سهم کوپن، سقف مصرف را نقض نمی‌کنند و retry یک سفارش مصرف جدید نمی‌سازد.
T28 دو ادمین روی نسخه‌های متفاوت محصول، تغییر یکدیگر را بی‌خبر بازنویسی نمی‌کنند.
T29 مشتری فقط برای سفارش واجد شرایط خود درخواست مرجوعی/لغو ثبت می‌کند و وضعیت واقعی رسیدگی و بازپرداخت را می‌بیند.
T30 استفادهٔ idempotency key یکسان با payload متفاوت یا توسط کاربر دیگر، داده یا عملیات اشتباه ایجاد نمی‌کند.

در تست مرورگر، حداقل Chromium، Firefox و WebKit در viewportهای اصلی بررسی شوند. viewport موبایل معادل آزمون دستگاه واقعی نیست؛ ادعای iOS/Android واقعی فقط با شواهد همان محیط.

امنیت و عملکرد را روی build بهینهٔ production در محیط test/staging حفاظت‌شده آزمایش کن؛ به تفاوت NODE_ENV و DEPLOYMENT_ENV در بخش ۱۹ پایبند باش. یافتهٔ بحرانی/بالای تأییدشدهٔ حل‌نشده، خطای مبلغ، نقض مجوز، فروش بیش از موجودی، شکست خرید یا مسیر جعلی موفقیت مانع انتشار است.

۲۳. آزمون ظرفیت برای ۲۰۰ کاربر

نامزد شروع: ۴ vCPU، RAM هشت GiB و ۸۰ تا ۱۰۰ GB NVMe با رسانه/backup بیرونی. این تخصیص ظرفیت تضمین‌شده نیست.

build، CI، generator بار، تست مرورگر و فرایندهای توسعه داخل این بودجهٔ production نیستند و باید در محیط جدا اجرا شوند.

برای بررسی ۲۰۰ کاربر هم‌زمان، نامزد نخست مجموع ۸ vCPU و ۱۶ GiB RAM است؛ یک سرور بزرگ‌تر یا دو App هرکدام ۲ vCPU/۴ GiB و یک DB با ۴ vCPU/۸ GiB. worker سبک باید در بودجهٔ همین منابع جا بگیرد یا جدا حساب شود.

فرض اولیهٔ قابل جایگزینی: ۲۰۰ کاربر، هر ۱۵ ثانیه یک ناوبری، سه درخواست پویا در هر ناوبری، تقریباً ۴۰ درخواست پویا در ثانیه. درخواست تصاویر و prefetch و اثر cache جدا اندازه‌گیری شوند.

تست ۲۰۰ VU با think time واقع‌بینانه، افزایش تدریجی، حداقل ۲۰ دقیقه بار پایدار و کاهش بار اجرا کن. نسبت اولیهٔ سفرها ۸۰٪ مرور، ۱۰٪ جست‌وجو، ۸٪ سبد و ۲٪ checkout است؛ با دادهٔ واقعی اصلاح شود. آزمون مستقل RPS برای یافتن نقطهٔ اشباع لازم است؛ ۲۰۰ VU را با ۲۰۰ RPS یکی ندان.

Warm/cold cache، رقابت آخرین موجودی و اختلال PSP/SMS بررسی شوند. generator بار روی سرور جدا اجرا شود. زیر بار از adapter کنترل‌شده استفاده کن؛ درگاه یا پیامک واقعی یا sandbox شخص ثالث بدون مجوز load test نشود.

هدف پیشنهادی درخواست‌های داخلی: p95 خواندن زیر ۵۰۰ms، ساخت سفارش زیر ۱۰۰۰ms بدون زمان PSP، خطای غیرمنتظره زیر ۰٫۵٪ و صفر نقض قواعد مالی/موجودی. کدهای خطای تجاری مورد انتظار مثل ۴۰۹ موجودی جدا شمرده شوند. صف DB/worker پایدار و حاشیهٔ ظرفیت کافی باشد.

گزارش باید سخت‌افزار، vCPU اشتراکی/اختصاصی، commit، dataset، config، cache hit، p50/p95/p99، throughput، مصرف CPU/RAM، pool/locks DB، صف و محدودیت‌ها را ثبت کند. عدد آزمون‌نشده به‌عنوان ظرفیت نهایی نوشته نشود.

۲۴. پیش‌نیازها، دستورات و CI/CD

در مخزن آماده کن:
- runtime و package manager pin‌شده و lockfile.
- .env.example با توضیح متغیرهای لازم و تفکیک development/test/production.
- Dockerfile چندمرحله‌ای و Compose توسعه/استقرار، شبکه و volumeهای لازم.
- schema، migration، seed کوچک و واضحاً آزمایشی.
- دستور راه‌اندازی یک‌مرحله‌ای مستند پس از تنظیم env.
- دستورهای واقعی install/dev/build/start/lint/typecheck/test/test:e2e/test:load/db:migrate.
- CI شامل lint، typecheck، تست‌های ضروری، build، اسکن dependency/secret/container و ثبت artifact.
- مسیر کنترل‌شدهٔ release، migration، health check، rollback و نگهداری نسخه.
- ثبت license/provenance وابستگی و دارایی، SBOM در صورت سازگاری ابزار منتخب.

package و browser binary و imageهای لازم را از منابع معتبر و نسخهٔ pin‌شده تأمین کن. cache/mirror کنترل‌شده برای اختلال شبکه مستند شود. بدون cache کامل وعدهٔ build آفلاین نده.

کلید خصوصی، merchant secret، OTP، دیتابیس مشتری و dump تولید وارد Git یا artifact عمومی نشوند. دسترسی CI به production حداقلی و از pull request ناشناس جدا باشد.

پیش‌نیازهای واقعی راه‌اندازی را در یک جدول با ستون‌های «مورد، مالک، وضعیت، روش تأمین و روش آزمون» ثبت کن: دامنه/DNS/TLS، میزبان، ذخیره‌سازی و backup، قرارداد PSP و sandbox، سرویس SMS و الگوی خدماتی، اطلاعات ارسال، حساب مالک/MFA، تصاویر و اطلاعات کالا، هویت قانونی/سیاست فروش و مجوز دارایی.

نماد اعتماد، مجوز، سیاست مرجوعی، مالیات، ضمانت اصالت و محدودیت حمل بر اساس وضعیت واقعی فروشنده بررسی شوند. تصویر نماد جعلی، مهلت قانونی حدسی یا نشان غیرقابل استعلام منتشر نکن.

۲۵. مراحل تحویل

فاز صفر: ارزیابی مخزن/محیط، قرارداد معماری، agentها، Skillها، پیش‌نیازها و برنامهٔ اجرایی.
فاز یک: design system، اتودهای لوگو، جریان‌ها، صفحهٔ محصول و قالب ادمین با دادهٔ نمونهٔ روشن.
فاز دو: یک مسیر عمودی کامل و متصل؛ ایجاد محصول در ادمین تا مشاهده، سبد، سفارش و پرداخت آزمایشی.
فاز سه: تمام قابلیت‌های اصلی کاتالوگ، کاربران، انبار، ارسال، مرجوعی، محتوا و اعلان‌ها.
فاز چهار: آزمون مستقل، اصلاح، امنیت، RTL، عملکرد، بکاپ و runbook.
فاز پنج: اتصال سرویس‌های واقعیِ دارای دسترسی، آزمون قرارداد، staging و آماده‌سازی انتشار قابل بازبینی.

پس از هر فاز، نتیجهٔ واقعی، فایل‌ها، شواهد و قدم بعد را کوتاه گزارش کن و کار مجاز بعدی را ادامه بده. اطلاعات ناقص کسب‌وکار را از نقص پیاده‌سازی تفکیک کن. با تمام‌شدن زمینهٔ گفتگو، STATUS و برنامه باید ادامهٔ کار را ممکن کنند.

۲۶. تعریف اتمام و تحویل نهایی

خروجی نهایی شامل:
- کد کامل و قابل اجرا با migration و تنظیمات.
- Skillهای محلی واقعی و AGENTS.md هماهنگ با پروژه.
- مستندات معماری، دسترسی، مالی، پرداخت و پیش‌نیازها.
- لوگوی SVG و design tokens، دارایی‌های مجاز و متن فارسی بازبینی‌شده.
- راهنمای تصویری یا دارای تصاویر واقعی محیط برای مشتری و ادمین.
- راهنمای نصب، deploy، rollback، backup/restore و مدیریت secrets.
- نتایج واقعی آزمون‌ها و گزارش امنیت/ظرفیت با commit و تاریخ.
- فهرست محدودیت‌ها و blockerهای واقعی پیش از انتشار.

فایل‌های حداقل مستندات: README.md، docs/ARCHITECTURE.md، docs/FA_COPY_GUIDE.md، docs/ADMIN_GUIDE_FA.md، docs/SECURITY.md، docs/ACCESS_MATRIX.md، docs/PAYMENTS.md، docs/DATA_MODEL.md، docs/DEPLOYMENT.md، docs/BACKUP_RESTORE.md، docs/CAPACITY.md، docs/TEST_REPORT.md، docs/RELEASE_CHECKLIST.md و docs/STATUS.md. آن‌ها باید متن و دستور واقعی داشته باشند و برای پرکردن فهرست ساخته نشوند.

معیار تحویل: تمام جریان‌های اصلی قابل استفاده و متصل به داده باشند؛ الزامات مهم آزمون شده باشند؛ خطاهای تأییدشدهٔ مانع انتشار رفع شده باشند؛ وضعیت اتصال واقعی PSP/SMS، تست‌های اجرا نشده و نیازهای صاحب کسب‌وکار صریح باشد.

عبارت‌هایی مثل «بدون باگ»، «امنیت کامل»، «تمام تست‌ها پاس شدند»، «ASVS compliant» یا «آمادهٔ production» را بدون شواهد به کار نبر. کیفیت را با پیاده‌سازی، آزمون مستقل، رفع خطا و گزارش دقیق نشان بده.
