# رابط فروشگاه و مدیریت Morphiume

تاریخ: ۲۰۲۶-۱۰-۱۲. مالک این مسیرها `frontend_engineer` است؛ API، auth، تنظیمات و منطق دامنه متعلق به هماهنگ‌کننده و عامل بک‌اند هستند. این گزارش میان پیاده‌سازی و آزمون اجراشده تفاوت می‌گذارد.

## مسیرهای پیاده‌سازی‌شده

| مسیر | رفتار متصل |
|---|---|
| `/`, `/products`, `/products/[slug یا id]` | محتوای محصول از `getCommerce()` روی سرور؛ فیلترهای URL؛ حجم، قیمت و موجودی؛ شناسه به نامک فعلی با ۳۰۸ هدایت می‌شود؛ ۴۰۴ واقعی برای محصول منتشرنشده/ناموجود |
| `/cart`, `/checkout` | سبد cookie سرور، تغییر تعداد/حذف/کوپن، نشانی محفوظ در این تب، OTP، quote سرور، تأیید مبلغ، idempotency، هدایت به پرداخت |
| `/test/payments/[authority]`, `/orders/[id]` | نتیجهٔ آزمایشی با مالکیت و verify سرور؛ وضعیت مستقل مالی/ارسال؛ پیگیری؛ retry فقط پرداخت قطعاً ناموفق؛ درخواست لغو/مرجوعی واجد شرایط |
| `/account`, `/favorites` | ورود تلفنی native Better Auth؛ نام اختیاری؛ اعلان‌های حساب با خوانده‌شدن؛ نشانی‌های ذخیره‌شده؛ علاقه‌مندی مهمان محلی و انتقال صریح به حساب؛ خروج و پایان ورود دستگاه‌های دیگر |
| `/guide`, `/collections`, `/collections/[slug]`, `/pages/[slug]` | راهنمای قابل توضیح از متادیتای واقعی؛ مجموعه‌ها؛ محتوای تأییدشدهٔ سرور؛ نبود اطلاعات با حالت خالی، بدون ساختن ادعای تجاری |
| `/admin/login`, `/admin` | auth جداگانه، راه‌اندازی واقعی TOTP و کدهای بازیابی، بررسی grant سرور، ناوبری بر اساس permissions واقعی |
| `/admin/products`, `/admin/products/new`, `/admin/products/[id]` | پیش‌نویس، ویرایش با expectedVersion، گالری تا ده تصویر پردازش‌شده با توضیح/حجم/ترتیب، پیش‌نمایش خصوصی، انتشار، کپی پیش‌نویس با SKU/نامک تازه، بایگانی، هشدار تغییر ذخیره‌نشده |
| `/admin/inventory`, `/admin/coupons` | دفتر موجودی و دلیل اصلاح، operationKey قابل تکرار؛ درصد صحیح basis point؛ حداقل خرید؛ تاریخ شمسی و ساعت تهران برای اعتبار کوپن |
| `/admin/orders`, `/admin/orders/[id]` | ثبت رهگیری، یادداشت داخلی، CSV سرور، خلاصهٔ قابل چاپ، رسیدگی به مرجوعی، دریافت‌ها و بازپرداخت با تأیید دوبارهٔ TOTP و تأیید مبلغ/سفارش |
| `/admin/content`, `/admin/settings`, `/admin/collections` | محتوای متن امن، انتشار صریح، version check، اطلاعات تماس قابل ویرایش، مقدار نامعلوم خالی، نسخهٔ سیاست آزمایشی فقط خواندنی |
| `/admin/customers`, `/admin/reports`, `/admin/audit` | مشتریان/مدیران، ایجاد حساب و تغییر نقش با MFA تازه، گزارش مالی واقعی و تاریخچهٔ فارسی؛ بدون ادعای ارسال ایمیل دعوت |
| `/admin/bulk` | حداکثر ۱۰۰ تنوع، قیمت/موجودی با مجوز، دلیل روشن، preview سرور، مقادیر قبل/بعد و commit اتمیک با operationKey و expectedProductVersion |
| `/admin/import` | CSV با نقل‌قول و UTF-8، پیش‌نمایش، dry run سرور، خطای ردیفی، تأیید صریح و ساخت اتمیک همهٔ پیش‌نویس‌ها |

`/api/admin/export?kind=products|orders` و endpoint یادداشت توسط هماهنگ‌کننده ارائه می‌شوند؛ رابط از خروجی با مجوز و فرمول‌گریزی سمت سرور استفاده می‌کند.

## قراردادهای مهم

- API عادی `{data}` یا `{error:{code,message,fields?}}` است. آرایهٔ خطای Zod در wrapper به نام فیلد فرم تبدیل می‌شود. auth از native Better Auth استفاده می‌کند و envelope تجارت روی آن اعمال نمی‌شود.
- هیچ token احراز هویت در local/session storage ذخیره نمی‌شود. تنها نشانی پیش‌نویس و شناسهٔ تکرارپذیر خرید این تب در sessionStorage هستند؛ خروج آن‌ها را پاک می‌کند. علاقه‌مندی مهمان در localStorage مجاز است.
- IRR مقدار صحیح string است. نمایش تومان از `src/lib/money.ts` می‌آید؛ قیمت خرید از client پذیرفته نمی‌شود. مبلغ بازپرداخت تنها برای درخواست مدیریتی به IRR تبدیل می‌شود و سرور مانده و مجوز را کنترل می‌کند.
- `financialVisible:false` در DTO مدیریت، تمام نمایش و چاپ مبلغ را مهار می‌کند. حذف فیلدهای حساس از JSON مسئولیت سرور است. اجازهٔ دیدن مبلغ، اجازهٔ بازپرداخت نیست.
- OTP موجود ۱۸۰ ثانیه و resend ۶۰ ثانیه است. زمان‌بندی UI مطابق تنظیم واقعی auth است؛ سرور مرجع مصرف/انقضا/سقف تلاش است.
- schema Product/Offer همان اطلاعات عمومی و مبلغ IRR را دارد؛ JSON-LD با escape و nonce پاسخ ساخته می‌شود. canonical/sitemap فقط از `PUBLIC_SITE_URL` واقعی ساخته می‌شوند. staging و صفحات خصوصی noindex هستند.
- کل HTML فارسی و RTL است. بومی‌سازی وضعیت‌ها از `src/lib/fa-copy`، فونت self-host و SVG اصلی استفاده شده است. قیمت/موجودی/خدمات/نظر ساختگی نداریم.

## شواهد اجراشده

- TypeScript کل مخزن و ESLint `src/app src/components` چند بار پس از تغییرهای واقعی اجرا شدند. آخرین نوبت پیش از تحویل با کد صفر بود؛ پس از افزوده‌شدن فایل‌های دیگر دوباره هماهنگ‌کننده بررسی می‌کند.
- build اولیهٔ رابط با Next 16.4 موفق شد. هشدار import CSS آن نوبت با import نسبی توکن‌ها پیش از Tailwind در منبع اصلاح شد. build کامل و نهایی پس از API/SSR و تغییرهای تازه، مسئولیت هماهنگ‌کننده است؛ نتیجهٔ آن اینجا جعل نمی‌شود.
- بررسی واقعی in-app browser روی dev جداگانه: سربرگ ۳۲۰ اصلاح شد و عرض document برابر client width شد؛ حساب در ۳۷۵، ۷۶۸ و ۱۲۸۰ نیز overflow نداشت. خطای شمارهٔ کوتاه، focus روی `phone-errors` و `aria-describedby` و `aria-invalid` بررسی شدند. مقدار ورودی در ابزار privacy-redacted بود؛ حفظ مقدار واقعی توسط مشاهدهٔ CUA ادعا نمی‌شود.
- QA مستقل مسیر T25 را در Chromium و WebKit تا پرداخت تأییدشده، یک اثر موجودی و ثبت/نمایش رهگیری اجرا کرد. overflow سفارش ۳۲۰ را یافت؛ اصلاح min-inline-size و track `minmax(0,1fr)` طبق bbox واقعی انجام شد. تأیید اصلاح به بازآزمون build نهایی وابسته است؛ گزارش قطعی در `docs/qa` نگهداری می‌شود.
- بررسی واقعی تابع تاریخ: `۱۴۰۵/۰۷/۲۰ ۱۸:۰۰` ↔ `2026-10-12T14:30:00.000Z`، روز کبیسهٔ معتبر ۱۴۰۳، رد روز نامعتبر ۱۴۰۴، و تبدیل صحیح `۰٫۲۹`/`.29` به ۲۹ basis point. بازبینی مستقل عامل فارسی نیز موارد ارقام عربی، ساعت نامعتبر و شکاف DST تاریخی را بررسی کرده است.
- capture تمام‌صفحهٔ CUA برای RTL بریده بود و فایل‌های نامعتبر پس از بازکردن و بررسی حذف شدند؛ مشاهدهٔ تصویر viewport و اندازه‌گیری DOM جدا انجام شد. تصاویر مسیر واقعی QA در `docs/qa/screenshots` هستند. تصویر crop‌شده به عنوان شواهد رابط تحویل داده نمی‌شود.

## کارهای باقی‌مانده یا متکی به ورودی

رابط ویرایش گروهی قیمت/موجودی بر قرارداد سرور پیاده شده است؛ آزمون مستقل API/DB در گزارش بک‌اند ثبت می‌شود و آزمون مرورگر واقعی پنل هنوز لازم است. استان/شهر پیشنهادهای snapshot منبع‌دار و امکان نوشتن آزاد دارند؛ این داده ادعای پوشش حامل یا به‌روز بودن رسمی تقسیمات نیست. گالری چندتصویری و تصاویر مختص حجم اکنون در قرارداد و رابط وجود دارند؛ آزمون مستقل API/DB آن‌ها در گزارش بک‌اند و آزمون مسیر مرورگر پس از build هماهنگ‌کننده ثبت می‌شود. فهرست‌های اصلی و انتخابگرهای راهنما/مجموعه/گروهی/موجودی صفحه‌بندی سرور دارند. API آرایه‌ای قدیمی هنوز محدود است؛ علاقه‌مندی مهمان اکنون resolver محدود به شناسه‌ها دارد و شمارندهٔ نمای کلی از totalItems استفاده می‌کند. آزمون مستقل همهٔ ابزارهای مدیریتی، ۲۰۰٪ zoom، دستگاه واقعی و Firefox باید طبق گزارش QA تکمیل/ثبت شوند.

اطلاعات قانونی/دامنه، سیاست‌های کسب‌وکار، SLA/هزینهٔ ارسال واقعی، عکس و مشخصات واقعی محصول و اتصال PSP/SMS ورودی صاحب کسب‌وکار هستند. متن و نماد جعلی برای آن‌ها تولید نشده است. نسخهٔ آزمایشی به معنی امکان پرداخت واقعی یا مجوز انتشار عمومی نیست.

## منابع مشاهده‌شده

- [Better Auth phone number](https://better-auth.com/docs/plugins/phone-number) و [TOTP](https://better-auth.com/docs/plugins/2fa)، مشاهده در ۲۰۲۶-۱۰-۱۲؛ با declaration/source نسخهٔ نصب‌شده تطبیق داده شدند. Context7 CLI در PATH اولیه موجود نبود، بنابراین از مستند رسمی و کد نصب‌شده استفاده شد.
- [Next CSP](https://nextjs.org/docs/app/guides/content-security-policy) و [Metadata](https://nextjs.org/docs/app/api-reference/functions/generate-metadata)، مشاهده در ۲۰۲۶-۱۰-۱۲؛ dynamic rendering و nonce/metadata.
- راهنمای `ui-ux-pro-max`، جست‌وجوی مشخص `error summary validation`: summary قابل focus، خطاهای متصل و حفظ مقدار. طراحی بصری از design system تصویب‌شدهٔ پروژه گرفته شد.

## گالری محصول؛ checkpoint رابط

`ProductDto.images` شامل `{url,alt,variantSku?}` است. فرم، حداکثر ده تصویر پردازش‌شده را با توضیح، ارتباط اختیاری به SKU، جابه‌جایی با دکمه‌های قابل استفاده با صفحه‌کلید و حذف از گالری مدیریت می‌کند. بارگذاری واقعی همان endpoint رسانهٔ مدیریت است. هنگام بارگذاری، ذخیره و انتشار متوقف می‌شوند و سایر فیلدهای فرم قابل ویرایش و محفوظ می‌مانند. پاک‌کردن گالری یا اطلاعات ضروری محصول منتشرشده نیازمند بایگانی است؛ بایگانی با نسخهٔ سرور اجرا می‌شود و ویرایش‌های ذخیره‌نشده را در فرم نگه می‌دارد.

صفحهٔ محصول، تصویرهای عمومی و تصویرهای همان SKU انتخاب‌شده را نمایش می‌دهد؛ تصویر متصل به حجم دیگر، نمایندهٔ حجم انتخاب‌شده نیست. انتخاب تصویر با دکمهٔ دارای `aria-pressed`، توضیح و اعلام شمارهٔ تصویر انجام می‌شود. پاسخ تک‌تصویری قدیمی همچنان قابل نمایش است. تصویرهای کنترل‌شده با `CspImage`، ابعاد ثابت و CSS خارجی رندر می‌شوند؛ attribute سبک درون‌خطی به تصویرها اضافه نمی‌شود. JSON-LD اکنون URLهای واقعی گالری را دارد.

TypeScript کل مخزن و ESLint `src/components src/app/products` با کد صفر اجرا شدند. فرمان `node docs/frontend/gallery-component-check.mjs` نیز در Chrome نصب‌شده با کد صفر قبول شد: component واقعی ویرایشگر و گالری، حفظ توضیح در بارگذاری معلق، alt/SKU/ترتیب در payload ذخیره، منع پاک‌کردن محصول منتشرشده، حفظ فرم پس از بایگانی، سقف ده تصویر، انتخاب صفحه‌کلیدی و جداسازی تصاویر حجم، سازگاری تک‌تصویر، containment در ۳۲۰ پیکسل و نبود `[style]` را بررسی کرد. API و مسیریاب Next در این آزمون fixture کنترل‌شده هستند؛ این نتیجه قبولی API/DB، CSP پاسخ واقعی یا E2E گالری محسوب نمی‌شود. آزمون مستقل build یکپارچه مسئولیت QA است.

در checkpoint گالری، صفحه‌بندی هنوز افزوده نشده بود. دامنهٔ فعلی، محصول را تا ۳۰۰ و سفارش را تا ۱۰۰ رکورد محدود می‌کند و فیلتر سمت رابط روی همین بخش محدود عمل می‌کند. قرارداد تصویب‌شدهٔ بعدی، `{items,page,pageSize,totalItems,totalPages}` و endpointهای مستقل `/api/catalog/page`، `/api/admin/products/page`، `/api/orders/page` و `/api/admin/orders/page` است؛ فیلتر/مرتب‌سازی باید سمت سرور و facets کاتالوگ از کل محصولات منتشرشده بیایند. پیشنهاد استان/شهر از snapshot منبع‌دار در lib هماهنگ‌کننده پس از checkpoint یکپارچه می‌شود؛ ورودی متنی برای نشانی قدیمی یا شهر تازه حفظ خواهد شد.

## checkpoint صفحه‌بندی، نشانی و ارسال

فهرست عمومی SSR و فهرست مدیریت محصولات، سفارش مشتری/مدیریت، راهنمای خانواده/نت/حجم، انتخاب محصول مجموعه و انتخاب تنوع گروهی/موجودی اکنون از page DTO سرور استفاده می‌کنند. فیلتر و مرتب‌سازی روی همهٔ رکوردهای مجاز اجرا می‌شوند؛ تصویر و قیمت کاشی کاتالوگ به همان حجم و موجودی انتخاب‌شده مربوط‌اند. URL فیلترها در صفحه‌های اصلی حفظ می‌شود و تغییر فیلتر صفحه را به ابتدا برمی‌گرداند. شناسه‌ها، قیمت‌های واردشده و نسخه‌های انتخاب مجموعه/گروهی در تغییر صفحه حفظ می‌شوند. تعارض گروهی، فهرست تازه را بدون پاک‌کردن draft دریافت می‌کند؛ کنارگذاشتن یک تغییر برای دریافت نسخهٔ تازه، صریح است. قیمت پاسخ گروهی فقط با permission و `financialVisible` نمایش داده می‌شود.

facets از کل محصولات منتشرشده می‌آیند و سرور سقف پیشنهادی و `facetsTruncated` را اعلام می‌کند؛ پیام محدودبودن فهرست فیلترها و گزینهٔ انتخاب‌شدهٔ خارج از آن حفظ شده‌اند. صفحهٔ خارج از محدوده، پیام روشن و راه بازگشت دارد. sitemap از `listSitemapProducts` کم‌حجم با زمان واقعی و سقف صریح backend استفاده می‌کند؛ شکست سقف به معنی خروجی کامل نیست. نمای خانه تنها چهار محصول منتشرشده درخواست می‌کند و ادعای پرفروش بودن ندارد.

Checkout و دفتر نشانی از input/datalist دارای `useId` یکتا و دادهٔ ثبت‌شده در `docs/LOCATIONS_SOURCE.json` استفاده می‌کنند. تغییر استان، پیشنهاد شهر را عوض می‌کند؛ شهر تازه و نشانی قدیمی قابل نوشتن‌اند و اطلاعات گیرندهٔ هدیه جدا باقی می‌ماند. استان/شهر، اعتبارسنجی پوشش حمل یا کدپستی نیستند.

`/admin/shipping` با مجوز `refunds.write`، هزینه و حداقل خرید ارسال رایگان را از API می‌گیرد. هزینه، حداقل خرید، دلیل و expectedVersion به صورت snapshot در پنجرهٔ تأیید نمایش داده می‌شوند؛ TOTP native تازه و تأیید نهایی لازم است. تومان با ابزار صحیح مشترک به مقدار canonical تبدیل می‌شود و API نیز آن را بررسی می‌کند. کمک فرم روشن می‌کند حداقل خرید بر مبلغ کالاها پس از تخفیف، بدون ارسال اعمال می‌شود و صفر همهٔ سفارش‌ها را شامل می‌شود. پیش‌فرض آزمایشی `configured:false` آشکار است؛ SLA یا هزینهٔ تجاری تأییدنشده ساخته نشده است.

TypeScript کل مخزن و ESLint `src/components src/app` با کد صفر اجرا شدند. هر دو فرمان `node docs/frontend/gallery-component-check.mjs` و `node docs/frontend/paging-locations-component-check.mjs` در Chrome نصب‌شده قبول شدند. آزمون دوم componentهای واقعی را با API، router و پاسخ TOTP کنترل‌شده می‌آزماید: صفحه‌بندی fixture بیش از سقف قبلی، حفظ URL/بازگشت فیلتر به صفحهٔ اول، قیمت/تصویر حجم درست، city پیشنهادی و آزاد، گیرندهٔ هدیه و ارقام فارسی/صفر اول کدپستی، مبلغ snapshot و gate تأیید ارسال، تعارض نسخه و پنهان‌بودن نقش فاقد مجوز، note راهنما، انتخاب‌های چندصفحه‌ای مجموعه/گروهی/موجودی، facet خارج از لیست و صفحهٔ خارج از محدوده. این‌ها قبولی احراز هویت واقعی، مجوز DB، محاسبهٔ ارسال سرور یا E2E production نیستند؛ بازآزمایی مستقل build یکپارچه لازم است.

در اسکن پیشین، علاقه‌مندی مهمان و شمارندهٔ نمای کلی دو مصرف قدیمی بودند؛ هر دو در checkpoint نهایی اصلاح شدند. `wishlist.tsx` از `GET /api/catalog/resolve?ids=...` و `ProductResolutionDto` مشترک استفاده می‌کند. شناسه‌های localStorage اعتبارسنجی، یکدست و یکتا می‌شوند؛ سقف ۱۰۰ انتخاب صریح است. شناسهٔ غیرقابل نمایش تا حذف صریح کاربر باقی می‌ماند و شکست resolver، حالت خالی جعلی نمی‌سازد. حذف آخرین انتخاب به طول guest وابسته است و دادهٔ resolver قبلی را نمایش نمی‌دهد. هنگام تغییر کاربر، component با کلید actor تازه mount می‌شود و دادهٔ قبلی در انتظار lookup جدید قابل نمایش نیست. `admin-overview.tsx` با pageSize1، totalItems منتشرشده/پیش‌نویس/سفارش را می‌گیرد و طول items را معیار شمارش نمی‌کند. آخرین `rg` در صفحه‌ها/componentها فقط literal POST ساخت محصول را یافت؛ GET آرایهٔ legacy محصول/سفارش در رابط باقی نماند. این اسکن به معنی حذف endpoint قدیمی API نیست. گردش موجودی در رابط، صریحاً تا ۲۰۰ رویداد اخیر است؛ تاریخچهٔ بی‌حد ادعا نمی‌شود. آزمون مرورگر واقعی پنل تازه، zoom و device/network واقعی همچنان مطابق گزارش QA باید ثبت شود.

آزمون component نهایی همچنین resolver محصول فراتر از سقف قدیمی، پاک‌سازی UUID تکراری/نامعتبر، حفظ انتخاب غیرقابل نمایش، شکست و retry بدون empty جعلی، حذف آخرین انتخاب، totalItems در نمای کلی و تعویض native-session کنترل‌شدهٔ حساب الف به ب با lookup معلق را بررسی کرد و قبول شد. این تعویض، proof احراز هویت یا مجوز backend واقعی نیست. TypeScript سراسری و ESLint src/components src/app پس از دو اصلاح نهایی با کد صفر بودند؛ source برای build هماهنگ‌کننده ثابت شد.

## checkpoint بازهٔ قیمت، metadata و دسترسی صفحه‌کلید

کاتالوگ عمومی، دو حد اختیاری قیمت به تومان با `minPriceToman` و `maxPriceToman` در URL و SSR دارد. تبدیل و مقایسه با ابزار صحیح مشترک و BigInt انجام می‌شوند؛ ارقام فارسی/عربی/لاتین و جداکنندهٔ هزارگان پذیرفته‌اند. دامنهٔ معتبر صفر تا سقف مبلغ برنامه است و قیمت اعشاری، منفی، بیش‌ازحد یا بازهٔ وارونه خطای متصل به فیلد و summary قابل focus دارد. مقدار نامعتبر پاک یا به عدد معتبر کوتاه نمی‌شود. جست‌وجوی معتبر صفحه را به ابتدا برمی‌گرداند، ولی draft نامعتبر URL انتخاب قبلی را تغییر نمی‌دهد. پاسخ 400 سرور نیز مقدارهای URL را در ورودی نگه می‌دارد؛ SSR خطای VALIDATION دامنه را داخل کاتالوگ نشان می‌دهد. دادهٔ SSR به query مربوط خودش وابسته است و در گذار به query تازه، محصول قبلی نتیجهٔ انتخاب تازه نشان داده نمی‌شود.

قیمت و تصویر کاشی از همان تنوعی انتخاب می‌شوند که هم‌زمان با حجم، موجودی و دو حد قیمت سازگار باشد. مرتب‌سازی قیمت، مانند قرارداد سرور، کمترین قیمت تنوع‌های سازگار هر محصول را نشان می‌دهد. ترکیب مستقل «یک حجم ارزان + حجم دیگر گران» یا «تنوع ارزان موجود + تنوع گران ناموجود» نتیجهٔ سازگار جعلی نمی‌سازد.

مطابق راهنمای metadata و caching نسخهٔ نصب‌شدهٔ Next، sitemap و robots به‌طور پیش‌فرض cache می‌شوند. هر دو اکنون `dynamic = "force-dynamic"` دارند و `getConfig()` را داخل handler صدا می‌زنند؛ خروجی به تنظیمات اعتبارسنجی‌شدهٔ زمان درخواست وابسته است، نه محیط config-free ساخت image. test/staging همچنان sitemap خالی و robots disallow دارند. فعال‌سازی واقعی live هنوز به gate سرور و ورودی‌های تأییدشدهٔ کسب‌وکار وابسته است؛ این تغییر آن را فعال نمی‌کند. تأیید manifest و رفتار metadata در build نهایی مسئولیت هماهنگ‌کننده/QA است.

همهٔ چهارده wrapper جدول فعلی، region با نام مطابق caption و `tabIndex=0` دارند؛ outline قابل مشاهده درون محدودهٔ scroll باقی می‌ماند. آزمون component واقعی جزئیات سفارش در ۳۲۰ پیکسل وجود scroll محلی، focus صفحه‌کلید، containment سند و قبولی قاعدهٔ `scrollable-region-focusable` axe را بررسی کرد. در کنار دریافت CSV محصولات/سفارش‌های مدیریت، مسیر native تأیید دوباره و توضیح شرط پنج‌دقیقه‌ای نمایش داده می‌شود؛ محدودیت واقعی دانلود در API هماهنگ‌کننده است.

فرم ورود مدیریت پیش از hydration با snapshot سرور `false` در fieldset غیرفعال قرار دارد و پیام آماده‌سازی دارد؛ snapshot مشتری `true` فقط پس از hydration کنترل‌ها را فعال می‌کند. handler هنگام آماده‌نبودن/مشغول‌بودن اجرا نمی‌شود. `node docs/frontend/login-hydration-component-check.mjs` با SSR واقعی AdminLogin و فایل JS عمداً معلق قبول شد: ورودی/دکمه پیش از hydration غیرفعال بودند، پس از hydration فعال شدند و مقدار کنترل‌شده با یک درخواست native sign-in حفظ شد؛ خطای hydration/page ثبت نشد. router و پاسخ auth fixture هستند و این proof احراز هویت واقعی یا اثبات علت شکست قبلی WebKit نیست.

`node docs/frontend/paging-locations-component-check.mjs` نیز با موارد تازه قبول شد: بازهٔ قیمت، ارقام فارسی/عربی، صفحهٔ اول و URL صفحهٔ بعد، تصویر/قیمت همان تنوع، trap حجم+قیمت و موجودی+قیمت، حد برابر و صفر، draft نامعتبر/وارونه، پاسخ‌های 400 با حفظ ورودی، کنترل تأیید CSV و axe محدود جدول سفارش. این آزمون از API کنترل‌شده استفاده می‌کند؛ صحت SQL قیمت یا E2E build جدید را ادعا نمی‌کند.

## checkpoint برچسب‌های دقیق و breadcrumb ساختاریافته

جست‌وجوی سفارش مدیریت اکنون فقط «شمارهٔ سفارش» را وعده می‌دهد؛ API جست‌وجوی نام گیرنده ندارد. گزارش، شمار وضعیت فعلی پرداخت‌شده را از دریافت وجه جدا می‌کند: سفارش با بازپرداخت جزئی/کامل در `paidOrders` نیست؛ دریافت‌های تأییدشدهٔ تمام دوره، شامل دریافت اضافه‌اند؛ خالص برابر دریافت منهای بازپرداخت انجام‌شده است و درآمد فروش ادعا نمی‌شود. موجودی و رزرو با عنوان واحدهای ثبت‌شدهٔ فعلی نشان داده می‌شوند؛ metric یا endpoint تازه‌ای ساخته نشد.

صفحهٔ محصول، BreadcrumbList با همان دو نام/مسیر breadcrumb قابل مشاهده دارد: عطرها و نام محصول. URLها با تنظیمات اعتبارسنجی‌شدهٔ درخواست، اول `PUBLIC_SITE_URL` و در نبود آن `APP_BASE_URL`، مطلق می‌شوند. درخواست nonce به هر دو script محصول و breadcrumb داده می‌شود. `components/structured-data.tsx` تنها serializer این دو JSON-LD است؛ نویسه‌های `<`, `>`, `&` و جداکننده‌های خط JSON-safe می‌شوند و مقدار اصلی پس از JSON.parse باقی می‌ماند. الگوی پیشین `replace(/</g, "\\u003c")` از نظر escaping صحیح بود؛ اصلاح حاضر آن را متمرکز و آزموده کرد و bug اثبات‌نشده‌ای به آن نسبت نمی‌دهد.

`node docs/frontend/structured-data-component-check.mjs` در Chrome نصب‌شده با کد صفر قبول شد. component واقعی صفحه/serializer با runtime و header کنترل‌شده بررسی شدند: round-trip مقدار `<` و متن escape لفظی، نبود بسته‌شدن script یا script تزریقی، nonce هر دو JSON-LD، برابری نام/ترتیب breadcrumb با مسیر قابل مشاهده و اولویت/جایگزین URL پایه. این آزمون، validator خارجی Schema/Google یا رفتار SEO live محسوب نمی‌شود.

اعلان محیط آزمایشی اکنون در section نام‌دار «وضعیت محیط فروشگاه» است؛ header موجود تنها banner landmark می‌ماند. آزمون component واقعی SiteShell، region نام‌دار، یک banner و قواعد axe مربوط به region/landmark را قبول کرد. harness صفحه‌بندی نیز با برچسب دقیق جست‌وجوی شماره، تعریف‌های مبلغ/شمار گزارش و fixture قدیمی خرید/صفحه‌بندی/نشانی/ارسال/قیمت/جدول دوباره قبول شد. APIها همچنان fixture هستند؛ بازبینی مستقل build جدید با coordinator/QA است.
TypeScript سراسری و ESLint src/components src/app پس از اصلاح نهایی tuple و serializer هر دو با کد صفر بودند؛ آزمون JSON-LD نیز پس از همین اصلاح دوباره قبول شد. source برای build هماهنگ‌کننده ثابت شد؛ build/restart یا آزمون DB در این checkpoint اجرا نشد.
