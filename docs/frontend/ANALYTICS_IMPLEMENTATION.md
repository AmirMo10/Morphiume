## Files and future integration contract

| New source | Export and responsibility |
|---|---|
| `src/components/analytics-client.ts` | `captureAnalytics(input: AnalyticsObservation): void`, `createAnalyticsEventId(): string \| null`; independent anonymous, bounded delivery |
| `src/components/admin-analytics.tsx` | `AdminAnalytics()`; future `/admin/analytics` aggregate-only panel |

`AnalyticsObservation` is either product_view/add_to_cart plus public product UUID, or search plus boolean hasQuery and one of zero/1_10/11_100/over_100. It optionally accepts a caller-retained event UUID for one logical action; otherwise it generates a cryptographic v4 UUID through the existing operationId helper. The identifier is ephemeral memory, not authentication or a persisted browser identifier. Missing entropy drops the observation. Canonical scalar reconstruction rejects extra keys, arrays, nested objects, non-v4 UUIDs, accessors, symbols and nonenumerable metadata. Neither a raw nor hashed search query is accepted. No URL, referrer, customer/session/cart/order ID, contact, address, cookie, token, fingerprint or money is accepted or added.

Callers emit only after an actual successful canonical product render, completed results interaction or successful cart mutation. The helper is void and is never awaited for browsing/purchase. Production event completeness or accepted collector counts are not claimed. An explicit event ID may be kept in memory for the same logical render/action; collector deduplication is a separate backend responsibility. The helper itself never retries and makes no exactly-once guarantee.

| Coordinator route used by source; actual runtime acceptance pending | Contract |
|---|---|
| `GET /api/analytics/config` | `{data:{captureEnabled:boolean}}`; one bounded attempt cached in memory for the document |
| `POST /api/analytics/events` | Approved BrowserAnalyticsInput JSON, at most1024bytes; neutral202 `{data:{ok:true}}` |
| `GET /api/admin/analytics/period?from&to` | AnalyticsPeriodDto; ISO calendar dates in payload, inclusive Tehran range,1–366days/default30 |

Config and event requests use credentials:omit, referrerPolicy:no-referrer, cache:no-store, CORS mode and redirect:error. Both fixed API paths are absolute URLs pinned to window.location.origin, never a caller-provided host or document base URL. The later independently proved Origin correction replaced same-origin mode; the installed Windows WebKit Cookie-omission failure remains explicit in `ANALYTICS_TRANSPORT_DIAGNOSIS.md`. No authorization header or authentication bypass is added. An abort timer of1000ms starts before each capture's config wait; the config attempt also has a1000ms abort. A capture whose deadline expired while waiting for config cannot POST later. Disabled, malformed, failed, timed-out or Basic401 config resolves false for this document; a new document may evaluate configuration again. POST failure/401/timeout is dropped without retry, caller error, auth mutation or cart failure. Response acknowledgements are not purchase evidence. Browser scheduling can delay execution of an abort callback; the configured timeout is a request budget, not a measured availability/SLA promise.

There is no telemetry storage, storage-based queue, persistent event ID or external analytics library. Response data is used only for the boolean config result. Report/private fetches remain credentialed through the existing private API helper and are distinct from anonymous capture requests.

## Panel behavior and definitions

The panel first requires an ordinary valid native admin session, matching the server-provided admin identity, mfaVerified and explicit analytics.read in the server permission list. It never infers data permission from a role name. The coordinator added the typed Permission/server map; frontend added the owner/product_manager/finance navigation fallback map. The panel still requires the explicit server list through a string-set membership guard and makes no unsafe Permission cast. No new five-minute financial rule is added for aggregate GET. Native pending/refetch/error/missing or different owner unmounts report state; API401/403 also unmounts it and directs to admin login. Removed permission prevents a report request. Aborted/old responses cannot repopulate the unmounted private screen.

The future screen has heading «آمار فعالیت فروشگاه», refresh «دریافت دوبارهٔ آمار», range «بازهٔ آمار فعالیت», inputs «از تاریخ» / «تا پایان تاریخ», apply «نمایش آمار», default «بازهٔ پیش‌فرض ۳۰ روز» and error retry «تلاش دوبارهٔ آمار». The calendar helpers accept Persian/Arabic/Latin digits, validate Jalali leap days/range bounds and translate only API parameters to ISO. URL dates remain Jalali. Invalid local draft retains the currently applied report; a new loading/error query never displays the prior period's cards. Dates remain editable on400. Displayed period and snapshot time use Jalali/Tehran, with bidi isolation.

Three separate named sections display11 scalar count cards using integer BigInt formatting, never Number conversion or monetary formatting:

- «مشاهده‌های بی‌نام مرورگر؛ آمار تقریبی»: product views, searches, browser add-to-cart observations and zero-result searches. These are advisory, can be missing or forged, and are neither unique people nor verified purchases. Loss is explicitly unmeasured. Disabled capture does not erase previously retained counts. Zero recorded observations do not prove no visitors/activity.
- «فعالیت‌های ثبت‌شدهٔ سفارش در بازه»: distinct started orders, verified receipts, orders with primary receipt and orders with delivered evidence in the selected period. Receipt counts include primary/extra/inventory_exception; a later refund does not remove the original receipt. These are period activity across potentially different order populations, not income or a visitor conversion funnel.
- «سرانجام سفارش‌های آغازشده در بازه»: only the cohort with recorded order creation in the period; primary receipt and delivered evidence are evaluated asOf the same report snapshot, including events after the period ended. The basis is explicitly started orders, separate from anonymous browser observations and people. No rate/percentage is invented, including zero denominators.

Browser coverage displays the actual30-day retention window, retained-from, first/last observed timestamps, partial-retention warning, product-dimension truncation and cleanup timestamp/pending flag. Missing timestamps stay explicitly unknown; no historical date is invented. Partial coverage can reflect capture start, retention boundaries or an unfinished period. Cleanup-pending means expired collector data remains; the UI does not promise a scheduled completion or offer retry/delete controls. Count cards contain no product/customer drilldown, raw event fields, private references, payloads or amounts. Production privacy/activation decisions remain owner inputs; technical retention display is not a fabricated legal policy.
