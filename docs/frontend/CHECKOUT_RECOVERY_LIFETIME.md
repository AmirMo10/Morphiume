# Controlled recovery lifetime correction

Context: published checkpoint5cf694c had a Linux Chromium generic-conflict recovery case with no observed POST after reload/click;56 other cases passed. Original trace/screenshot was unavailable, so its exact cause is not established here. The coordinator authorized controlled diagnosis and correction only after source review. No actual application/native server, PostgreSQL, worker, build/restart or credentials were used by frontend.

The actual published CheckoutContent keyed its entire child by privacy generation and continuityCartId. A valid owner could restore its pending record and enable «بررسی نتیجهٔ ثبت سفارش» while cart initialization still had null continuity. Null→cart ID then unmounted the child and aborted its lifetime signal. Pending recovery intentionally does not require a cart, so waiting for cart.ready would weaken missing/replaced-cookie replay rather than fix the lifetime.

`checkout-recovery-timing-check.mjs --baseline` pins the exact published checkout source5cf694c5ed97272851ad32685fed3abd5634f005 inside the fixture. It renders the real Checkout/Commerce and installed native customer client with fully intercepted synthetic HTTP. Native A is verified, a bounded original pending record is saved through the real helper, and current cart initialization is delayed. Both engines reproduce two controls: a pre-dispatch transport gap loses the mounted button/signal and sends zero HTTP POST; a held response has one HTTP POST but loses the response/navigation when the cart key changes. The original key/payload remains pending. Those four baseline controls are accepted reproductions, not a claim that the exact CI timing matched the fixture's deliberate dispatch gap.

The correction changes only checkout.tsx in the cart flow. An owner/generation-scoped controller owns pending/known recovery, submission, busy/error state and its lifetime signal. It survives null→ID/current cart/claim initialization. The address/quote form remains a separate cart-keyed child under the same privacy generation, so normal cart changes still unmount it, abort quote work and reset address/quote/consent/operation state. Starting checkout saves/transfers the immutable record into the stable controller before the form unmounts. The recovery button still requires a validated matching native owner and never waits for current cart readiness. There is no timer, automatic replay, quota/auth/config/schema or API mutation in this correction.

Owner/privacy changes and unmount still abort recovery. PRICE_CHANGED/OUT_OF_STOCK/CART_CHANGED clear only the proven precommit record and return to the cart-scoped fresh form/review; generic CONFLICT/VALIDATION remains the original pending record. The submitted key/body is never rebuilt from the newly initialized cart. Known results keep only minimal IDs/status, clear address draft, refresh the current cart best-effort and navigate to the owned result; refresh failure cannot replace the known order with an unknown one. Recovery/precommit errors remain visible and keyboard-focusable. Pending/known headings and retry/order links retain their accessible labels.

The corrected harness passes ten controls across Chrome/WebKit: one exact original POST after continuity settlement during the pre-dispatch gap; one held response survives settlement and produces its known result; generic conflict preserves the record and an explicit retry uses the same key/body; owner A→B aborts the old response/navigation and clears the prior recovery; normal cart replacement aborts its pending quote, clears the old cart address, removes the old payment control and issues no checkout POST. The known stored record has no input/address. Optional unit:undefined from the address whitelist is compared by its actual serialized JSON transport shape; no field/payload assertion is dropped. All pageerror assertions remain zero.

Affected actual component checks also pass: cart privacy both engines with storage failure, gift first claim, CART_CHANGED/new consent, generic conflict, immutable recovery/new selections and320px tagged axe; native-cart timing17 including actual library signal/gift/claim→quote; seven-consumer SSR; global TypeScript and scoped ESLint. These synthetic controls do not prove a real receipt, SQL stock effect, native OTP/MFA login, deployed recovery or a fix of the original CI artifact's exact cause. Coordinator rebuild and independent affected native acceptance are required before publishing this correction.

Final-run qualification: the initial broad cart-privacy run passed on the extracted controller before the error-focus refinement. A final repeat on the frozen source passed the native-client timing17 suite, but the broader mocked-session fixture stopped at its retained zero-pageerror assertion in WebKit with access-control warnings for synthetic order/cart fetches. That fixture navigates away from the result document before waiting for its order data; this is a source-review hypothesis, not a proven attribution of those warnings. No error/assertion is suppressed, no repeat is relabeled as passed, and no order/cart/session source is changed to hide it. The dedicated final-source recovery10, normal quote-reset, event integration13, panel7, SSR/static checks remain accepted; the final broad mocked-session repeat is explicitly unaccepted pending independent native acceptance or further authorized transport diagnosis.
