# Cart lifecycle: observed behavior and proposed consumption

2026-10-12. Source inspection only while current application/runtime is frozen for QA. No source, schema, test, PostgreSQL, native-auth, worker or credential changes/calls were made. This is a proposed policy and acceptance contract, not implemented behavior or a new test result. Relevant specification: guest/account section10, cart section11, idempotency section15, private-state section17, T01/T09/T12/T25/T30; repository commerce skill/invariants apply.

## Observed current behavior

| Step | Actual source behavior |
|---|---|
| Guest cart | `service.ts:createCart` stores a random bearer digest; API `cartFor/cartResponse` stores id.token in HttpOnly, SameSite=Lax, HTTPS-Secure cookie with30-day maxAge. No stock reservation occurs. |
| Cart reads/writes | cartAccess permits an unowned cart only with its digest-matching token, or an owned cart only for its current authenticated owner. getCart does not claim/merge. Writes lock the cart and check expectedVersion. API POST is additive, PUT is absolute quantity, DELETE is zero/removal. |
| Native OTP | PhoneVerification verifies through maintained customerAuth and calls onVerified. Checkout refreshes/quotes; an account login reloads. No explicit domain cart claim/account-cart merge runs at OTP success. The guest cart remains bearer-accessible until checkout ownership is assigned. |
| Quote | Uses verified actor, server prices/eligibility/settings. Empty cart is invalid. Quote does not create an order or consume stock/cart. |
| Durable checkout | createCheckout locks actor/idempotency/cart, validates version/accepted quote, snapshots order items/money/address/policy/coupon and reserves stock/quota, persists attempt/outbox, then sets cart.user_id and rotates its digest. **It does not delete cart_item, clear cart.coupon_code, increment cart.version or mark consumed.** |
| Payment | initialize/verify/reconcile use durable attempt/order evidence after commit, independent of cart. retryPayment operates on owned original order, original amount and reservation/receipt state; created/pending/unknown/succeeded attempts block a new attempt. No payment path consumes/restores cart items. |
| Logout/account switch | AccountContent.signOut clears the current tab's two checkout sessionStorage keys and reloads. It does not clear cart cookie or address drafts in other tabs. Once owned, old cart is denied to anonymous/another owner; cartFor then creates a new guest cart and a cart response replaces the cookie. CommerceProvider refreshes on mount/manual calls, without an explicit identity-change invalidation. |

Source paths: `src/server/commerce/service.ts` cartAccess/getCart/setCartItem/setCartCoupon/createCheckout/retryPayment; `src/app/api/[...segments]/route.ts` cartFor/cartResponse/cart and checkout routes; `src/components/{phone-verification,checkout,commerce-client,account}.tsx`; `db/migrations/0001_initial.sql` cart/cart_item/order_item schema. Order snapshots are durable; cart has no address field. Browser drafts separately retain address and serialized checkout payload/key under unscoped per-tab storage keys.

QA's second-purchase fixture was corrected from additive POST to PUT quantity1. That is correct API use and is **not by itself an application defect**. Retaining purchased contents is the separate lifecycle policy decision identified above; source findings are not a reproduced account-isolation exploit.

## Proposed policy

1. **Consume only after a new durable order is created, inside its transaction.** After snapshots/reservations/coupon redemption/attempt/idempotency/outbox are established, DELETE that locked cart's items, clear coupon_code and increment version/updated_at; retain its owned cart ID and existing digest rotation. Commit all or none. On validation, stock, coupon, maintenance or DB rollback, contents/coupon/version/ownership remain unchanged. Provider network runs afterward. Consumption means selections moved to the order, not payment success or physical fulfillment.
2. **Stored exact checkout replay resolves before touching cart.** Same verified actor/operation/key and normalized original payload returns the preserved order/attempt/accepted amount with current attempt state; no second clearing/version increment/reservation/job. Changed payload conflicts. A replay after new selections were added must not clear those selections. Foreign account/key/cart access never returns previous-owner data. Keep CheckoutDto unchanged; refresh current cart separately instead of mixing a mutable current cart into the saved payment result.
3. **Recover payment through the original order.** Unknown create/verify or lost HTTP response keeps its pending operation/key and owned order. Retry the original payload/key to learn whether creation committed, or use owned order list/status; never rebuild an order merely because cart is empty. Known eligible failure uses retryPayment after unresolved-attempt checks, retaining original order snapshots/amount/policy. Expired reservation/coupon reallocation remains atomic. Failed, cancelled, refunded or returned orders never automatically repopulate cart; an explicit future reorder would require current eligibility, prices and new consent. During maintenance, saved replay/pre-pause attempts remain usable; new attempt/order creation remains gated.
4. **Define browser-cart ownership at verified login.** Add an explicit verified-session claim operation for the current browser's guest cart, before loading account-private address/history or requesting a quote. Lock and validate native current actor plus cart/version/token, assign owner, revoke guest bearer and increment version. Same-owner claim replay is effect-free; another owner receives uniform denial. An unverified number never claims/merges. The current browser cart is the working cart; preserve its items/coupon and revalidate coupon eligibility under the verified actor in quote. Do not implicitly discover/merge arbitrary old account carts, especially legacy carts still containing previously ordered items. Cross-device synchronized carts would be a separate active-cart pointer/merge design, not claimed here. This continuity/claim rule is the explicit guest→account behavior for this slice.
5. **Keep account transitions private.** On logout or verified A→B identity change, clear address/quote/consent/pending operation and in-memory cart/private data before loading B; fetch a fresh authorized cart and use the native session as authority. Never convert an A-owned cart back into an anonymous cart or disclose its contents via the old bearer. Do not delete durable orders/idempotency when clearing browser drafts. Current-cookie replacement should be server controlled; owned cart access remains session/owner based even with a stale cookie token.

The minimal consumption change needs no new table: existing cart version, items, coupon and owner fields suffice. The optional early claim also uses existing fields. Any future global account-cart registry/lifecycle schema needs separate approval and a read-only legacy audit; do not infer which retained historical cart should merge or automatically rewrite originals. Already created legacy orders/carts are not silently consumed/backfilled by deployment. The behavior starts with newly created orders; owners can explicitly edit retained legacy selections.

## Coordinator/frontend integration requirements

- Checkout ingress must preserve replay without first requiring a nonempty current cart or creating a replacement via cartFor. Parse native actor/body/key, pass cookie proof for new operations, and let domain idempotency resolve first. Current checkout calls cartFor before domain replay and may create an unused replacement cart if its cookie is inaccessible; do not make that preflight a new empty-cart/ownership gate on saved replay. GETcart may replace inaccessible cookies; checkout replay should not fabricate unrelated carts/cookies.
- Proposed `claimCart(actor,cartId,guestToken,expectedVersion):Promise<CartDto>` / POST `/api/cart/claim` are explicit future contracts. Root owns native actor/CSRF/body/cookie handling; frontend calls it only after genuine OTP/session success, then refreshes cart/quote. No custom auth/session crypto or mock login is introduced.
- Pass client expectedVersion on future cart PUT/DELETE/coupon writes, optionally POST as a bounded precondition. Current root handler derives a fresh server version, so a stale UI absolute PUT can re-add purchased quantities after consumption. A stale destructive/absolute operation should409+refresh, not silently operate on a new lifecycle version. Additive POST remains additive; an automatic retry must not reuse a previously computed absolute quantity.
- Replace unscoped browser draft storage with a bounded envelope tagged to cart and verified actor identity. A guest draft may continue through the **same current cart's first verified claim**; preserve recipient data entered in that flow, including recipient phone differing from purchaser. After A→B/logout, stale/mismatched drafts must be ignored/removed. Client tags are not authorization proof. No auth tokens are stored. Cross-tab invalidation must clear other tabs' in-memory/private drafts and revalidate native session on focus/resume; sessionStorage clearing in one tab alone is insufficient.
- After a known checkout response, clear completed address/consent draft and refresh cart/header before redirect where practical; retain only the owner-scoped recovery identifier/state needed to handle a lost response. On reload an empty cart plus unresolved checkout must show recovery/owned-order actions, not discard its key or invite another order. Do not regenerate the key while outcome is unknown. Privacy/logout clearing never overrides server ownership or deletes the saved order.
- All cart/checkout/account/order/draft recovery responses stay private/no-store. Clear old account data on401/403. Server remains authoritative for price/coupon/stock/phone ownership; header counts and browser storage never grant access.

## Meaningful acceptance contract for the next authorized implementation

| Case | Required result |
|---|---|
| New order | Immutable quantities/coupon/amounts preserved in order/redemption; current cart empty, coupon null, version increases once; reservation/attempt/outbox correct. |
| Any precommit failure | Cart contents/coupon/version/owner and financial rows unchanged, including pause/stock/quota/version/settings errors. |
| Lost response / exact replay | Original payload/key finds one saved order/attempt despite empty/rotated/edited cart; no second effects; changed payload409; foreign actor cannot recover it. |
| Two same-key submits | One consumption/order/attempt/reservation set. |
| Two distinct keys / same version | First consumes; second conflicts on advanced version or empty cart and leaves no orphan idempotency/order/reservation/job. |
| Cart edit versus checkout | If edit wins lock, stale checkout fails and requires new quote; if checkout wins, stale absolute edit fails and cannot re-add old purchased quantity. New explicit additive click after refresh adds only its requested delta. |
| Payment unknown/failed/late/extra | Cart remains consumed; original order/attempt recovery is used; unknown blocks new attempt; known retry uses old amount; inventory/receipts/coupon invariants and durable cancellation guard remain. |
| Claim / account isolation | Verified guest contents continue for A; old guest bearer cannot read/write after claim; B with same cookie/key cannot view A's cart/order/address. No claim for unverified/disabled/session-expired actor. Concurrent A/B claims produce one owner. |
| Cross-tab logout/switch | A's address/serialized payload/consent/cart UI clears in every active/resumed tab; B starts with B/guest authorized state; legitimate first guest→A claim preserves that guest draft only. |
| Repeat purchase | After consumption, POST add1 yields1; PUT set1 stays1; cookie/account refresh does not resurrect old coupon or selections. Existing POST-additive semantics are unchanged. |
| Migration/history boundary | No wholesale cleanup/backfill of retained legacy carts, paid snapshots, receipts, unknown attempts or shared queue. |

Backend owns domain consumption/claim and scoped PG concurrency/rollback/history tests; root owns routes/cookies/session/replay ingress; frontend owns recovery UX/versioned writes/draft invalidation; QA owns independent native/browser two-account/two-tab/lost-response acceptance. Run only canonical generated-schema tests in a coordinator-quiescent window with public fingerprints preserved. Public DDL is unnecessary for this minimal policy; any expanded schema requires explicit GO. No tests or runtime acceptance were executed for this plan.
