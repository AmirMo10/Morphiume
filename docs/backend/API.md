# Domain API contracts

Contracts are implemented in `src/contracts/commerce.ts`. Root owns HTTP routing, CSRF, input parsing, private-response no-store and conversion from the maintained auth library to an Actor. Callers never construct Actor from client body fields. The domain rereads active session, verified customer phone or admin MFA grant, and current roles.

Factory `createCommerce({pool,payments,deploymentEnv,appBaseUrl,merchantKey?,reservationMinutes?,shippingFeeIrr?,freeShippingThresholdIrr?,policyVersion?,readShippingPolicy?})` lives in `src/server/commerce/service.ts`. Money JSON is `{amountIrr: decimalString, currency: "IRR"}`. Frontend uses the central تومان formatter. Checkout accepts cart/version, inline recipient/address, shippingMethodId, accepted quote fingerprint and policy version, plus a separately supplied idempotency key. It accepts no price/discount/shipping/tax/total values from the client. A configured free-shipping threshold applies inclusively to subtotal minus the exact rounded discount; an omitted threshold preserves the baseline fee.

| Flow | Domain calls / authorization |
|---|---|
| Public catalog | listProducts(filter), getProduct(slugOrId); only published products; private draft preview requires admin catalog permission |
| Product admin | listAdminProducts/createProduct/updateProduct/publishProduct/archiveProduct; expectedVersion on existing edits |
| Bulk administration | bulkEdit(actor,{operations:[{variantId,expectedProductVersion,priceToman?,inventoryDelta?}],reason,operationKey,dryRun}); maximum 100 unique variants, price and inventory permissions checked independently; preview has no write effects |
| Cart | createCart returns a server-only guestToken plus DTO; getCart/setCartItem/setCartCoupon receive cookie secret; quantities 0–20 and version checks |
| Customer checkout | quoteCheckout(actor,guestToken,cartId); createCheckout(actor,guestToken,input,key); retryPayment(actor,orderId,key) blocks unresolved previous attempts |
| Provider callback | verifyPayment(authority) independent of browser cookie; authority maps to persisted provider/merchant/attempt; order detail still needs authorization |
| Customer status | getOrder(actor,idOrNumber), listOrders; address/shipment/timeline visible only to owner or granted admin |
| Shipment/inventory | recordShipment with carrier/tracking/status; listInventory/getInventoryLedger/adjustInventory with operationKey and reason |
| Returns/refunds | requestReturn owned and state guarded; decideReturn with explicit review/restock; finance listReceipts/requestRefund/completeManualRefund |
| Account | saveAddress/listAddresses/deleteAddress, setWishlist/listWishlist under verified customer ownership |
| Catalog/content | listCoupons/saveCoupon, listCollections/saveCollection, listContent/saveContent, importProducts rows with dryRun and all-or-nothing draft commit |
| Worker | createJobs({pool,commerce,notify?}).tick returns expired/processed counts; heartbeat only after successful DB tick |

Ownership on a claimed cart overrides the original guest token and checkout rotates its digest. After logout the route creates a new guest cart when the previous one is unavailable. Guest cart IDs, order IDs, order numbers and authority values never reveal private order data themselves.

Business errors use CommerceError: VALIDATION 400, UNAUTHENTICATED 401, FORBIDDEN 403, NOT_FOUND 404, and conflict/state/stock/price issues 409. Unknown payment results remain visible for follow-up rather than claiming a completed sale. Return/refund/collection/import methods exist at domain level; HTTP/UI completion is reported by the coordinator separately.

BulkEditDto returns `{dryRun,changes:[{variantId,sku,productName,currentPrice,nextPrice,currentStock,nextStock}],operationId?}`. Existing committed keys are scoped to actor and canonical payload and return their stored result even after versions advance. Changed payload with a committed key conflicts. Rows lock in product UUID, variant UUID, balance UUID order; every requested product version is checked before mutation. All prices/movements, product version increments, inventory ledger, operation result and audit commit together. Inventory output includes `product_version` for warehouse previews without catalog permission.

Committed bulk operations additionally require an MFA-enabled account and a factor proof from the last five minutes inside the domain transaction. Session, grant and current field permissions are checked at the idempotency/replay boundary and after stock locks; authorization rows are held in share mode through the effect. The recency comparison uses PostgreSQL clock_timestamp(), because now() is fixed at transaction start and cannot detect proof aging during a lock wait. The proof is checked again after all authorization share locks return, since a locking SELECT can evaluate its predicate before waiting. Preview keeps standard unexpired-grant behavior. A saved result stays immutable; committed replay still requires current permission, enabled factor and fresh proof, and resumes returning the original result after proof renewal.

Shipment accepts preparing → shipped → delivered, preserving exact status/carrier/tracking replay without extra writes. Delivered → shipped, preparing → delivered and any change from cancelled are rejected. Refund request/completion use the same enabled-factor, current-permission and post-lock wall-clock proof checks as committed bulk, even for replay. Refund operation keys bind the requesting actor and payload; another actor using the key conflicts. Successful manual completion accepts exact evidence replay and rejects differing evidence with CONFLICT. These domain checks supplement the native HTTP guard; controlled database grant fixtures do not prove native factor issuance.

Controlled notifications use `notifyOrderEvent(pool,deploymentEnv,type,payload,dedupeKey)` in `src/server/jobs/notifications.ts` as the worker's notify callback. Supported order/payment/shipment events create one generic Persian test message for the persisted order user; payload recipient fields never select a recipient and no address, phone or amount is copied into the text. Unknown types or malformed/missing orders are ignored. Live invocation fails closed. This is an in-app test/staging inbox; no email/SMS dispatch or backfill of previously completed events is claimed. Root owns inbox HTTP read/mark-read authorization and account UI.

Product galleries use optional input `images:[{url,alt,variantSku?:string|null}]`, maximum ten images. DTO `images` is always an ordered array; `imageUrl` remains the first generic image or first image overall for compatibility. Variant SKU must name an active variant in the submitted product. Alt text is required and bounded to 240 characters. An absent `images` field keeps the legacy single-image update behavior: `imageUrl` becomes one generic image with product-name alt; explicit `images:[]` removes the gallery on a draft/archived product. Removing required images/description/concentration/family from a published product is rejected until it is withdrawn. Publication requires a ready gallery.

Image URLs are exact registered `/media/<lowercase UUID>.webp` references to ready WebP metadata. New attachments require uploader ownership for product managers; current owners may reuse the single-store ready library. Authorized editors may retain/reorder already-approved product images. The exact `/assets/sample-perfume.svg` fixture is allowed only in test/staging. Arbitrary asset prefixes, external URLs, traversal, query strings, missing or unready media are rejected. Public/admin/wishlist product lists load galleries in one batch query; collections batch per collection. Gallery metadata tests do not claim byte-upload or browser image rendering acceptance.

Pagination exports `PageDto<T>={items,page,pageSize,totalItems,totalPages}`, `ProductPageInput`, `AdminProductPageInput`, `OrdersPageInput` and `CatalogPageDto`. `listProductsPage(input={})` returns the catalog page and global facets; `listAdminProductsPage(actor,input={})` returns a product page under current `catalog.write`; `listOrdersPage(actor,input={})` returns an owned customer page or granted admin page under `orders.read`. Default page/size is 1/24, size is bounded to 1–100 and page to 1–1,000,000. An out-of-range page returns empty items and the accurate count. Invalid bounds fail rather than silently clamp. Existing capped array methods remain available for compatibility.

Product paging filters `search`, `family`, `concentration`, exact stored `note`, `volumeMl`, `available` and optional `minPriceToman`/`maxPriceToman`; admin paging also filters draft/published/archived `status`. Each supplied price bound is a string converted exactly once through the central money utility to integer IRR. Bounds are inclusive whole تومان from zero to the application cap of 100,000,000 تومان; Persian/Arabic digits and existing grouping separators are accepted. Negative, fractional, malformed, overflow and reversed ranges fail validation; a provided blank bound is invalid and an omitted bound is unconstrained. Note membership matches any top/heart/base note as an exact JSON string, independent of substring search. Search is normalized, bounded to 120 characters and treats SQL wildcard characters literally. Requested volume, available stock and price range must match the same active variant. Sorting is `name`, `price_asc` or `price_desc`: price order uses the minimum integer price of the same matching active variants, then name/id; name order uses name/id. DTO variants still contain all active variants for customer selection, so the display variant must match the requested filters. Facets contain up to 100 sorted distinct families, concentrations, notes and active-variant volumes from the entire published catalog, independent of the current filter/page. Top-level `facetLimit:100` and `facetsTruncated:boolean` report the cap; at most one extra value per dimension is queried to detect it. Exact filters continue to work for values outside the visible facets. Order search matches only order number, never recipient/address or order ID; status/paymentStatus use the declared enums. Count and items share the same authorization scope, filters and repeatable-read read-only transaction. Orders sort by createdAt descending with ID descending to break ties.

Nonempty catalog pages use five SELECT queries (count, bounded product rows, variants, gallery, global facets). Admin product pages use four plus three fresh authorization queries. Order pages use seven plus one customer/three admin authorization queries, loading items, shipment, events, returns and refunds in batches. BEGIN, SET LOCAL and COMMIT add three statements. Empty pages skip child hydration. Hydration query counts do not grow with page size. `listExportProducts(actor,maximum=10000)` and `listExportOrders(actor,maximum=10000)` use current admin permissions and one consistent snapshot; the ceiling must be 1–10,000, and a count exceeding it produces an explicit CONFLICT without a partial result. Exports have the same four/seven hydration SELECT budgets plus admin authorization. Product grouping is linear in loaded children.

`listSitemapProducts(maximum=10000)` uses only count and bounded metadata SELECTs in one snapshot. It returns `SitemapProductDto[]` with id/slug/updatedAt for published products having an active variant, regardless of stock. Drafts, archives and products with only inactive variants are excluded. Its validated ceiling also rejects over-limit counts explicitly; it loads no images, prices or private order information.

`resolvePublishedProducts(ids:string[])` returns `ProductResolutionDto={products:ProductDto[],unavailableIds:string[]}` for guest favorites independently of catalog pages. UUIDs are trimmed, lowercased and deduplicated in first-input order. The domain accepts at most 100 distinct IDs and bounds raw duplicate parsing to 1,000 entries. Unknown, draft, archived and inactive-only products all appear uniformly in unavailableIds, with no status disclosure. Returned products retain requested order and use one read-only snapshot plus a fixed product/variant/gallery batch, three SELECTs for a nonempty resolved set; an empty input returns empty arrays. No per-ID queries occur.

`listVariantsPage(actor,input:VariantPageInput={})` requires fresh catalog.write or inventory.write and returns `PageDto<VariantDto>`. Inputs are the common page/pageSize bounds and literal normalized SKU/name search. Rows include id, sku, productName, productStatus, active, volumeMl, productVersion and available. Only catalog permission projects/returns price; only inventory permission projects/returns onHand/reserved. Historical inactive/archived SKUs remain visible with explicit flags for legitimate stock corrections. Count and rows use the same snapshot and filter; fixed query budget is two selection queries plus three authorization queries. No gallery hydration or financial fields are queried for inventory-only staff. Name search normalizes Persian/Arabic digits, letters and whitespace in SQL; description and notes are not searched by this method.

The optional shipping reader has the exact interface `(queryable:CommerceQueryable)=>Promise<CommerceShippingPolicy>`, where `CommerceQueryable=Pick<PoolClient,'query'>` and the policy is `{shippingFeeIrr:bigint,freeShippingThresholdIrr?:bigint,policyVersion:string}`. The domain validates nonnegative whole-toman IRR amounts within the money cap and a nonempty version of at most 128 characters. Every fresh quote and new checkout invokes the reader with its existing short ordinary transaction client. The application reader takes shared transaction advisory lock 818002 and SELECT FOR SHARE; the settings writer takes the exclusive advisory lock before write, which also protects an absent/default row. No network call occurs inside a quote transaction.

Quote fingerprints include policy version, source fee/threshold and resolved shipping. Changed settings require fresh consent even when payable shipping coincidentally stays the same. New orders persist the accepted quote's policy and amounts; old orders/payment attempts and matching idempotency replays remain unchanged. Replay is resolved before invoking the current reader. Omitting the reader retains the original static option behavior. Settings HTTP/runtime ownership and live activation prerequisites remain with the coordinator.
