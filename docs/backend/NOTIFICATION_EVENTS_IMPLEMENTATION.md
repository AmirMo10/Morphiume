The constructor rejects live/unknown deployment modes before connecting. `parseNotificationEventInput(unknown)` also exports the strict two-UUID worker payload guard. It rejects extra caller type/recipient/actor/permission/audience/text/reason/contact/provider/amount fields, getters, symbols, hidden fields, custom prototypes and coercible/nested inputs. UUID case is normalized. `notificationTemplate(type)` and `notificationRecipientRoles(permission)` are pure exports for bounded contract checks. `NotificationTemplate`, `NotificationEventDispatcherOptions` and `NotificationEventDispatcher` types are exported.

The new contracts file defines audiencecustomer|operator, the planned finite NotificationKind allowlist, required operator permissionorders.fulfill|refunds.write, NotificationPageInput, InAppNotificationDto and NotificationPageDto. These page types are a future API contract; this dispatcher implements **no feed, mark-read method, producer or HTTP route**. The item has id/kind/title/body/orderId(nullable for legacy)/createdAt/readAt. It exposes no source event/permission/recipient/actor/evidence/contact. Private audience comes from the distinct native API route, never a caller ownership field.

This is a **notification delivery transaction, not the anonymous analytics collector**. Root injects its worker pool; no max2/admission/quota policy is borrowed from B. It uses500ms lock timeout and3s per-statement timeout, no external network call, no hidden retry, a bounded recipient set and one parameterized batch. Mapped delivery/DB/overflow failure throws a static CommerceErrorCONFIGURATION503 so the future worker retries rather than marks delivery complete. Raw DB error messages are never propagated to the job error field. `processed`/insertedMessages count committed internal records, not a read receipt or external transmission.

## Source and routing semantics

Each call first serializes on notification-only advisory namespace818006 plus a hash of the canonical event UUID; B uses818005. It reads only `order_event.type` and the owning `orders.user_id`, requiring persisted event.id/order_id to match both pointers. It takes no financial/event rowFORUPDATE. Missing/mismatched/unmapped events return ignored/0/0 without inventing any message. The event's type chooses the fixed template. The source key/actor, order snapshots, refund reason/evidence, receipt amounts/references and job-supplied text are not selected into messages.

| Canonical source | Customer | Current operator permission |
|---|---|---|
| order.created/payment.verified/shipment.shipped/shipment.delivered | Generic owned experimental update | None |
| request.cancel/return/approved/rejected/received/closed | Generic owned request update | orders.fulfill |
| refund.pending/completed/failed | Generic owned refund update | refunds.write |
| payment.inventory_exception/extra_receipt | Result needs review; never fabricated payment failure | refunds.write |

No job-name alias is treated as source evidence: order.paid, shipment.updated, payment.exception, payment.failed, legacy.order_update and unknown types are unmapped here. Existing legacy jobs retain their existing consumer until joint cutover. Source fixtures in the prepared integration tests include controlled persisted events for the new producer types; they prove dispatcher semantics when executed, **not atomic business producer behavior or native MFA issuance**.

A customer recipient is the durable order owner with current enabled account and verified-phone flag. Operators come from the maintained ROLE_PERMISSIONS map, with current enabled account and enabled MFA factor. They may be offline: delivery does not require an active session/admin grant. Sorted userFORSHARE and then current matching membershipFORSHARE locks keep delivery eligibility valid through batch commit and remove revoked roles after waits. There is no new five-minute finance gate for ordinary inbox delivery/access. Future reads still require current enabled native session, live MFA grant and message-required role permission. Delivery eligibility is not access authorization.

Select at most501current operator users;501is explicit overflow, never a silent truncation. Recipient IDs are deduplicated across eligible roles. Under the per-event advisory lock, the union of previously stored operator recipients and the new current set must remain at most500over the event's lifetime. A changing role cohort after a crash cannot add another500recipients. Overflow throws before inserting even the customer row, preserves earlier committed messages, and requires operator review; it does not delete old messages or invent completion. Up to500operators plus one customer are inserted by one jsonb recordset batch. A user who is both owner-customer and eligible operator can have two separate audience records; future API audience filtering is mandatory.

Each new event key hashes the exact canonical tuple[eventUUID,audience,DB-derivedrecipientID], with prefixnotification:v2. Unique source_event_id/audience/user_id also enforces DB dedup. Repeated delivery leaves id/title/body/readAt/createdAt unchanged. A retry selects current roles again; previously committed revoked-recipient rows remain history, but read/mark permissions must hide them. Newly eligible operators do not automatically get historical completed events; this module scans no history or queue. Role changes observed only on a retry of an authorized new notification job follow current routing, subject to the lifetime cap.

Titles/bodies are fixed Persian experimental text within160/500characters. Failure text does not claim transferred money; exception text does not invent failed payment/shipment. No reasons, evidence, addresses, tracking codes, contacts, amounts or provider references are interpolated. UI must render text normally and obtain any order details through current scoped authorization.
