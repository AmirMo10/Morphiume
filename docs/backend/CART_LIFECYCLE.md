## Contract

The factory exports `claimCart(actor:Actor,cartId:string,guestToken:string,expectedVersion:number):Promise<CartDto>`. Existing CartDto/CheckoutDto shapes remain unchanged. A customer needs a current non-disabled user, canonical verified Iranian mobile and a live maintained-auth session. Customer proof uses `clock_timestamp()` before/after cart waits and at the final shared user/session lock boundary; no admin MFA or five-minute freshness rule applies. Authenticated cart item/coupon writes also recheck that proof after waits and near commit.

Unclaimed cart plus matching bearer/version assigns the customer, rotates/revokes the bearer and increments version/updated_at once, retaining all items/coupon. Same-owner claim replay returns the **current** cart with no mutation, even with an old token/version; it never clears newly added selections. Different owner/unknown cart/wrong guest bearer uniformly returns NOT_FOUND404 after authentication. Invalid UUID/token shape/version is VALIDATION400; stale matching unclaimed version is CONFLICT409. Expired/disabled/unverified customer is UNAUTHENTICATED401; admin actor cannot claim and receives FORBIDDEN403. Owner authorization comes from the native actor, never cart ID/token alone.

New checkout snapshots selected quantities, coupon/money/address/policy, reserves inventory/quota and creates order/attempt/idempotency/outbox in its transaction. It then deletes that locked cart's items, clears coupon, assigns owner/revokes bearer and increments version/updated_at once. Final current customer proof precedes commit. Any error rolls back every staged effect, including consumption/version/ownership and idempotency rows. Provider network initialization remains after commit.

Saved exact actor/operation/key/normalized-payload replay resolves before cart access. Empty, edited or inaccessible current cookie cannot prevent recovery; changed payload conflicts. A saved replay never consumes newly added selections or an old retained cart. CheckoutDto returns the existing order/attempt/current attempt state/accepted total, not a mutable cart. Unknown payment keeps its durable original order/attempt and blocks a fresh attempt; authoritative known failure retries that same order with accepted snapshots. Late/extra receipts never restore cart selections. Cancellation/refund/return does not automatically repopulate a cart.

`CART_CHANGED` (409) is emitted only by **new createCheckout's locked cart version mismatch**, after actor/key/fingerprint lookup has found no saved order. No staged effects/key row commit; monotonic cart versions prevent that old payload from later creating an order. The UI may discard that stale pending attempt, requote and obtain new consent/key. A saved payload mismatch remains generic `CONFLICT` and retains the original recovery state; exact saved replay still succeeds before the version gate. Claim/item/coupon version, budget, quota and other conflicts retain their prior codes. No operation-status endpoint, tombstone or schema was added.

## Lock boundaries

New checkout orders locks as settings/idempotency → cart → customer budget → coupon/stock → final user/session proof. The customer budget uses `FOR NO KEY UPDATE`: it still serializes same-customer active-order counts and conflicts with existing payment retry's `FOR UPDATE`, while permitting FK `KEY SHARE` from another staged idempotency row. Claim/cart writes lock cart before their final user/session share locks. Saved replay omits cart and budget work entirely. Existing retry business logic, leases, inventory sweeps and global queue selection are unchanged.

The initial attempt to move `FOR UPDATE` after cart correctly denied obsolete versions but produced a real40P01 in a deterministic two-waiter test; automatic transaction retry hid that error from ordinary result assertions. The corrected mode is tested by capturing actual client40P01 errors in isolated fixtures and observing both real cart waiters, plus explicit claim/checkout and retry/budget schedules. Tests do not replace runtime queue semantics or add diagnostic HTTP handlers.

## Integration boundaries

Root's accepted ingress contract is explicit cartId+expectedVersion and matching current HttpOnly cookie for claim/absolute quantity/coupon mutations; no replacement-cart preflight on those mutations. Saved checkout recovery passes the actor/body/key directly to the domain even when matching cookie proof is absent. GETcart/additive POST retain their existing permitted fresh-cart behavior. Frontend must refresh the consumed cart, preserve owner-scoped unknown recovery, clear stale account drafts across tabs and use updated versions; those UI/native facts are not claimed complete by this domain slice.

Cutover affects only a new durable checkout or explicit current-browser claim. Other retained legacy carts, paid snapshots, receipts and unknown attempts remain untouched. Tests model legacy retained shapes inside generated schemas; no real legacy rows are rewritten.
