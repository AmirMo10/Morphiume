# Commerce invariants

Observed/implemented contract, 2026-10-12. Runtime checks are reported separately; this document is not proof of passing tests.

- DB and server money use integer IRR; public JSON uses decimal strings. Prices, shipping and payable totals are whole تومان expressed as multiples of 10 IRR. Admin price input is an integer تومان string converted once. Application money cap is 1,000,000,000 IRR, an engineering limit rather than a provider promise. Percent discounts round down to whole تومان. Tax is zero in controlled staging until owner-approved applicability exists.
- `on_hand >= reserved >= 0`; sellable equals on_hand minus reserved. Cart creation reserves nothing. Checkout locks balances in UUID order, snapshots accepted amounts/recipient/policy, creates reservation, attempt and outbox in one transaction. Network calls occur after commit.
- `checkout_idempotency` is scoped to user and operation and checks a canonical request fingerprint. Different input with the same key conflicts; an existing operation returns its preserved result even after policy settings change. Cart secrets are opaque random values stored only as digests; claim rotates the digest and requires the verified customer thereafter. Object IDs alone grant no access.
- Explicit current-browser cart claim preserves items/coupon, assigns only the verified current customer and revokes its guest bearer/version once. Same-owner replay returns current selections without effects; different owners receive uniform denial. Customer session/account/verified-phone validity is rechecked with wall-clock time after cart/auth waits and near commit. No global cart merge or historical backfill occurs.
- Only a newly committed durable checkout consumes its locked items/coupon and increments cart version once. Order snapshots/reservations/quota/attempt/outbox and consumption commit atomically. Saved exact actor/payload replay resolves before cart access and cannot clear newly added selections. Unknown/failed/late payment recovery remains through the original owned order; payment/refund/return does not restore cart selections. Cart→customer budget uses NO KEY UPDATE to retain active-order serialization without conflicting with other idempotency FK KEY SHARE waits.
- CART_CHANGED409 means new checkout found no saved order after actor/key/payload lookup and rejected a stale locked cart version. Its transaction commits no effects and the old payload cannot create later as cart versions only advance; requote/new consent is required. Saved payload mismatch stays CONFLICT, exact saved replay bypasses current cart checks, and all other claim/item/coupon/budget/quota conflicts retain their existing code.
- A successful receipt is unique by provider, merchant and provider reference. One order commits inventory once and has at most one shipment. Every distinct receipt remains recorded; additional funds enqueue an exception. Late payment after released reservation reallocates only available stock, otherwise records a paid inventory exception.
- Expiry and stock changes write inventory ledger operation keys. Per-customer row locks serialize the three-active-order reservation budget. Worker jobs use durable outbox leases and retry, including payment initialization committed with the attempt. Delivery may repeat; external recipients must use the provided dedupe key. No global exactly-once claim applies.
- Product edits check a version and retain order snapshots. Missing variants become inactive. Inventory adjustment cannot reduce on_hand below active reserved stock.
- Product shortDescription/careInstructions/approvedWarnings are optional supplied plain text with blank DB/DTO defaults and 600/4000/4000 input limits. Absent update fields preserve the row read under the product lock; explicit blank clears. Short description participates in normalized search; care/warnings do not. Content, gallery, variants, version and audit save in one transaction; paid snapshots remain immutable. Imports create only and reject existing slug/SKU rather than updating prior content.
- Product create/update/publish/archive/import requires a currently enabled MFA account, live session/grant and catalog.write using wall-clock time after business/authorization waits. Newly stocked variants also require current inventory.write. Final shared account/session/grant/role locks protect the proof through commit; any staged effects roll back on denial. Multi-row import takes that locked proof only after its last business wait, and owner-only foreign-media reuse is rechecked against current roles. Ordinary catalog actions do not acquire the financial five-minute freshness rule.
- Product and collection slug claims are immutable and unique within their separate URL namespaces. Renames retain all old claims pointing directly to the entity; its current slug is the canonical destination. An entity can reclaim its own old slug; another entity cannot take a current/historical claim, including one owned by an archived entity. SQL triggers enforce claims for imports/seeds/raw fixture inserts as well as service writes. New UUID-shaped slugs are rejected; ID route fallback stays unambiguous. Public resolution hides withdrawn targets and their aliases uniformly.
- Bulk preview has no durable effects. Commit checks all product versions and reserved balances, locks sorted products/variants/balances, and updates all selected rows or none. Price and stock permissions apply only to their requested fields. The actor/key/fingerprint record stores one result and audit operation; repeated requests cannot apply stock movement twice.
- Committed bulk also requires an MFA-enabled account, fresh five-minute factor proof and current field permissions at replay/mutation boundaries, using database wall-clock time after waits. Preview retains standard grant behavior; saved results remain immutable and require renewed proof when stale. A remaining grant cannot authorize commit after the account factor has been disabled.
- MFA_REQUIRED (403) denotes stale factor age alone after valid enabled account/session/live grant and current required roles. Invalid/revoked/disabled state remains denial, including when combined with stale age. Base state and factor age are reread after authorization waits; the five-minute window and grant/session validity do not change.
- Free shipping is configurable in integer IRR and applies inclusively after discounts. Quotes fingerprint the source fee/threshold, policy version and resulting quote fee. Fresh quotes/new checkouts read and validate settings with their existing ordinary transaction client; shared/exclusive advisory lock 818002 covers the absent-row case as well as row locks. Changed settings require fresh consent. Unset threshold keeps the existing fee, and old orders/attempts/idempotent results retain accepted amounts. No threshold or shipping policy is inferred from brand facts.
- Customer order reads require current session and ownership. Admin operations require a current session, unexpired MFA grant and current role permission. Supporting operators cannot refund or change roles by default.
- Paginated counts and bounded items have identical authorization/filter scope and one repeatable-read snapshot. Global facets use only published catalog rows. Bounded exports reject an exceeded ceiling explicitly and never return silently truncated financial/catalog data. Page/export hydration uses batched child queries.
- Collection indexes return bounded summaries and real member counts without product galleries. Public detail/count/facets include only published products with an active variant; detail preserves configured membership order unless an explicit supported sort is selected. Complete admin selection retains at most 300 stored IDs and labels, including withdrawn/inactive members. An already-published collection remaining published may retain previously linked hidden members; new hidden attachments and draft publication are rejected. This is an engineering retention rule, not an invented customer return/shipping policy. Stored collection/member/product locks serialize concurrent edits and withdrawal. Legacy array methods reject above 100 collections or 1000 membership rows; first-party consumers use pages/details.
- Optional catalog price bounds convert whole تومان once through the central utility and compare inclusive BIGINT IRR values. Volume, availability and price range bind one active variant, including the price-sort key; a different SKU cannot supply stock/volume for a priced SKU. Full DTO variant lists remain available for selection.
- Shipment advances from preparing to shipped to delivered; cancelled shipment/order cannot resume, and delivered cannot regress to shipped. Exact status/carrier/tracking replay does not write timestamps, history, audit or notification jobs, including after a later refund. Actual shipment changes still require eligible paid/partially-refunded funds.
- Checkout maintenance consent is read/locked before actors/orders/inventory. New orders and attempts are rejected atomically during pause; saved idempotent results and durable pre-pause attempts remain usable. Strict boolean validation fails closed. Shared/exclusive setting lock 818003 fixes the writer/checkout lock order and the absent-default-row race.
- Cancel and return transitions are distinct: cancellation never becomes received. Full-order physical receipt needs an explicit manual quality/restock decision; no quality policy or return window is inferred. One active request is allowed under the order lock. Immutable decisions bind actual source/target state, actor and normalized reason/restock; exact replay has no effects, differing payload conflicts. Legacy ambiguous closures/replays require manual review and are not backfilled with invented evidence. Order+variant restoration keys plus existing positive legacy restoration evidence prevent a second committed-line restoration. Rejected or documented unreceived closure may be reviewed again; a received full return cannot.
- Approved cancellation is durable beyond the mutable order status. An immutable approved cancel decision or exact legacy approved event matched to a cancel request prevents allocation after later payment-exception transitions. Multiple authoritative late receipts remain recorded as inventory exceptions, with no stock, shipment or coupon reactivation; generic return approval is not cancellation evidence.
- Refund budgets lock the receipt/order and include pending, processing and succeeded refunds. Request and manual completion require an MFA-enabled account, current finance permission and five-minute factor proof rechecked with clock_timestamp() after all financial and authorization waits, including saved replay. Request keys bind actor and payload; completed manual evidence replays only when exact, otherwise conflicts. Recording a manual completion does not automatically restock a returned perfume. Quality review and approved return policy are needed.
- A manual failed refund means an authorized operator explicitly recorded confirmed non-transfer with reason and evidence. Unknown/timeout outcomes remain unresolved. Only pending/processing can become failed; immutable decisions bind refund, actor, operation key and normalized payload, with unique actor/key across refunds. Exact replay requires fresh finance proof after all waits, including decision/unique-key locks; conflicting terminal payload/actor/key is rejected. Failed status releases its budget once without changing receipts, order amounts, other successful refunds, unknown payment attempts or inventory. Failed and succeeded are mutually exclusive terminal decisions.

Reversible decisions: Next.js/TypeScript modular monolith; Drizzle stable schema for library auth plus explicit reviewed SQL domain migrations and pg transactions; one warehouse; standard shipping with configurable fee; PostgreSQL outbox; configurable 15-minute reservation; test/staging mock provider. Retain PostgreSQL financial records when changing any of these choices.
