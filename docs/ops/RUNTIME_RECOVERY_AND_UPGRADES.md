## Upgrade protocol after a first deployment

`runtime/deploy.py` remains first-deployment-only. Do not bypass its populated-schema/existing-service guard or rerun seed to upgrade a running namespace. `runtime/upgrade.py` is now prepared and synthetically tested; it remains unexecuted and requires a new source review/accepted-image dispatch. A future upgrade needs independently accepted **new** source/config/manifest/archive and explicit Backend migration/schema review, plus all five explicit previous source/config/manifest/archive/Ops identities.

Before invoking the command, the coordinator specifically fast-forwards the clean checkout to the accepted new source and separately verifies/loads its archive. The running old image, its archive, frozen Ops bundle and protected deployment record remain retained independently of that checkout. The command verifies both releases and current healthy UID1001 writers, holds the release lock, records the fresh DB's applied checksums, pauses only runtime app/worker, takes and rehashes an encrypted backup identifying the **old running release** (also recording the executing backup-code fingerprint), then invokes only the candidate image's guarded CLI migration against `morphiume_staging_runtime`/its owner. It invokes no seed, Git operation, image pull or role/secret change.

Both current and candidate root600 env files point to immutable verified Ops bundles. New bundles live below `releases/SOURCE/ops-bundles/OPS_SHA256/ops`; historical single-source bundles remain retained/readable against their own trusted hash. If an explicit access profile exists, upgrade binds it to candidate image/Ops/config hashes and durably selects the new canonical profile before writer recreation; origin/secrets remain the same. Pending/failed preview transitions block upgrade. After app/worker readiness and exact image/source/user checks, existing migration names/checksums must remain unchanged. The command preserves old metadata, promotes candidate env/record and retains `upgrade-result.json`; native fixture acceptance remains **pending**. Timer approval must explicitly bind the new release and active profile; original integration schema/history is never the migration target.

Arguments are the common explicit new release identities plus `--previous-source`, `--previous-config-id`, `--previous-manifest-digest`, `--previous-archive-sha256`, `--previous-ops-sha256` and `--migration-reviewed`. Default execution is an unexecuted plan; only explicit `--apply --quiescent-window-released` after dispatch starts the protocol. Partial markers/candidate env, wrong prior identity, wrong DB/writer identity or invalid/incomplete/corrupt backup stop before migration. Failure stops any candidate writers, preserves phase/backup/state and does not automatically restart an old image after a possibly changed schema. The9 local upgrade/imported-backup tests use mocked server commands and prove ordering, no seed, partial-state and backup-identity rejection; they are not real migration/backup/recovery results.

Failure preserves stopped/partial state and evidence for a reviewed recovery decision. Image rollback is allowed only if Backend has confirmed the resulting schema is compatible with the prior image; it does not roll schema backward. Prefer a separately isolated restore rehearsal for business validation, never an automatic restore over the current runtime or original DB. Switching to a newer working-tree migration set or main tip before its image is accepted would invalidate this sequence.
