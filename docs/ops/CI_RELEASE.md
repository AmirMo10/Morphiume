# CI and controlled release contract

The coordinator owns shared package scripts and `.github` workflow files. This is the operations interface and acceptance contract for their implementation; a workflow existing in source does not establish that a CI run passed.

Use the pinned Node runtime/package manager and frozen lockfile. Required jobs are install, lint, typecheck, meaningful domain/authorization/concurrency tests against disposable real PostgreSQL, production build, browser acceptance tests, dependency audit, secret scan, image vulnerability scan and artifact manifest. Record exact commit/tool versions and reports. Preserve failures as evidence; confirmed critical/high reachable findings and finance/inventory/authorization failures block release. Generate a dependency/asset license/provenance register and compatible SBOM/provenance alongside the immutable image.

Build `linux/amd64` off the deployment server from `deploy/staging/Dockerfile`; test that app/worker/migration all start as uid1001. Run release smoke/security/performance checks with `NODE_ENV=production`, `DEPLOYMENT_ENV=staging` and controlled mock adapters. Explicitly test live-mode rejection of mocks, missing secrets, seed/demo controls and unsafe config. Do not give unknown pull requests registry write or deployment/PSP/SMS secrets. Pin third-party Actions by reviewed full commit SHA; do not use unverified mutable tags for release identity.

Publishing an image or deployment artifact needs coordinator authorization. After an approved push/release, keep the last known-good image identity and compatible schema plan, verify transferred image checksum/digest, quietly validate Compose, back up, migrate once, wait for app/worker readiness and perform T25. Limit release concurrency so two migrations/deploys cannot overlap. Serialize deployment using a host lock or environment concurrency; do not expose the Docker API publicly. Use a dedicated constrained deployment identity before enabling unattended CI access; the current root SSH key is for the authorized manual setup and does not establish minimal CI privileges.

Retain build logs/test reports/image SBOM and source revision without runtime secrets or DB dumps. Retry with verified official package/image mirrors/caches during network failures, and document the cache completeness; incomplete caches cannot promise offline builds. Live release remains blocked by owner inputs, verified service connections, restore evidence, independent acceptance/security tests and actual network/capacity results in their reports.

## First image failure and replacement gate

CI run38242058151 built the initial image without runtime configuration, then image job114787802116 failed Grype with exit2; that image was not published or accepted for deployment. Findings included Debian bookworm Perl/GnuTLS/glibc/ncurses packages, unused global CLI undici/brace-expansion and esbuild's Go binary. No advisory was suppressed and no severity gate was weakened.

The replacement uses pinned Node24.21.0 Alpine3.24 for both stages and a standalone application plus bundled JS CLI runtime. The final stage removes npm/Yarn and copies only web/CLI runtime dependencies, static/public assets and SQL. The complete Linux image must actually migrate/seed an isolated DB, serve app readiness/media, run a successful worker heartbeat, handle shutdown and pass native customer/admin flows before scan/push. Upload Grype JSON with package locations on failure so remediation targets the actual file/package; a base choice or local dependency probe does not prove the scan passes. Retain scan/tool/database timestamps, SBOM and exact tested/published digest.

The first minimal Alpine image subsequently passed its Linux-musl encoder build but failed nine High APK findings. [Exact evidence and remediation assessment](IMAGE_SECURITY.md) preserves all findings, pins official patched OpenSSL/zlib APK versions and distinguishes Node's embedded OpenSSL from the system libraries. A final-filesystem Node/native/TLS audit is prepared; it and the unchanged scan/container acceptance gates must actually pass before publication. Unsupported-protocol/call-path reasoning is documented as inference, not a scan exception or broad security clearance.

The loaded image is scanned and functionally tested before an attested candidate is pushed. Promotion compares that candidate's exact Linux amd64 config digest to the tested Docker image ID and checks its source revision label; a mismatch fails without promoting the source tag. Candidate publication metadata, sanitized scan/browser evidence and the accepted identity are retained. Generated reports/configuration live in ignored build-context paths so they cannot trigger a different second build.

Windows standalone smoke found Sharp's addon was traced but adjacent native DLLs were omitted. Asset preparation now copies only the installed, exactly versioned Sharp/libvips platform packages, preserves their license files and executes a real WebP encoder smoke. The repaired Windows purchase regression passed in Chrome/WebKit. Linux musl still requires the actual image/media acceptance; Windows success does not establish that result.
# Accepted archive fallback

After scan, actual image/browser/worker acceptance and registry platform-config identity validation, CI additionally exports that same locally tested platform image through `docker save`, gzip and SHA256 as the seven-day `accepted-runtime-image` artifact. The artifact also contains `image-identity.json`. This allows the authorized private staging host to receive a verified archive through SSH if registry pull credentials are unavailable, without building on that host or changing package visibility. Before `docker load`, compare the archive SHA256; afterwards compare loaded image ID to `testedPlatformConfig` and its revision label to `sourceCommit`. Registry provenance/SBOM remains on the matching published manifest; the platform archive is not represented as an attested multi-platform manifest. This path is prepared and has not yet produced or transferred an accepted archive.
