# Fresh protected runtime database proposal

This is a reviewable plan, not an executed database or deployment change. The accepted-image gate and Backend's explicit end of the shared PostgreSQL quiescent regression window must both precede any cluster DDL/DML. Do not infer that the window ended from elapsed time or CI success. No original fixture row, queue event, credential or migration history is to be reset, copied into runtime, replayed or deleted.

## Boundaries and concrete names

Use a fresh logical database in the existing isolated staging PostgreSQL18.6 cluster, avoiding another persistent PostgreSQL memory ceiling on the4.8GiB host. PostgreSQL roles are cluster-wide, so creating these roles/database is shared-cluster DDL and remains prohibited during the current quiescent window. Adding a database changes cluster catalogs/files; it preserves the original database's schema/data/history and is not a claim that the physical cluster bytes remain unchanged.

## New credentials, grants and failure guards

Generate fresh random DB passwords and separate app customer/admin/control secrets. Worker receives independently generated required validator secrets. Preserve every original secret/key file; do not rotate or overwrite `.env.local` or the previous local connection files. App/worker/migration JSON files are mode600 uid1001; new DB password files are separate root-protected setup inputs. Only the setup process uses the existing bootstrap authority, without exporting it to the app/worker/migration jobs. Backup outputs use the new runtime namespace; using the existing authorized staging encryption recipient does not rotate its private key or establish offsite custody.

New migration owner: LOGIN, NOSUPERUSER, NOCREATEDB, NOCREATEROLE, no membership in any original role, ownership limited to the new DB/public schema. New app role: LOGIN with the same administrative restrictions, explicit CONNECT to the new business DB, USAGE on its public schema, SELECT/INSERT/UPDATE/DELETE plus sequence USAGE/SELECT through the migration owner's default privileges. Revoke PUBLIC CONNECT and other DB/schema privileges in the new DB, then explicitly grant its owner/app access; cluster administrators retain administrative authority. Do not grant CREATE/DDL to app/worker and do not alter grants in the original DB to make a check pass. These grants do not prove the new roles cannot CONNECT to another database with preserved PUBLIC privileges. The intended boundary is no original table/owner grants or original-role membership; report any measured connection access separately.

Before any setup/migration/seed/backup/restore command:

1. Assert the original reserved live mount is still `/dev/mapper/vg0-lv--2`, ext4, and all new/preserved paths resolve to their explicitly reviewed locations. Reject symlinks into original data/config or the reserved mount.
2. Require the accepted source/config/archive identities and a clean checkout at that specific published source, or a separately approved ops bundle with recorded hashes; never follow an unreviewed newer main tip. App image stays the accepted immutable ID.
3. Detect existing new roles/database/config/marker. A partial/mismatching state stops for recovery; do not reset a database or regenerate passwords. Creation must be serialized. Role creation can be transactional; database creation is a separate PostgreSQL operation, so record/recover any partial state explicitly.
4. Before migrations/seed or any runtime SQL operation, authenticate through the actual supplied URL and assert `current_database()='morphiume_staging_runtime'` plus the expected role. A hostname/port or staging mode alone cannot prove target isolation.
5. Prove new roles have no original-role membership, original object ownership/table grants, superuser/CREATEDB/CREATEROLE or runtime schema CREATE. Measure original database CONNECT separately without claiming it is denied by the new DB's grants. Do not silently change any preserved original privilege.

The database creation command must use the reviewed constant identifiers, fresh passwords supplied privately and no secret-bearing command arguments or captured configuration output. No application image needs a runtime secret at build time. No SQL above has been executed by this plan.

## Concrete prepared source and dispatch contract

`deploy/staging/runtime/compose.yaml` contains only app, worker and guarded maintenance jobs. It uses the existing external internal network `morphiume-staging_database`, has no PostgreSQL service, binds app only to127.0.0.1:3001 and mounts media from the approved nested runtime path. Read-only Docker inspection observed that network and its `db` alias on the healthy existing container. Actual server Compose startup/network reachability has not been tested. Local Docker Compose5.5.1 quiet model validation with synthetic immutable image/ops-directory values passed; service env-file reading was disabled for this synthetic check because server-private files do not exist locally.

`runtime/contract.py` generates fresh private app/worker/migration/bootstrap/connection settings in memory, validates exact DB/role/origin/provider contracts and enforces mount/path, source, accepted archive/config and ops-bundle identities before mutation. `runtime/prepare.py` defaults to an unexecuted plan. Its explicit apply mode detects existing roles/database/config/partial state before creating anything; it creates only the new role/DB/schema/default grants. Database creation starts with connections disabled until PUBLIC privileges are revoked and explicit owner/app CONNECT exists. It compares original integration aggregates before/after without changing original grants or data. Secret-bearing role statements are not printed; statement/error logging is suppressed for that setup session only. New passwords enter authenticated checks through private stdin, never command arguments.

`runtime/deploy.py` is intentionally a **first-deployment** command. It requires pristine runtime schema, no existing runtime containers/deployment marker, complete protected settings and the same accepted image/source/network. It runs actual DB/role guards, accepted bundled migration and synthetic owner seed, then waits for nonroot app/worker readiness and checks their image IDs. Partial/existing deployment stops for reviewed recovery. The first pristine database has no populated business state to back up before its seed; subsequent upgrades need a separately reviewed backup/migration/rollback procedure rather than rerunning this command. Its seed-only env file contains fresh synthetic owner credentials; those keys do not enter app/worker services.

`runtime/db-target.mjs` is mounted read-only from the reviewed ops bundle for maintenance only. It validates both the configured URL and actual `current_database()`/`current_user()`, administrative flags, schema CREATE and original-role membership before starting a CLI bundle. App/worker retain the tested image commands. `runtime/backup.py` can stream an encrypted runtime-only DB/media backup only after both actual runtime writer containers are stopped and their image IDs match the deployed release. It uses new namespace credentials and the previously authorized encryption recipient. This prepared command has not produced a real backup. Fresh restore, health/monitor and gated timer source are now prepared; their actual execution/business acceptance/installation remain pending. See [runtime recovery and upgrade contract](RUNTIME_RECOVERY_AND_UPGRADES.md).

All apply commands require explicit `--source`, `--config-id`, `--manifest-digest`, `--archive-sha256`, `--ops-sha256`, `--quiescent-window-released` and `--apply`. The quiet-window flag is supplied only after an explicit coordinator release; elapsed time, successful CI or a flag alone is not authorization. They also require an already verified/loaded release at `/srv/morphiume/staging/runtime/releases/ACCEPTED_SOURCE` and a clean `/opt/morphiume` checkout at that source. They never pull an image or follow a newer main tip.
