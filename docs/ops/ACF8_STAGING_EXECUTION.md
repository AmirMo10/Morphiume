## پایش و پشتیبان زمان‌بندی‌شده

دو timer موجود موقتاً متوقف شدند و enabled بودنشان حفظ شد. guard و approval قدیمی E4 پیش از جایگزینی در تاریخچهٔ خصوصی آرشیو شدند. چهار unit پایه، cadence پنج‌دقیقه‌ای سلامت و inode/بایت‌های قفل ثابت ماندند؛ guardهای جدید به ACF8، پروفایل واقعی، T25 و restore پذیرفته‌شده وابسته‌اند.

اولین شروع مستقیم health خودِ سرویس را با موفقیت و یک action کامل کرد، اما collector شناسهٔ cached اجرای قبلی را پیش از شروع async خواند و با صفر نمونهٔ منابع رد شد. نتیجهٔ اولیه حفظ شد. اصلاح محدود collector با baseline شناسه و ActiveState و آزمون حالت قبلی→اجرای جدید انجام شد؛ شروع دوم برای اندازه‌گیری معتبر بود. بنابراین health دو شروع مستقیم و backup یک شروع مستقیم داشتند؛ تکرار آزمون‌های خرید صفر باقی ماند.

چرخه از journal معتبر PID1 و stdout همان Python/InvocationID اثبات شد؛ زمان اجرای process به‌صورت جدا ادعا نشده است. مقادیر CPU/حافظه در خلاصهٔ امن، بیشینهٔ نمونه‌های cgroup هستند، نه ظرفیت کل میزبان. OOM مشاهده‌شده صفر بود. سلامت 50s/256MiB/یک core و backup20min/512MiB/نیم core با stop90s حفظ شدند. پشتیبان اندازه‌گیری‌شدهٔ زمان‌بندی، بازیابی مستقل همین اجرا را به ارث نمی‌برد؛ restore آن capture تازه هنوز pending است.

پس از دو اندازه‌گیری، approval به recurring ارتقا یافت، هر دو guard با hash جدید دوباره رندر و انتخاب واقعی manager بررسی شد. فقط دو timer قبلاً enabled شروع شدند؛ enable/disable یا تغییر زمان‌بندی صادر نشد. health پنج‌دقیقه‌ای و backup روزانه03:00UTC با jitter15min است. فعال بودن timer، پایان همهٔ اجراهای خودکار آینده یا تحویل اعلان بیرونی را ثابت نمی‌کند.

## حدود و ادامهٔ عملیات

این محیط staging با PSP/SMS کنترل‌شده، CIDR و Basic روی IP خصوصی است. TLS/domain، درگاه و پیامک واقعی، مقصد offsite، نگه‌داری کلید و WAL/PITR همچنان وابستگی‌های واقعی‌اند. ظرفیت E4 به نسخهٔ تازه تعمیم داده نشده و در این درخواست بار تازه اجرا نشد. schema، storage و دادهٔ محیط فروش رزروشده بازنویسی نشدند؛ حفاظت mount اثبات برابری همهٔ ردیف‌های آن پایگاه نیست.

برای عملیات بعدی [قرارداد جاری](STAGING_CONTRACT.md)، [runbook](RUNBOOK.md) و [پشتیبان/بازیابی](BACKUP_RESTORE.md) را بخوانید. منبع برنامه را با commit ابزارها یا main جابه‌جا نکنید؛ blob ابزار از commit مستقل و hash ثابت materialize می‌شود. guard قدیمی E4 و مثال‌های generic مجوز restart نسخه613 یا restore روی دادهٔ فعلی نیستند. گذرواژه، Basic، OTP، URI عامل دوم، کوکی، تماس و شناسه‌های fixture در Git منتشر نشدند.

بررسی‌های آفلاین اجراشده: ۳۷ مورد guard بازیابی و ۴۶ مورد scheduler عمومی، سپس ۲۴ مورد collector اصلاح‌شده و ۳۰ مورد پذیرش رکورد بازیابی، مستقلاً توسط هماهنگ‌کننده موفق بودند؛ آزمون قرارداد خصوصی عامل تجارت نیز ۱۴۲ مورد موفق داشت. این موارد به جای اجرای واقعی server/native حساب نشده‌اند. بررسی مستقل نهایی ۹۷ لینک و ۶۲۱ فیلد JSON را کنترل کرد. اسکن مرحلهٔ Git ابتدا سه هش عمومیِ پروفایل را به‌عنوان generic API key علامت زد؛ استثنای دقیق همان hash و فقط دو مسیر گزارش افزوده شد. اسکن نهایی صفر یافته داشت و کنترل منفی، hash متفاوت و همان hash خارج از مسیر مجاز را همچنان رد کرد.
