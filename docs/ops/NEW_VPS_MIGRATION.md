# New VPS: reproduce the accepted Morphiume staging site and data

Prepared **20 October 2026**. The owner canceled OVF/OVA and chose: upgrade dependencies, fully test the resulting source and packaged image, then prepare a clean-VPS migration. This document prepares that migration; it does not claim a destination deployment. No destination address, verified SSH fingerprint or target inventory has yet been supplied.

The requested replica includes the storefront/admin, all six labeled demo products and their uploaded images, variants/prices/stock, settings, existing accounts/MFA, immutable orders/receipts/payment/stock history and pending work. It stays `DEPLOYMENT_ENV=staging` with controlled payment/SMS. Preserve the current source and its backups until the new target is accepted. A later real-sales launch at `morphiume.ir` has separate requirements in [MORPHIUME_IR_MIGRATION.md](MORPHIUME_IR_MIGRATION.md); copying the demo ledger is appropriate for this replica and inappropriate for a fresh real-sales ledger.

## What to buy

| Use | CPU | RAM | Persistent storage | Meaning |
| --- | --- | --- | --- | --- |
| Initial equivalent staging replica | **4 vCPU** | **8 GiB** | **100 GB NVMe** | Recommended starting purchase, with offsite encrypted backups and builds/tests elsewhere |
| More recovery/growth margin | **8 vCPU** | **16 GiB** | **160 GB NVMe** | Prefer when running an isolated restore beside the source workload or retaining substantial history locally |
| Larger public workload | Measure first | Measure first | Size from actual growth | No concurrency, sales throughput or availability guarantee follows from a VPS size |

The current active configured limits total **3,200 MiB / 3.125 GiB**: PostgreSQL 1,280 MiB, app 1,536 MiB, worker 384 MiB. These are limits, not measured use; OS/Nginx/Docker, filesystem cache, backup/encryption, image loading and recovery need additional room. CPU quotas total 3.5 cores but are ceilings, not guaranteed demand. An 8 GiB VPS is the minimum purchase class for this handoff; the host guard allows Linux `MemTotal` down to 7 GiB because advertised memory and usable memory differ. Optional 2–4 GiB swap is emergency margin. Build, browser suites and load generation run off-host.

The coordinator's fresh read-only SSH inventory at `2026-10-20T06:24:06Z` observed Ubuntu24.04.5/noble x86_64, kernel6.8.0-146, four CPU, 5,155,532,800 bytes RAM (about4.80GiB), healthy app/worker/DB and Compose5.6.0. The root filesystem had 25,185,042,432 total / 19,009,507,328 available bytes; that is the root filesystem, not a complete data/backup-volume sizing calculation. Historical synthetic E4 tests on this host are [scoped evidence](../qa/E4_CAPACITY_EXECUTION.md), not a capacity guarantee for a new VPS or the upgraded release. Historical stopped restore projects consume disk even while using no active container RAM. Do not start them as part of the replica. Re-observe data/mount/backup usage at the final capture rather than treating these free-space figures as permanent.

For storage, budget: OS/Docker + allocated current PostgreSQL cluster plus growth + exact media bytes + accepted/fallback image archives and layers + retained encrypted backups + largest isolated restore working set + at least 25% free headroom. Add original integration/stopped-restore archives separately if the owner wants those historical environments transferred as archives. They are not additional active store services. A 100 GB NVMe disk is a starting recommendation, not permission to omit this calculation. Keep recovery copies outside both VPSs; same-disk copies are not offsite backup.

The accepted image is Linux/amd64; ARM requires a separately built/tested artifact. Ubuntu 24.04 is supported by the [official Docker Ubuntu installation instructions](https://docs.docker.com/engine/install/ubuntu/).

Use the signed official Ubuntu and Docker repositories. Explicitly record full Apt versions, including epoch/suffix, rather than guessing them from a Docker CLI semantic version. Select matching Engine/CLI versions and pin all five Docker packages in the private target manifest. Ubuntu security patch versions are resolved from signed repositories at preparation and recorded. Do not indefinitely hold security updates just to preserve a historical number. [Ubuntu package guidance](https://ubuntu.com/server/docs/how-to/software/package-management/).

## Safe preparation tools

The bounded [bootstrap](../../deploy/vps/bootstrap.py), [replica Compose](../../deploy/vps/compose.replica.yaml), [role initializer](../../deploy/vps/init-replica.sh), [media validator/extractor](../../deploy/vps/restore_media.py) and [requirements manifest](../../deploy/vps/requirements.json) are target-only. Defaults perform no network, package operation, Docker operation or mutation:

```bash
python3 -B deploy/vps/bootstrap.py
python3 -B deploy/vps/restore_media.py
# On the NEW target, read-only; retain this metadata privately:
sudo python3 -B deploy/vps/bootstrap.py --inspect
```

Before installation, use the provider console/firewall to permit only the reviewed administrator/VPN sources. Confirm a second working SSH session and console recovery. The package bootstrap does not alter SSH/firewall rules; Nginx's package may start its default site. Do not open the new host publicly before the target proxy/perimeter is reviewed. Docker publishes can bypass UFW, so app loopback/no DB publication and actual IPv4/IPv6 tests are required. Use Docker-compatible `iptables`/`ip6tables` policy where needed. [Docker firewall guidance](https://docs.docker.com/engine/network/packet-filtering-firewalls/).

`--apply` requires the destination's exact machine ID, an IPv4 address actually assigned to that host (provider NAT/public origin is recorded separately), restricted SSH CIDR, independently reviewed SHA-256 of the official Docker signing key and all five full Apt package versions. Download/review key bytes from `https://download.docker.com/linux/ubuntu/gpg` over verified TLS and record the hash privately; a placeholder is not an accepted key. Retrieve package candidates from the official signed Noble repository. Do not reuse the source's SSH fingerprint for the new VPS.

```bash
# Variables below come from the reviewed NEW-target manifest; none is a secret.
# Do not run this against the source or replace them with guessed values.
sudo python3 -B deploy/vps/bootstrap.py --apply \
  --machine-id "$TARGET_MACHINE_ID" --target-ip "$TARGET_LOCAL_IPV4" \
  --ssh-allow "$ADMIN_CIDR" --docker-key-sha256 "$DOCKER_KEY_SHA256" \
  --docker-ce "$DOCKER_APT_VERSION" --docker-ce-cli "$DOCKER_APT_VERSION" \
  --containerd-io "$CONTAINERD_APT_VERSION" \
  --docker-buildx-plugin "$BUILDX_APT_VERSION" \
  --docker-compose-plugin "$COMPOSE_APT_VERSION"
```

The guard rejects source `192.168.240.51` including an address alias, hostname `morphiume`, wrong OS/architecture, incomplete observations, existing Morphiume/Docker/Nginx paths/services, unexpected listeners, failed services, pending reboot, unsynchronized time and insufficient resources. It never removes conflicts or overwrites a partial install. After any failure, retain logs/state and review a continuation; repeating `--apply` is deliberately refused once state exists. Run quiet Compose validation, never dump rendered secret-bearing configuration.

## Ordered capture, transfer and restore

1. **Accept the upgraded release first.** Complete dependency/lockfile/base-image review, lint/type/unit+DB/security gates, production build, three-browser source tests and the same tests against the packaged image; record actual failures/fixes/scan findings. Check schema compatibility explicitly. A dependency upgrade is not permission for an unreviewed DB major upgrade. Keep the current source healthy until cutover; do not run upgrade/seed commands opportunistically on it.
2. **Inspect and bind the fresh target.** Verify SSH fingerprint independently through the provider console; use strict checking and a dedicated deployment key. Record disks/mounts/free space, 4 vCPU/8 GiB class, OS/architecture, time, listeners, users/services and console recovery. Run read-only preflight, then the reviewed package installation. Apply security updates/reboot before the application migration. Re-observe afterward.
3. **Prepare fresh target paths and accepted source/tooling.** Use `/opt/morphiume` at the exact reviewed source/tool commit, `/etc/morphiume-replica` root0700 and `/srv/morphiume/replica` root0700. Create a fresh `postgres` child owned999:999 mode0700 and a root-only release/backup/evidence area; media stays absent for the guarded extractor. These must resolve without symlinks. Refuse anything already present rather than merging, deleting or resetting. The target Compose project is `morphiume-replica`.
4. **Take a fresh consistent export under an explicit write fence.** Pause new ingress mutations, worker and source health/backup callbacks in a recorded exclusive window; capture and later restore exact prior scheduling intent. Wait for in-flight requests/transactions, prove no competing writers, retain baseline, then export the active `morphiume_staging_runtime` database with its own PostgreSQL-version `pg_dump --format=custom`, retaining owner/ACL metadata. Encrypt the stream directly with `age`; never write plaintext DB data to disk. The existing scheduled backup deliberately uses `--no-owner --no-acl`; it remains a recovery checkpoint but is not sufficient by itself to prove an exact privilege replica. Capture role attributes/default ACL/extension/locale and full row/sequence/media hashes. Do not copy PGDATA. PostgreSQL logical export omits cluster-global roles, which are supplied explicitly. [pg_dump contract](https://www.postgresql.org/docs/18/app-pgdump.html).
5. **Export media/config and verify ciphertext.** Encrypt the complete media tree at the same fence, including private originals/capability as protected backup material. Encrypt exact app/worker config, role-password files, reviewed ACL metadata and source recipient/public operational settings separately, with a strict allowlist. Preserve distinct customer/admin auth secrets so existing MFA/account data remains usable; do not print them. Generate a separate target bootstrap-superuser password; owner/runtime credentials may be preserved for this isolated replica or rotated with all dependent config in one reviewed step. Never copy bootstrap seed env. Source recovery identity remains under independent custody, not in Git or an app mount. Retain source and offsite ciphertext SHA-256/byte-count proofs.
6. **Transfer over strict SSH, then compare independently.** Place encrypted bundle/image files in a fresh target root0700 directory with files0600. Verify target hashes/byte counts against the independently retained source manifest before decrypt/load. Use an offsite copy too. Do not place passwords in SCP/rsync URLs/arguments/logs. If doing a rehearsal, resume the source's exact prior services after capture; that backup is then a rehearsal point, not an eventual zero-loss cutover point.
7. **Verify and load the accepted app image.** Run `deploy/staging/verify-release.py` in its standalone **verification-only** mode with the four exact accepted identities. Its source-specific `--load`/`--verify-loaded` wrappers are not target bootstrap commands. A target operator then loads only that verified archive, uses the import-only `runtime/engine_image.py` `prove`/`mapped_report` contract to cryptographically rebind config/layers/source/user/launcher to the actual target Engine ID, and records the proof in the target manifest. The helper currently pins the observed containerd diagnostic contract; a changed target backend/version stops acceptance for compatibility review. Never reuse a source Engine proof or fall back to a mutable tag. The Compose image variable uses only the proven target immutable ID. Pull the accepted PG image at its recorded digest and verify platform before creating the new cluster.
8. **Restore protected config and start only the fresh DB.** App/worker JSON files are owned1001:1001 mode0600; parents root0700. DB role-password secrets are readable only by UID999 via exact secret mounts; target bootstrap password is new. Keep migration-owner config outside app/worker mounts. Preserve the distinct customer/admin auth secrets and each service's actual source values in both service configs; do not replace or align them during replication. Their URI host remains internal `db:5432`, database `morphiume_staging_runtime`, runtime role `morphiume_runtime_app`. Only review/change `APP_BASE_URL` and dependent canonical-origin settings for the new target; keep mocks/staging/media path. A protected `deploy.env` contains immutable image IDs and target origin, not passwords. Run `docker compose --env-file /etc/morphiume-replica/deploy.env -f /opt/morphiume/deploy/vps/compose.replica.yaml config --quiet`, then `up -d --no-build --pull never --wait --wait-timeout 180 db` with those exact Compose inputs. This creates only the `postgres` bootstrap DB and the two non-superuser roles; the application DB must still be absent.
9. **Restore the whole application database once.** Inspect the trusted dump TOC/schema beforehand and verify its database name. Through the fresh DB service only, pipe authenticated `age --decrypt` output to `pg_restore -U postgres --dbname postgres --create --exit-on-error`. This creates the source-named application DB and restores its exact owners/ACL/history/data. `--create` cannot be combined with a single transaction; an error leaves a stopped, partial target for inspection, never an automatic retry/drop/clean. Refuse an already-existing application DB. Do not use `--clean`, `--disable-triggers`, selective finance deletion, seed or migration. If only an old no-owner/no-ACL backup is available, stop and supply/review a separate exact role/ACL restoration plan rather than claiming privilege equivalence. [pg_restore contract](https://www.postgresql.org/docs/18/app-pgrestore.html).
10. **Restore media without activating source preview authority.** Temporarily decrypt media to a protected root0700 RAM directory `/dev/shm/morphiume-replica-RUNID`, file `media.tar.gz` mode0600; ensure RAM headroom first or use a separately reviewed encrypted-disk extraction path for larger archives. Record its plaintext hash after successful authenticated decryption. Run `restore_media.py --inspect --archive PATH --expected-sha256 HASH`, then a separately reviewed `--apply --machine-id "$TARGET_MACHINE_ID" --target-ip "$TARGET_LOCAL_IPV4"` with the same exact archive/checksum. Apply re-observes the target machine/local addresses and refuses the source including aliases. It rejects links/traversal/duplicates/devices/expansion bounds and existing media/quarantine paths. Public/private media goes to the UID1001 media root; the known old capability goes to root-only `/etc/morphiume-replica/quarantine`, outside that mount. Compare all retained media hashes plus the explicitly quarantined capability. Remove only the named temporary plaintext/key files after proof; never install the age identity persistently on the target or in the app container.
11. **Compare before starting writers.** With target app/worker still absent, compare every table/PK/row digest, immutable financial snapshot, migration/checksum, sequence, role/grant/default ACL, extension/collation and DB/schema ownership. Verify all six demo products, two variants each, current exact stock (not initial seed stock), old QA archives, image associations and media bytes. Check DML credentials cannot create schema/roles and are not superusers. Preserve existing owner/customer accounts, MFA and order ownership. Source sessions may remain in the dump; new origin cookies differ, so test fresh normal login rather than copying browser cookies. No table-count-only comparison qualifies this step.
12. **Bind target proxy/origin and accept the running site.** Remove Nginx default site only after preserving/reviewing the fresh-host config. Install a target-specific strict Host/proxy/client-IP policy, validate/reload it and permit only the selected VPN/CIDR. App stays `127.0.0.1:3001`; DB has no host publication. Set `Host`/forwarded proto/IP from trusted proxy facts; do not trust arbitrary external headers. For `morphiume.ir`, prepare DNS/TLS/renewal and canonical origin without changing source DNS until cutover. A public-domain preview still remains CIDR/VPN protected. Run the application profile with the exact accepted immutable image, then verify app DB readiness, real worker heartbeat, UID/read-only/capabilities/limits, graceful stop/restart and no unexpected public ports.

**New-origin admin behavior:** the existing source exception is hard-coded to `http://192.168.240.51`, staging, mocks and a protected server-only capability. At a new IP/domain it is intentionally inactive; the owner uses normal login/MFA. Do not rewrite the old capability or expose shared admin access publicly. Any later request for a new restricted preview exception needs a reviewed implementation and fresh target-specific acceptance. Preserving the store's business state does not mean preserving the old host's LAN address or widening its admin access.

## Destination acceptance, scheduling and cutover

Run a native product/admin-to-cart-to-OTP-to-order-to-mockverify-to-inventory-to-shipment/tracking scenario on the destination, plus replay/foreign-order denial, media/filters/mobile/RTL and normal owner MFA. Use a new bounded synthetic fixture and preserve all prior ledger/account rows. Record one receipt/stock commitment and exact owned cleanup; never delete history or the six retained demo products. Confirm target app/worker identities and proxy/IPv4/IPv6 boundary with actual external requests. A prepared script or CI result is not destination acceptance.

Create target-specific monitored health/encrypted-backup units and timers bound to the new manifest/paths/config, with deployment/backup locks and tested failure/time limits. Do not copy/enable source schedule approvals or unit callbacks pointing to `/srv/morphiume/staging/runtime`. Measure each service once, restore an actual target encrypted checkpoint in a fresh isolated project and perform business/media acceptance, then enable the reviewed cadence (source intent: health every five minutes; daily backup03:00UTC plus jitter). Test offsite retrieval and independent age key access. General RPO/PITR and alert receipt require their own measured evidence; a logical dump alone is not continuous WAL recovery.

For final transfer, repeat the fresh capture/restore from a **new** fenced source point if source data changed after rehearsal. Keep only one authoritative writer set: after the final capture, leave source writes/worker stopped while completing final comparison, target acceptance and routing switch. Record an agreed outage window and recovery point; DNS TTL alone cannot prevent stale clients writing to two independent databases. Change only reviewed A/AAAA/canonical records and preserve mail/TXT/CAA. Observe target and retain old source image/data/backups with a closed write perimeter.

Before target writes, rollback may return traffic to the still-authoritative source and restore its exact prior scheduling intent. After any accepted target write, do not route back to an old independent ledger: fence both sides and reconcile/transfer authoritative changes first. An image rollback does not undo schema/data. Never `down --volumes`, prune shared storage, overwrite source/stopped restore environments or replay partial restore commands. Keep failure journals and repair forward through a new reviewed operation.
