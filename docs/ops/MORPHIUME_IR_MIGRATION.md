# morphiume.ir: migration and public-release runbook

Prepared 2026-10-18 for the owner's stated later move to **another VPS**. This is an unexecuted migration plan. The current authorized delivery is the optimized, protected private-IP staging application with controlled payment/SMS. Domain selection is known; DNS ownership/access, destination VPS and real service contracts have not been verified.

The existing [launch evidence matrix](../LAUNCH_READINESS.md), [CI acceptance](../qa/REDESIGN_CI_EXECUTION.md) and [redesign staging execution](REDESIGN_STAGING_EXECUTION.md) define what has actually run. This document contains no production credentials or copy-and-run commands with staging database defaults.

On 18 October the existing server completed redesign cutover, three native purchase cases, encrypted backup/isolated accepted six-check/gallery recovery, owned cleanup, healthy source, measured health/backup, bound recurring approval/active enabled timers and final server/client observations. The [current private-preview acceptance](../qa/REDESIGN_RECOVERY_EXECUTION.md) is complete; publication is separately reported by the coordinator with its confirmed commit. Current activation does not establish future automatic delivery or a second restore of the measurement's new backup. Destination VPS, domain/TLS and real-provider inputs below belong to the later migration and did not block this controlled preview. No DNS change, destination provisioning or public-sales activation occurred in this work.

## What must change before this can be a live deployment

The current accepted image is not a public-sales image. `src/server/config.ts:getConfig()` rejects live unconditionally after checking required services. `src/server/auth/otp.ts:sendOtp()` has controlled mock delivery only. `src/server/media.ts` writes local private/public files and does not use `OBJECT_STORAGE_ENDPOINT`. `deploy/staging/Dockerfile` selects the staging-only `runtime.mjs` ENTRYPOINT; `deploy/staging/runtime/compose.yaml`, `operator-config.mjs` and DB target guards bind staging/mock identities and paths.

Implement and test a **separate reviewed live configuration/launcher/deployment contract**, real selected SMS adapter, selected persistent media/storage adapter and required business/provider validation before changing that gate. Rebuild off the VPS and accept the new exact image. Do not copy the staging Compose, weaken its guards, bypass the current ENTRYPOINT ad hoc or replace `staging` with `live` in an old approval. Staging tools remain scoped to staging.

The existing Zarinpal v4 adapter in `src/server/payments/zarinpal.ts` has create/verify/inquiry and separately declared reverse capability. Its controlled tests do not establish merchant approval, sandbox connectivity, the permitted reverse window or real bank refund execution. [Provider contract and limits](../backend/PAYMENTS.md).

## Release manifest and environment separation

The coordinator prepares one private immutable manifest before any mutation. It binds the full accepted application commit, CI run/attempt and artifact identities, tested platform config, registry manifest/provenance/SBOM, archive checksum, actual server Engine mapping, exact deployment-tool hashes, canonical HTTPS origin, DB role/database names, media roots, source migration history/checksums and planned target history, configuration fingerprints, backup IDs and recovery location. Store values/secrets separately; public evidence contains only safe identities and outcomes.

Use dedicated live configuration, Compose project, network, database roles, media root and backups on the new VPS. Their exact names/paths must be reviewed after its inventory; no inherited staging paths or implicit database fallback. App/worker get DML-only credentials, migration gets only the owner role, bootstrap superuser remains separately scoped. Config parents are protected and service mounts read-only. Customer/admin auth secrets differ; generate independent live secrets. Do not carry `MOCK_CONTROL_SECRET`, `BOOTSTRAP_ADMIN_*`, private Basic credentials, synthetic customer accounts, OTP inboxes, test payment controls or test fixture financial rows into live.

Pinned versions in today's accepted artifact are evidence of that artifact, not a promise of latest supported releases on migration day. Recheck maintained runtime/security support and official installation guidance, review lockfile/base-image changes and rerun CI when selecting the future live candidate. Build/install/browser/load generators remain off the VPS.

## Ordered migration procedure — not executed

1. **Inventory and prepare the destination.** Record resolved disks/mounts, free space, architecture, current services/listeners and administrative access. Preserve anything already on that VPS. Pin reviewed software and image identities; configure default-deny ingress and only intended reverse-proxy/administrative access. App, DB and optional cache remain nonpublic. Verify actual IPv4/IPv6 Docker publication externally; UFW status alone is insufficient. The existing `deploy/provision.sh` and `deploy/nginx/morphiume.conf` are historical private-IP preparation, not this live runbook's executable implementation.
2. **Finish the live implementation and accept its artifact.** Use the same maintainable modules/auth/commerce invariants. Real service adapters need typed bounded timeouts, unknown-outcome handling and sanitized failures. Keep live fail-closed for mocks, sample/bootstrap values, missing services and unsafe origins. Add meaningful contract/negative tests; run source and packaged-image acceptance. Record scan findings and disposition; no unresolved confirmed High/Critical exploit, amount/permission/oversell failure or fake payment success may be accepted.
3. **Provision isolated data and secrets.** Choose and record the new exact database and distinct bootstrap/owner/runtime roles. Prepare fresh service-scoped config/secret files with no output of secret-bearing Compose/environment dumps. App/worker remain nonroot, read-only with scoped writable media/cache/tmp, limited resources/capabilities, readiness, real worker heartbeat and graceful shutdown. Quietly validate the reviewed live Compose. The accepted staging `runtime/contract.py` and `db-target.mjs` must not be coerced to admit a live target.
4. **Choose the authoritative migration data.** Current staging data is synthetic and must not become the live sales ledger. For a fresh shop, create the live schema with reviewed canonical migrations using the owner role, **without `db:seed`**, then create only the approved live owner/catalog/settings through a dedicated reviewed provisioning path. If separately authorized real data must move, specify its source and complete entity/financial/media dependency closure; preserve immutable order/receipt/inventory/audit history. Do not selectively delete financial rows or copy staging user/session/MFA/rate-limit tables into live. A fresh live owner provisioner and its native MFA acceptance need explicit implementation; the staging seed is not that provisioner.
5. **Capture and rehearse recovery before cutover.** Take an encrypted, consistent DB+media backup of any authoritative existing environment; record writer stop/capture windows, schema/role/sequence/catalog and media checksums, and independent age recipient/key custody. Store a versioned encrypted copy outside both source and destination VPS. Verify ciphertext/checksums and actually retrieve/decrypt into a fresh isolated restore project; never restore over the current source or a previous rehearsal. Existing `runtime/backup.py` and `redesign-isolated-restore.py` are staging-scoped examples with historical project contracts, not ready-to-run live tools.
6. **Apply reviewed schema/data with writers stopped.** Hold a target-specific deployment lock; journal each operation once. Run only intended canonical migrations against the explicit live owner URL; preserve checksum history and compare schema/catalog/ACL/sequences plus all authoritative row identities/digests before and after transformations. `db/migrate.ts` supports explicit migration URLs and rejects altered applied SQL, but its fallback URL must not select the target implicitly. No seed, destructive reset or automatic rollback is part of migration. Retain failures and partial state for forward repair.
7. **Establish canonical TLS and proxy behavior.** Choose `https://morphiume.ir` or an explicitly approved canonical alternative and make `APP_BASE_URL`, `PUBLIC_SITE_URL`, auth trusted origin, redirects, callback and public metadata agree. Issue and verify a valid certificate and renewal, then redirect public HTTP/alternate approved host appropriately. Review HSTS after correct domain/TLS behavior. Nginx sets trusted host/proto/client forwarding values; do not trust arbitrary external forwarded headers. Credentialed CORS/CSRF and separate host-only admin/customer cookies remain enforced. Public health reveals no connection detail; `/healthz` alone is infrastructure, whereas `/api/health/ready` proves app DB readiness.
8. **Handle preview and payment access deliberately.** Keep the old private preview protected and distinct; close or retain its lease through its reviewed contract. Its all-route CIDR+Basic policy cannot be copied to a public shop or PSP callback. The live proxy gets an explicit reviewed public policy with separately authorized admin/monitoring protections. No test route or OTP debug control may be reachable. Verify callbacks can reach only the documented endpoint; retain server-to-server verification and binding, and do not disable CSRF globally to permit callback return.
9. **Run native functional acceptance on the destination.** Verify owner login/MFA/recovery/revocation, product draft/media/preview/publish, guest/returning-customer cart/OTP/address, exact IRR quote and consent, create/verify/reconciliation, receipt/stock/order and tracking. Exercise an unknown provider outcome, replay and foreign-order denial; ensure saved attempts do not create another order or duplicate fulfillment. Separate controlled test transactions from real sales and agree cleanup/accounting before the first small real charge. Do not run load against real PSP/SMS. Readiness, native journey, media, DB permissions and worker tick/stop/restart must be actual results against the exact target image.
10. **Verify operations and recovery semantics.** Bind monitoring and schedulers to the new live manifest/tool/config identities; measure successful health and encrypted backup services within reviewed limits, then restore only prior explicitly enabled scheduling intent. Add independent offsite delivery/retention and an authorized received alert drill. For RPO≤15 minutes, implement and test a supported base-backup/WAL/PITR path, restore a chosen timestamp and record the newest recoverable transaction. After recovery, reconcile PSP payments beyond the recovery point before resuming fulfillment; absent recovered orders are not proof of failed payments. Measure full incident-to-business RTO separately from HTTP checks and backup age.
11. **Test public access, indexing and experience.** From outside the VPS test valid TLS/renewal, only intended IPv4/IPv6 ports, canonical redirects, cookies/Origin/CSRF, product and collection SEO, structured price units, robots/sitemap, private no-store and lack of test controls. Examine two Iranian mobile networks and fixed Internet on real devices for images, OTP, payment return and tracking. Record laboratory performance before release; p75 LCP/INP/CLS/RUM requires actual visitors and approved privacy rules. Previous synthetic E4 capacity does not qualify a new host or real providers.
12. **Cut over DNS and observe the agreed window.** Snapshot DNS beforehand and adjust only reviewed records; preserve unrelated MX/TXT/verification/mail records. Coordinate A and AAAA so stale IPv6 cannot reach an old or unprotected origin. Verify propagation and certificate/host routing from independent resolvers/networks. Start fulfillment only after the authoritative DB/payment reconciliation state is accepted. Retain old server/image/backup evidence under the agreed window and publish a safe final manifest, actual outcomes, limitations and responsible operators to main.

## Roll forward and failure handling

Before any schema change, record compatibility with the previous image. An application-image rollback does not rewind schema or finance. If compatibility is unknown, keep affected writers stopped and prepare a forward repair from retained evidence. Do not run old613 against schema13, reuse historical staging approvals, remove old restore pairs, use `down --volumes`, globally prune storage, or restore over the current ledger as routine rollback.

A pre-write DNS rollback may return traffic only to a still-compatible authoritative environment. After accepted new purchases, do not route buyers back to an old independent database: reconcile/transfer the authoritative changes through a reviewed plan first. A failed deploy/recovery keeps its journal, backup and partial state; retry with a new reviewed operation only after the cause and exact preserved state are understood.
